# MongoDB: основы

В PostgreSQL задача с комментариями — это две таблицы и `JOIN`. Если у задач разный набор полей (у одних есть чек-лист, у других вложения, у третьих напоминания), таблицу приходится расширять колонками, которые почти всегда пустые. MongoDB хранит каждую запись как **документ** — JSON-подобный объект, где вложенные списки и объекты лежат прямо внутри. Задачу вместе с комментариями можно прочитать одним запросом, а новое поле не требует миграции.

```bash
docker run -d --name mongo -p 27017:27017 mongo:7.0
pip install pymongo
```

## Минимальный пример

```python
from pymongo import MongoClient

client = MongoClient('mongodb://localhost:27017')
tasks = client.tasker.tasks

result = tasks.insert_one({
    'title': 'Сдать отчёт',
    'done': False,
    'owner': 'anna',
    'tags': ['работа', 'срочно'],
    'comments': [
        {'author': 'boris', 'text': 'Не забудь про графики'},
    ],
})

tasks.find_one({'_id': result.inserted_id})
# {'_id': ObjectId('6ae2480b8addc17de1204636'), 'title': 'Сдать отчёт', 'done': False, 'owner': 'anna',
#  'tags': ['работа', 'срочно'], 'comments': [{'author': 'boris', 'text': 'Не забудь про графики'}]}
```

Ни базу `tasker`, ни коллекцию `tasks` создавать заранее не нужно: они появятся при первой записи.

## Как это работает

Устройство похоже на реляционную базу, но с другими словами:

| PostgreSQL | MongoDB |
|---|---|
| база | база |
| таблица | коллекция |
| строка | документ |
| колонка | поле |
| первичный ключ | поле `_id` |

У каждого документа есть `_id`. Если не задать его самому, MongoDB создаст `ObjectId` — 12 байт, в которых зашито время создания (`result.inserted_id.generation_time`), поэтому такие id примерно сортируются по времени.

Схема не обязательна: документы одной коллекции могут иметь разные поля. Это свобода и одновременно ответственность — следить за формой данных теперь должен код (например, через [Pydantic](../../../languages/python/typing/pydantic.md)).

## Поиск

Запрос — это тоже документ: «найди документы, похожие на этот».

```python
tasks.insert_many([
    {'title': 'Купить хлеб', 'done': True, 'owner': 'anna', 'tags': ['дом'], 'priority': 1},
    {'title': 'Починить кран', 'done': False, 'owner': 'boris', 'tags': ['дом', 'срочно'], 'priority': 3},
    {'title': 'Записаться к врачу', 'done': False, 'owner': 'anna', 'priority': 2},
])

# Несколько условий — это И
tasks.find({'owner': 'anna', 'done': False}, {'_id': 0, 'title': 1})
# {'title': 'Сдать отчёт'}, {'title': 'Записаться к врачу'}

# Значение в массиве: ищет среди элементов
[t['title'] for t in tasks.find({'tags': 'срочно'})]
# ['Сдать отчёт', 'Починить кран']

# Операторы сравнения и сортировка
[t['title'] for t in tasks.find({'priority': {'$gte': 2}}).sort('priority', -1)]
# ['Починить кран', 'Записаться к врачу']

# ИЛИ и проверка наличия поля
[t['title'] for t in tasks.find({'$or': [{'done': True}, {'priority': {'$exists': False}}]})]
# ['Сдать отчёт', 'Купить хлеб']

# Поле во вложенном документе — через точку
[t['title'] for t in tasks.find({'comments.author': 'boris'})]
# ['Сдать отчёт']

tasks.count_documents({'done': False})  # 3
```

Второй аргумент `find` — **проекция**: какие поля вернуть (`1`) или скрыть (`0`).

## Изменение

Изменения описываются операторами, которые начинаются с `$`:

```python
tasks.update_one(
    {'title': 'Сдать отчёт'},
    {
        '$set': {'done': True},
        '$push': {'comments': {'author': 'anna', 'text': 'Готово'}},
    },
)

tasks.update_many({'tags': 'дом'}, {'$addToSet': {'tags': 'личное'}})  # добавить, если ещё нет
tasks.update_one({'title': 'Купить хлеб'}, {'$inc': {'priority': 1}, '$unset': {'done': ''}})

# Создать, если не нашёлся
tasks.update_one({'title': 'Новая'}, {'$set': {'done': False}}, upsert=True)

tasks.delete_many({'title': 'Новая'})
```

Изменение одного документа атомарно: `$push` комментария и `$set` статуса выполнятся вместе. Поэтому, если данные, которые меняются вместе, лежат в одном документе, транзакции часто не нужны.

## Индексы

Без индекса MongoDB просматривает всю коллекцию — в плане запроса это `COLLSCAN`:

```python
tasks.find({'owner': 'anna'}).explain()['queryPlanner']['winningPlan']['stage']  # 'COLLSCAN'

tasks.create_index([('owner', 1), ('done', 1)])
# теперь план: FETCH ← IXSCAN (поиск по индексу)
```

Уникальный индекс — как `UNIQUE` в SQL:

```python
db.users.create_index('email', unique=True)
db.users.insert_one({'email': 'anna@example.com'})
db.users.insert_one({'email': 'anna@example.com'})
# DuplicateKeyError: E11000 duplicate key error collection: tasker.users index: email_1 dup key: ...
```

## Вложить или сослаться

Главное решение при проектировании в MongoDB — класть ли связанные данные внутрь документа:

- **вложить**, если данные читаются вместе с родителем, принадлежат только ему и их немного: комментарии к задаче, адрес пользователя, чек-лист;
- **сослаться** (хранить `owner: 'anna'`), если данные нужны сами по себе, общие для многих документов или их может стать очень много. Пользователь — отдельный документ, а задачи ссылаются на него.

Лимит на один документ — 16 МБ. Массив, который растёт бесконечно (все действия пользователя за годы), лучше вынести в отдельную коллекцию.

## Асинхронный клиент

Для FastAPI нужен асинхронный драйвер. В PyMongo 4.13+ есть `AsyncMongoClient` с тем же API и `await` (в бета-версии он появился ещё в 4.9). Раньше для этого использовали отдельную библиотеку Motor, теперь она объявлена устаревшей.

## Частые ошибки

- **Опечатка в имени поля.** `find({'titel': 'Купить хлеб'})` не выдаст ошибку, а просто вернёт пусто: схемы нет, и поле `titel` «существует» у всех документов со значением «нет». Проверяйте данные на входе.
- **`_id` строкой.** `find_one({'_id': '6ae2480b...'})` вернёт `None`, потому что `_id` — это `ObjectId`, а не строка. Нужно `ObjectId('6ae2480b...')`.
- **Обновление без оператора.** `update_one(filter, {'done': True})` — PyMongo откажет: `ValueError: update only works with $ operators`. Для полной замены документа есть `replace_one`.
- **MongoDB вместо PostgreSQL «потому что без схемы».** Если данные связаны между собой, нужны `JOIN`, строгие ограничения и сложные транзакции, реляционная база проще. MongoDB хороша, когда данные естественно ложатся в документы.

## Когда не использовать

Если данные связаны между собой и читаются в разных разрезах — задачи по пользователям, пользователи по проектам, отчёты с `JOIN` по нескольким таблицам, — реляционная база проще: внешние ключи, ограничения и транзакции на несколько таблиц там есть сразу, а в MongoDB их приходится имитировать в коде. Для «гибкой схемы» в PostgreSQL часто хватает колонки `JSONB` рядом с обычными.

MongoDB не берут ради одной коллекции-кэша, счётчиков или очереди — для этого есть [Redis](../redis/basics.md). Полнотекстовый поиск с опечатками и релевантностью — задача [Elasticsearch](../elasticsearch/search.md), а не документной базы.
