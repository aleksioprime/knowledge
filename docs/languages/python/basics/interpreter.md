# Интерпретатор, GIL и сборщик мусора

Знать, как интерпретатор выполняет код, нужно, когда программа ведёт себя непонятно: память растёт, хотя объекты «удалены», потоки не ускоряют вычисления, а в проекте откуда-то берётся каталог `__pycache__`. За всем этим стоят байт-код и виртуальная машина, подсчёт ссылок и сборка мусора по поколениям, глобальная блокировка интерпретатора.

## Минимальный пример

```python run
import gc
import sys
import weakref


class Task:
    def __init__(self, title):
        self.title = title


task = Task("Купить хлеб")
alias = task
print(sys.getrefcount(task))  # 3: task, alias и аргумент getrefcount

task.parent = task  # цикл: объект ссылается сам на себя
ref = weakref.ref(task)
del task, alias
print(ref() is None)  # False — счётчик ссылок не обнулился из-за цикла

gc.collect()
print(ref() is None)  # True — сборщик мусора нашёл цикл и освободил объект
```

## Как это работает

Интерпретатор сначала переводит исходный код в байт-код, а потом выполняет его инструкция за инструкцией. Память объектов освобождает подсчёт ссылок, а циклы, которые он не видит, добирает сборщик мусора. GIL гарантирует, что в один момент байт-код выполняет только один поток.

### Интерпретатор Python

Видео по теме: [youtube.com/watch?v=f-jFxO2Kzlo](https://www.youtube.com/watch?v=f-jFxO2Kzlo).

Python — интерпретируемый язык: программу не нужно заранее компилировать, как в C или C++. Интерпретатор сам читает исходный код и выполняет его.

При первом запуске сценария интерпретатор проверяет синтаксис и компилирует код в байт-код (bytecode) — низкоуровневое представление исходного кода. Затем байт-код выполняет виртуальная машина Python (Python Virtual Machine, PVM): она по очереди читает инструкции байт-кода и исполняет их.

Байт-код функции можно посмотреть модулем `dis`:

```python run
import dis

def func_(x):
    return x % 2

dis.dis(func_)
```

#### Каталог `__pycache__` и файлы `.pyc`

Каталог `__pycache__` интерпретатор создаёт автоматически и хранит в нём скомпилированный байт-код импортированных модулей — и тех, что импортирует ваш сценарий, и тех, что импортируют они.

Файлы `.pyc` — это и есть скомпилированный байт-код. Они создаются при импорте модулей, а ещё их можно использовать, чтобы распространять модули или приложения в скомпилированном виде.

Файлы `.pyc` привязаны к версии Python: файл, созданный одной версией, не подойдёт другой.

### Сборщик мусора (GC)

Когда объект больше не нужен — например, на него не осталось ссылок, — он становится мусором (garbage), и сборщик мусора (garbage collector) освобождает его память.

Основа управления памятью в Python — подсчёт ссылок (reference counting): для каждого объекта хранится число ссылок на него. Когда оно становится равным нулю, память освобождается сразу.

Кроме этого, в Python есть сборка мусора по поколениям (generational garbage collection). Она делит объекты на несколько «поколений» и проверяет их с разной частотой. Этот механизм находит циклические ссылки, которые подсчёт ссылок не видит.

`sys.getrefcount` показывает число ссылок на объект. Оно на единицу больше ожидаемого: аргумент самой функции — тоже ссылка.

```python run
import sys

arr_1 = []
arr_2 = arr_1
print(sys.getrefcount(arr_1))
```

`gc.collect()` принудительно запускает сборку мусора и возвращает число найденных недостижимых объектов:

```python run
import gc

gc.collect()
```

#### Поиск утечек памяти

Для отладки утечек памяти есть сторонние инструменты:

- **memory_profiler** — запустите программу командой `python -m memory_profiler my_script.py`. Для функций с декоратором `@profile` появится построчный отчёт: сколько памяти используется в каждой строке и где она растёт.
- **objgraph** — рисует граф ссылок. Пример ниже создаст изображение `my_list.png` со всеми объектами, на которые ссылается `my_list`.

::: warning Этот пример запускайте локально
Нужны сторонние пакеты `memory_profiler` и `objgraph` (а для картинки — ещё Graphviz), в браузере их нет.
:::

```python
from memory_profiler import profile

@profile
def my_func():
    # код, который может вызывать утечку памяти
    pass
```

```python
import objgraph

my_list = [1, 2, 3]
objgraph.show_refs([my_list], filename='my_list.png')
```

### GIL

Статья по теме: [tproger.ru/translations/global-interpreter-lock-guide](https://tproger.ru/translations/global-interpreter-lock-guide).

Глобальная блокировка интерпретатора (Global Interpreter Lock, GIL) — механизм CPython, который гарантирует, что в любой момент времени байт-код Python выполняет только один поток. GIL защищает внутренние структуры интерпретатора в многопоточной среде и упрощает его реализацию.

## Частые ошибки

- Ожидание, что `del obj` сразу освободит память → объект живёт дальше, потому что на него ссылается другая переменная, элемент списка или замыкание → `del` удаляет только имя; проверьте `sys.getrefcount` и найдите, кто ещё держит ссылку.
- Циклические ссылки в объектах с `__del__` или в долгоживущих кэшах → память растёт, хотя объекты «удалены», и освобождается только при сборке мусора → разрывайте цикл явно или держите обратную ссылку через `weakref`.
- Потоки для вычислений на CPU → программа с четырьмя потоками работает не быстрее однопоточной, а иногда медленнее из-за переключений под GIL → для тяжёлых вычислений берите `multiprocessing`, потоки оставьте для ожидания ввода-вывода.
- `.pyc` или `__pycache__` в системе контроля версий → после смены версии Python или машины файлы бесполезны и только засоряют историю → добавьте `__pycache__/` в `.gitignore`.
- Вызов `gc.collect()` в горячем цикле «чтобы не текло» → каждый вызов обходит все отслеживаемые объекты, и программа заметно замедляется → доверьте сборку автоматике, а `gc.collect()` оставьте для отладки и редких точек, например после выгрузки большого набора данных.

## Когда не использовать

Ручное управление сборкой мусора (`gc.collect()`, `gc.disable()`, настройка порогов) почти никогда не нужно в прикладном коде: подсчёт ссылок освобождает большинство объектов сразу, а автоматический сборщик справляется с циклами. Вмешиваться стоит только после измерений, когда профилировщик показал, что паузы сборщика мешают.

Если задача упирается в GIL, обходить его через хитрости с потоками бесполезно. Для параллельных вычислений возьмите процессы (`multiprocessing`, `concurrent.futures.ProcessPoolExecutor`) или библиотеки, которые отпускают GIL в C-коде, например NumPy. Для ожидания сети и дисков подойдут потоки или `asyncio` — там GIL не мешает.
