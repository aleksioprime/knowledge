# Транзакции и оптимизация

Перевод денег — это два `UPDATE`, и если между ними упадёт сервер, деньги исчезнут с одного счёта и не появятся на другом. Транзакция делает группу операций неделимой: либо применяются все, либо ни одна. Вторая половина заметки — о том, что делать, когда запрос стал медленным: как прочитать план, зачем нужны индексы и почему `VACUUM` и `ANALYZE` влияют на скорость в PostgreSQL.

## Минимальный пример

```sql run
CREATE TABLE account (id INTEGER PRIMARY KEY, balance NUMERIC NOT NULL CHECK (balance >= 0));
INSERT INTO account VALUES (1, 100), (2, 0);

BEGIN;
UPDATE account SET balance = balance - 100 WHERE id = 1;
SAVEPOINT before_bonus;
UPDATE account SET balance = balance + 50 WHERE id = 2;
ROLLBACK TO SAVEPOINT before_bonus;   -- бонус отменён, перевод остался
UPDATE account SET balance = balance + 100 WHERE id = 2;
COMMIT;

SELECT * FROM account ORDER BY id;
-- 1 | 0
-- 2 | 100

CREATE INDEX account_balance_idx ON account (balance);
EXPLAIN SELECT * FROM account WHERE balance > 50;
-- Seq Scan on account  (cost=0.00..1.02 rows=1 width=36)
--   Filter: (balance > '50'::numeric)
-- таблица из двух строк: планировщик читает её целиком, индекс не нужен
```

## Как это работает

### Транзакции

Транзакция объединяет операции в атомарную единицу:

```sql
BEGIN;

UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;

COMMIT; -- или ROLLBACK
```

**ACID**:

- Atomicity — всё или ничего;
- Consistency — ограничения целостности сохраняются;
- Isolation — конкурентные транзакции получают определённые гарантии видимости;
- Durability — подтверждённые изменения переживают сбой.

Уровни изоляции и аномалии подробно разобраны в [справочнике PostgreSQL](../postgres/README.md#уровни-изоляции).

`SAVEPOINT` позволяет откатить часть транзакции:

```sql
SAVEPOINT before_optional_step;
-- изменения
ROLLBACK TO SAVEPOINT before_optional_step;
```

Держите транзакции короткими: долгие транзакции удерживают блокировки и snapshots, мешают очистке старых версий и увеличивают риск конфликтов.

### Индексы и оптимизация

Индекс — отдельная структура, ускоряющая чтение ценой места и более дорогих записей. Индексировать «каждый столбец» нельзя считать оптимизацией.

#### Базовый алгоритм оптимизации

1. Зафиксировать симптом: latency, частоту, объём результата, параметры и время деградации.
2. Получить реальный SQL и план `EXPLAIN (ANALYZE, BUFFERS)` на репрезентативных данных. Для изменяющего запроса использовать безопасную тестовую транзакцию или сначала обычный `EXPLAIN`.
3. Найти узел, где много времени, чтений, циклов, spill или сильное расхождение `rows` и `actual rows`.
4. Проверить блокировки, ожидания, I/O, CPU, память, временные файлы и конкурирующую нагрузку.
5. Проверить статистику, селективность условий, объём и распределение данных.
6. Уменьшить работу: отфильтровать раньше, не читать лишние столбцы, устранить лишние `DISTINCT`/сортировки, исправить N+1 и коррелированные вычисления.
7. Подобрать индекс под реальные `WHERE`, `JOIN`, `ORDER BY`; проверить порядок столбцов составного индекса.
8. При необходимости переписать запрос, партиционировать данные, предрассчитать тяжёлую агрегацию.
9. Повторно измерить на сопоставимой нагрузке и проверить побочные эффекты записи.

#### Откуда берётся стоимость плана

Планировщик оценивает:

- число строк и селективность по статистике (`ANALYZE`);
- распределение значений, наиболее частые значения, гистограммы, долю `NULL`, число различных значений;
- размер строк и таблиц;
- стоимость последовательного/случайного чтения страниц;
- стоимость обработки tuple, операторов и функций CPU;
- возможность индекса, сортировки, параллелизма и выбранного join-алгоритма.

В PostgreSQL `cost=startup..total` — **условные единицы**, не миллисекунды. Оптимизатор сравнивает корректные планы и обычно минимизирует итоговую стоимость. Ошибка оценки cardinality внизу дерева размножается и может привести к неверному join-порядку и алгоритму.

`EXPLAIN ANALYZE` реально выполняет запрос. Для `DELETE`/`UPDATE` он реально изменит данные, если не выполнять его в транзакции с последующим `ROLLBACK`.

### PostgreSQL: VACUUM, ANALYZE и spill

#### VACUUM

Из-за MVCC `UPDATE` и `DELETE` оставляют старые версии строк.

`VACUUM`:

- помечает место мёртвых версий доступным для повторного использования внутри таблицы;
- обновляет visibility map, помогая `Index Only Scan`;
- предотвращает wraparound transaction ID;
- обычно не уменьшает файл таблицы для ОС и допускает параллельную обычную работу.

`VACUUM FULL` переписывает таблицу, возвращает место ОС, требует дополнительного диска и берёт `ACCESS EXCLUSIVE` lock. Это тяжёлая операция, а не регулярная замена autovacuum.

#### ANALYZE

`ANALYZE` собирает статистику распределения данных для планировщика. Он не удаляет мёртвые версии. После крупной загрузки или резкого изменения распределения ручной `ANALYZE` может исправить оценки раньше autovacuum.

`VACUUM ANALYZE` последовательно выполняет обе задачи: очистку и сбор статистики.

#### Spill

**Spill to disk** — перенос промежуточных данных из оперативной памяти во временные файлы. Это не «spill-таблица» как постоянный объект.

Частые причины:

- сортировка не помещается в `work_mem`;
- hash join или hash aggregate превышает доступную память;
- materialization или оконная обработка требует большого промежуточного набора.

В плане ищите `Sort Method: external merge Disk`, несколько `Batches` у hash-узла и temp read/write buffers. Также полезны `log_temp_files` и статистика временных файлов.

Нельзя бездумно глобально увеличивать `work_mem`: лимит применяется к **каждому** подходящему узлу плана и параллельному worker, а одновременно работают многие запросы. Сначала уменьшите набор данных и исправьте план; затем при необходимости меняйте память адресно для сессии/транзакции.

## Частые ошибки

- Транзакция открыта, а код ушёл ждать внешний HTTP-запрос или ввод пользователя → `idle in transaction`, блокировки держатся минутами, autovacuum не может убрать старые версии → делать внешние вызовы до `BEGIN` или после `COMMIT`, ставить `idle_in_transaction_session_timeout`.
- Ошибка внутри транзакции PostgreSQL проигнорирована, выполнение продолжено → все следующие команды отвечают «current transaction is aborted» → откатывать транзакцию целиком или заранее ставить `SAVEPOINT` и возвращаться к нему.
- `EXPLAIN ANALYZE` для `UPDATE`/`DELETE` на рабочей базе → данные действительно изменены → оборачивать в `BEGIN; ... ROLLBACK;` или смотреть обычный `EXPLAIN`.
- Индекс на столбец, по которому фильтруют через функцию (`WHERE lower(email) = ...`) или с приведением типа → планировщик всё равно выбирает `Seq Scan` → создать индекс по выражению или писать условие так, как хранится столбец.
- Ручное увеличение `work_mem` в `postgresql.conf` после одного медленного отчёта → память умножается на число узлов и сессий, сервер уходит в swap → поднимать `work_mem` через `SET LOCAL` только для нужной транзакции и прежде всего уменьшать объём сортируемых данных.

## Когда не использовать

Явная транзакция лишняя для одиночного `INSERT` или `UPDATE`: каждая команда и так атомарна (режим autocommit). Оборачивать в `BEGIN ... COMMIT` чтение одного отчёта тоже не нужно, если не требуется согласованный снимок нескольких запросов. Длинные массовые операции, наоборот, лучше дробить на пачки, а не держать в одной многочасовой транзакции.

Индекс не стоит добавлять «про запас»: на маленькой таблице планировщик всё равно выберет последовательное чтение, а на часто обновляемой таблице каждый индекс замедляет запись. Если запрос выполняется раз в сутки и укладывается в допустимое время, оптимизация ему не нужна — сначала измерьте, потом меняйте.
