# JOIN

Задачи лежат в одной таблице, пользователи — в другой, а в отчёте нужно показать имя исполнителя рядом с названием задачи и не потерять пользователей, у которых задач нет. `JOIN` собирает строки из нескольких таблиц по условию в одну выборку. Здесь — логические виды соединений, разница между условием в `ON` и `WHERE`, физические алгоритмы и оценка числа строк в результате.

## Минимальный пример

```sql run
CREATE TABLE users (id INTEGER PRIMARY KEY, name TEXT NOT NULL);
CREATE TABLE task (id INTEGER PRIMARY KEY, title TEXT NOT NULL, user_id INTEGER REFERENCES users (id));

INSERT INTO users VALUES (1, 'Анна'), (2, 'Борис'), (3, 'Вера');
INSERT INTO task VALUES (1, 'Купить хлеб', 1), (2, 'Написать отчёт', 1), (3, 'Разобрать почту', NULL);

SELECT u.name, t.title
FROM users u
LEFT JOIN task t ON t.user_id = u.id
ORDER BY u.id, t.id;
-- Анна  | Купить хлеб
-- Анна  | Написать отчёт
-- Борис | NULL
-- Вера  | NULL

SELECT u.name, t.title
FROM users u
JOIN task t ON t.user_id = u.id
ORDER BY t.id;
-- Анна | Купить хлеб
-- Анна | Написать отчёт
```

## Как это работает

### Логические виды JOIN

Пусть `A` — левая таблица, `B` — правая.

| Вид | Результат |
|---|---|
| `INNER JOIN` | Только совпавшие пары A–B |
| `LEFT OUTER JOIN` | Все строки A; для несовпавших B заполнена `NULL` |
| `RIGHT OUTER JOIN` | Все строки B; для несовпавших A заполнена `NULL` |
| `FULL OUTER JOIN` | Все совпавшие пары и несовпавшие строки обеих таблиц |
| `CROSS JOIN` | Декартово произведение: каждая строка A с каждой B |
| Self join | Таблица соединена сама с собой через разные alias |
| Semi join | Строки A, для которых существует совпадение в B |
| Anti join | Строки A, для которых совпадения в B нет |

Semi/anti join обычно записываются через `EXISTS` / `NOT EXISTS`:

```sql
SELECT d.*
FROM departments d
WHERE EXISTS (
    SELECT 1
    FROM employees e
    WHERE e.department_id = d.id
);
```

`NATURAL JOIN` и `JOIN ... USING (...)` соединяют одноимённые столбцы. `NATURAL JOIN` хрупок: добавление одноимённой колонки может молча изменить результат, поэтому в прикладном коде лучше явный `ON`.

### Условие в ON и WHERE

Для `INNER JOIN` перенос условия между `ON` и `WHERE` часто эквивалентен. Для `OUTER JOIN` — нет:

```sql
-- сохраняет отделы без активных сотрудников
SELECT d.name, e.email
FROM departments d
LEFT JOIN employees e
  ON e.department_id = d.id
 AND e.active;

-- WHERE отбрасывает NULL-расширенные строки и превращает смысл в INNER JOIN
SELECT d.name, e.email
FROM departments d
LEFT JOIN employees e ON e.department_id = d.id
WHERE e.active;
```

### Физические алгоритмы JOIN

Логический `INNER/LEFT/...` описывает результат, а физический алгоритм — способ вычисления.

| Алгоритм | Идея | Хорошо работает когда |
|---|---|---|
| Nested Loop | Для каждой внешней строки ищет совпадения во внутреннем источнике | Внешний набор мал, на внутреннем есть подходящий индекс |
| Hash Join | Строит hash-таблицу по меньшей стороне и проверяет большую | Equality join, достаточно памяти |
| Merge Join | Читает обе стороны в порядке ключа и сливает | Входы уже отсортированы/индексированы или сортировка окупается |

Некоторые СУБД имеют дополнительные варианты. Алгоритм выбирает оптимизатор; название логического JOIN само по себе алгоритм не определяет.

### Сколько строк может вернуть JOIN

Для таблиц по 10 и 100 строк **без ограничений уникальности**:

| JOIN | Минимум | Максимум |
|---|---:|---:|
| `CROSS JOIN` | 1000 | 1000 |
| `INNER JOIN` | 0 | 1000 |
| `LEFT JOIN` | 10 | 1000 |
| `RIGHT JOIN` | 100 | 1000 |
| `FULL JOIN` | 100 | 1000 |

Максимум достигается, если каждая строка совпадает с каждой. Для `FULL JOIN` отсутствие совпадений даёт 110 строк, но минимум — 100: все 10 левых строк можно сопоставить с частью правых, сохранив итог не меньше большей стороны.

Если соединение идёт `PK = FK` или `PK = PK`, верхние границы ниже. На собеседовании всегда проговаривайте предположения об уникальности ключей и `NULL`.

## Частые ошибки

- Условие по правой таблице в `WHERE` после `LEFT JOIN` (`WHERE t.done = false`) → строки без пары отброшены, `LEFT JOIN` молча стал `INNER JOIN` → перенести условие в `ON` или добавить `OR t.id IS NULL`.
- Соединение по неуникальному столбцу → строки размножаются, `COUNT(*)` и `SUM` завышены → проверить уникальность ключа на одной из сторон или агрегировать её в подзапросе до соединения.
- Пропущено условие `ON` или в нём опечатка (`a.id = a.id`) → декартово произведение: миллионы строк и зависший запрос → всегда соединять по ключам обеих таблиц и проверять план на `Nested Loop` без условия.
- `NOT IN (SELECT user_id FROM task)` при `NULL` в `user_id` → анти-соединение возвращает ноль строк → использовать `NOT EXISTS` или добавить `WHERE user_id IS NOT NULL` в подзапрос.
- `NATURAL JOIN` или `USING` в прикладном коде → после добавления одноимённой колонки `updated_at` в обе таблицы результат пустеет → писать явный `ON`.

## Когда не использовать

`JOIN` лишний, когда нужна только проверка наличия связанных строк: `EXISTS` выражает намерение точнее и не размножает строки. Если данные второй таблицы нужны лишь для одного агрегата по группе, часто проще оконная функция или подзапрос в `SELECT`.

Соединения по десяти таблицам в каждом запросе — признак того, что для чтения стоит подготовить денормализованное представление (view, материализованное представление) или заранее посчитанную таблицу. А если таблицы живут в разных сервисах, соединять их в SQL нельзя: данные собирают на уровне приложения.
