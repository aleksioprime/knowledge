# Подзапросы, CTE и операции множеств

Чтобы найти задачи дольше средней или самую долгую задачу каждого пользователя, одного `SELECT` мало: нужен промежуточный результат, на который опирается основной запрос. Подзапросы и CTE позволяют собрать такой результат внутри одного выражения, а операции множеств — склеить или сравнить несколько выборок. Здесь — виды подзапросов, чем CTE отличается от подзапроса и как работают `UNION`, `INTERSECT` и `EXCEPT`.

## Минимальный пример

```sql run
CREATE TABLE task (id INTEGER PRIMARY KEY, title TEXT, user_id INTEGER, hours NUMERIC);
INSERT INTO task VALUES
    (1, 'Купить хлеб', 1, 0.5), (2, 'Написать отчёт', 1, 3),
    (3, 'Позвонить врачу', 2, 0.2), (4, 'Собрать стенд', 2, 4);

-- скалярный подзапрос: задачи дольше средней
SELECT title FROM task WHERE hours > (SELECT AVG(hours) FROM task) ORDER BY id;
-- Написать отчёт
-- Собрать стенд

-- CTE: самая долгая задача каждого пользователя
WITH longest AS (
    SELECT user_id, MAX(hours) AS max_hours FROM task GROUP BY user_id
)
SELECT t.user_id, t.title
FROM task t
JOIN longest l ON l.user_id = t.user_id AND l.max_hours = t.hours
ORDER BY t.user_id;
-- 1 | Написать отчёт
-- 2 | Собрать стенд

-- UNION склеивает строки и убирает дубликаты
SELECT user_id FROM task UNION SELECT 3 ORDER BY 1;
-- 1, 2, 3
```

## Как это работает

### Подзапросы и CTE

#### Подзапрос

Подзапрос — запрос внутри другого выражения. Он бывает:

- скалярным: одна строка и один столбец;
- табличным: несколько строк/столбцов;
- в `FROM` (derived table);
- в `WHERE`, `HAVING`, `SELECT` или DML.

**Некоррелированный** подзапрос не ссылается на внешний запрос и логически может быть вычислен независимо:

```sql
SELECT *
FROM employees
WHERE salary > (SELECT AVG(salary) FROM employees);
```

**Коррелированный** ссылается на текущую строку внешнего запроса:

```sql
SELECT e.*
FROM employees e
WHERE salary > (
    SELECT AVG(x.salary)
    FROM employees x
    WHERE x.department_id = e.department_id
);
```

Логически коррелированный подзапрос проверяется для внешних строк, но оптимизатор может преобразовать его в join или другой план. Не следует заранее считать, что он обязательно выполнится буквально N раз — смотрите `EXPLAIN`.

#### CTE

CTE — именованный результат в рамках одного SQL-выражения:

```sql
WITH department_stats AS (
    SELECT department_id, AVG(salary) AS avg_salary
    FROM employees
    GROUP BY department_id
)
SELECT e.*
FROM employees e
JOIN department_stats s USING (department_id)
WHERE e.salary > s.avg_salary;
```

Отличия от обычного подзапроса:

- CTE даёт имя и часто улучшает читаемость;
- на один CTE можно сослаться несколько раз;
- `WITH RECURSIVE` позволяет обходить деревья и графы;
- CTE не существует после завершения statement;
- это не автоматически «быстрее» и не временная таблица.

В современных PostgreSQL нематериализованный CTE, используемый один раз, обычно может быть встроен в запрос. `MATERIALIZED` принудительно создаёт промежуточный результат, `NOT MATERIALIZED` разрешает встраивание; решение влияет на оптимизацию.

### Объединение результатов

Операции множеств требуют одинакового числа столбцов и совместимых типов:

| Операция | Результат |
|---|---|
| `UNION` | Объединяет и удаляет дубликаты |
| `UNION ALL` | Объединяет и сохраняет дубликаты |
| `INTERSECT` | Общие строки |
| `EXCEPT` | Строки первого запроса, которых нет во втором |

`UNION ALL` обычно дешевле, потому что не делает дедупликацию. Имена результирующих столбцов берутся из первого запроса. Общий `ORDER BY` ставится после последней ветки.

`JOIN` добавляет **столбцы**, сопоставляя строки; `UNION` добавляет **строки** из совместимых выборок.

## Частые ошибки

- Скалярный подзапрос вернул несколько строк → ошибка «more than one row returned by a subquery used as an expression» → добавить агрегат, `LIMIT 1` с `ORDER BY` или переписать через `IN` / `EXISTS`.
- `NOT IN (SELECT ...)`, когда в подзапросе встречается `NULL` → внешний запрос возвращает ноль строк → использовать `NOT EXISTS` или отфильтровать `NULL` в подзапросе.
- `UNION` там, где дубликаты не нужно убирать → лишняя сортировка или хеширование на больших наборах, запрос медленный → брать `UNION ALL`, если строки заведомо различны или повторы допустимы.
- CTE, на который ссылаются несколько раз, помечен `MATERIALIZED` «на всякий случай» (или наоборот, в старых версиях PostgreSQL CTE всегда материализуется) → условия внешнего запроса не проталкиваются внутрь, читается вся таблица → проверить план и выбрать `MATERIALIZED` / `NOT MATERIALIZED` осознанно.
- `WITH RECURSIVE` без условия остановки или с циклом в данных → запрос не завершается → ограничить глубину счётчиком уровня или использовать `CYCLE` / проверку пройденного пути.

## Когда не использовать

Подзапрос лишний, когда нужные данные можно получить обычным `JOIN` или оконной функцией: «средняя по отделу рядом с зарплатой» — это `AVG(...) OVER (PARTITION BY department_id)`, а не коррелированный подзапрос на каждую строку. Цепочка из пяти вложенных подзапросов читается хуже, чем те же шаги, названные через `WITH`.

Операции множеств не подходят, когда нужно сопоставить строки по ключу и добавить столбцы — это задача `JOIN`. А если один и тот же промежуточный результат нужен нескольким запросам или сессиям, CTE не поможет: он живёт в пределах одного выражения, здесь нужна временная таблица или материализованное представление.
