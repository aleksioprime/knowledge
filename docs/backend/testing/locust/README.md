# Нагрузочное тестирование с помощью Locust

Сервис задач работает на одном пользователе, но что будет, когда одновременно зайдут пятьсот? Ответ до релиза даёт нагрузочное тестирование: оно проверяет производительность приложения под определённой нагрузкой и показывает, как ведёт себя приложение при одновременном доступе нескольких пользователей. Так находят узкие места до развертывания или перед событием с наплывом пользователей.

Locust — инструмент нагрузочного тестирования с открытым исходным кодом на Python. Сценарий виртуального пользователя описывается обычным классом: какие конечные точки вызывать, с какими паузами и как часто. Locust запускает нужное число таких пользователей и считает RPS, время ответа и ошибки.

## Минимальный пример

Файл `locustfile.py`: виртуальный пользователь запрашивает список задач и раз в несколько секунд создаёт новую.

```python
from locust import HttpUser, between, task


class TaskUser(HttpUser):
    wait_time = between(1, 3)

    @task(3)
    def list_tasks(self):
        self.client.get('/tasks')

    @task(1)
    def create_task(self):
        self.client.post('/tasks', json={'title': 'Купить хлеб'})
```

Запуск без веб-интерфейса: 50 пользователей, по 10 новых в секунду, 30 секунд.

```sh
pip install locust
locust -f locustfile.py --headless -u 50 -r 10 -t 30s --host http://localhost:8000
```

В конце Locust печатает сводку по каждому запросу:

```text
Type     Name          # reqs    # fails  |   Avg   Min   Max   Med  |  req/s failures/s
GET      /tasks           563   0(0.00%)  |    12     4    48    11  |  18.77      0.00
POST     /tasks           187   0(0.00%)  |    15     6    61    14  |   6.23      0.00
         Aggregated       750   0(0.00%)  |    13     4    61    12  |  25.00      0.00
```

Без `--headless` откроется интерфейс на http://localhost:8089, где число пользователей и графики задаются вручную.

## Как это работает

### Генерация нагрузки
Locust не создаёт реальные OS-потоки → он:
- использует gevent
- создаёт greenlet на каждого пользователя
- может держать 10 000+ VU в одном воркере
- но RPS зависит от задержек API

### Типы нагрузочных тестов
1. Load test
    - фиксированное количество VU
    - замер стабильной работы
2. Stress test
    - увеличиваешь VU до тех пор, пока сервис не упадёт
3. Spike test
    - резкое повышение нагрузки
4. Soak test
    - длительное тестирование (часы/сутки), чтобы поймать утечки памяти
5. Break-point test
    - бинарный поиск максимального количества VU

### Подсчёт RPS в Locust

RPS = total_requests_per_second = сумма вызовов всех задач * количество пользователей * частота цикла

Если хочешь максимальный RPS:
- wait_time = constant(0)
- маленькие задачи
- много воркеров

### Установка locust:
```sh
pip install locust
```

### Структура файла теста:
```python
from locust import HttpUser, task, between

class WebsiteUser(HttpUser):
    wait_time = between(1, 5)

    def on_start(self):
        print("Пользователь начал работу")

    def on_stop(self):
        print("Пользователь закончил работу")

    @task
    def index(self):
        # Задача, которая вызывается
        self.client.get("/")
```

### Настройка задержек (wait_time)
```python
wait_time = between(1, 3)
wait_time = constant(1)
wait_time = constant_pacing(1)
```
`constant_pacing(3)` — Locust гарантирует, что запросы выполняются каждые 3 секунды, учитывая длительность выполнения предыдущего запроса.

### Авторизация виртуального пользователя:
```python
def on_start(self):
    r = self.client.post(
        "/api/auth/login",
        data={"username": "user1", "password": "password"}
    )
    token = r.json()["access_token"]
    self.client.headers.update({"Authorization": f"Bearer {token}"})
```

### Ограничение времени жизни пользователя
```python
class MyUser(HttpUser):
    stop_timeout = 60  # VU живёт 60 секунд
```

### Вес задач (weight)
Вес определяет частоту выполнения задачи ("often" выполнится в 5 раз чаще)
```python
@task(5)
def often(self):
    ...

@task(1)
def rarely(self):
    ...
```

### Логирование ошибок
Locust автоматически помечает запрос как failure если response.status_code >= 400 или вручную вызван response.failure
```python
with self.client.get("/api/test", catch_response=True) as response:
    if response.status_code != 200:
        response.failure("Неверный код ответа!")
    else:
        response.success()
```

### Множественные группы пользователей
Можно создать несколько классов. В UI ты выбираешь, какие классы участвуют в тесте
```python
class Buyer(HttpUser):
    ...

class Admin(HttpUser):
    ...
```

### Headless-режим (без UI)
```sh
locust -f locustfile.py --headless -u 500 -r 20 -t 5m
```
- `-u` - количество пользователей
- `-r` - скорость появления
- `-t` - время теста

### Распределённый режим (master/worker)
```sh
# Запуск мастера
locust -f locustfile.py --master
# Запуск воркера
locust -f locustfile.py --worker --master-host=127.0.0.1
```

## Частые ошибки

- Нагрузка и приложение запущены на одной машине → процессор делят генератор и сервис, цифры занижены и непонятно, кто упёрся → запускать Locust на отдельной машине или хотя бы смотреть загрузку CPU обоих процессов.
- Запросы с разными ID в пути (`/tasks/1`, `/tasks/2`) → в отчёте тысячи строк по одному запросу на каждую, статистики нет → задавать общее имя: `self.client.get(f'/tasks/{task_id}', name='/tasks/[id]')`.
- Все пользователи стартуют сразу (`-r` равен `-u`) → пик соединений в первую секунду, ошибки от перегрузки не связаны с реальной нагрузкой → наращивать пользователей постепенно и смотреть на установившийся режим.
- Авторизация в каждой задаче, а не в `on_start` → половина RPS приходится на `/login`, тест измеряет не то → логиниться один раз при старте пользователя и хранить токен в заголовках клиента.
- Ответ 200 с ошибкой в теле считается успехом → сервис отвечает `{"error": ...}`, а отчёт зелёный → проверять тело через `catch_response=True` и вызывать `response.failure()`.
- Один воркер на тысячи RPS → Python-процесс упирается в CPU, и Locust предупреждает `CPU usage above 90%` → запускать распределённый режим с несколькими воркерами.
- Тест идёт в базу с реальными данными → после прогона тысячи задач «Купить хлеб» в продакшене → нагружать отдельный стенд с копией данных.

## Когда не использовать

Для проверки правильности ответов нужен не Locust, а [pytest](../pytest/README.md): нагрузочный тест отвечает на вопрос «сколько выдержит», а не «правильно ли». Если нужно просто оценить производительность одного endpoint без сценария, быстрее запустить `wrk` или `ab` одной командой. Для нагрузки на уровне десятков тысяч RPS с одного хоста Python-генератор станет узким местом, тогда берут k6 или Gatling.

Нагрузочный тест бесполезен без цели: сначала определите ожидаемую нагрузку и допустимое время ответа, иначе результат не с чем сравнивать.
