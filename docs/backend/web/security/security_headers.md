# Защитные HTTP-заголовки

Экранирование в шаблонах закрывает XSS там, где о нём подумали. Но в «Задачнике» десятки шаблонов, сторонний виджет чата и старый код, который кто-то когда-то пометил `| safe`. Защитные заголовки — второй слой: сервер одним ответом говорит браузеру, откуда можно грузить скрипты, можно ли показывать сайт во `<iframe>`, нужно ли ходить только по HTTPS. Даже если XSS всё-таки случилась, браузер не выполнит встроенный скрипт и не отправит данные на чужой домен. Заголовки настраиваются в одном месте (обычно в NGINX), поэтому это самая дешёвая защита из всех.

## Минимальный пример

Базовый набор в конфигурации NGINX:

```nginx
server {
    listen 443 ssl;
    server_name tasker.ru;

    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
    add_header Content-Security-Policy "default-src 'self'; object-src 'none'; frame-ancestors 'none'" always;
    add_header X-Content-Type-Options "nosniff" always;
    add_header Referrer-Policy "strict-origin-when-cross-origin" always;
    add_header Permissions-Policy "camera=(), microphone=(), geolocation=()" always;

    location / {
        proxy_pass http://app;
    }
}
```

Ответ сервера после перезагрузки конфигурации:

```http
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Strict-Transport-Security: max-age=31536000; includeSubDomains
Content-Security-Policy: default-src 'self'; object-src 'none'; frame-ancestors 'none'
X-Content-Type-Options: nosniff
Referrer-Policy: strict-origin-when-cross-origin
Permissions-Policy: camera=(), microphone=(), geolocation=()
```

`always` заставляет NGINX добавлять заголовки и к ответам с ошибками (4xx, 5xx) — без него страница 404 останется без защиты. Проверить, что заголовки дошли, можно командой `curl -sI https://tasker.ru` или в DevTools на вкладке Network.

## Как это работает

Набор заголовков зависит от приложения. Базовый ориентир — пять заголовков из примера.

### HSTS

`Strict-Transport-Security` заставляет браузер использовать HTTPS: получив заголовок один раз, он сам переписывает `http://` на `https://` и не даёт обойти ошибку сертификата. Это закрывает атаку, при которой первый запрос по HTTP перехватывают в открытой сети.

Не включайте долгий `max-age` и `includeSubDomains`, пока все затронутые домены не готовы: браузер запомнит правило на год, и поддомен без HTTPS станет недоступен. Начинают с `max-age=300`, проверяют и увеличивают. Директива `preload` добавляет домен в список, зашитый в браузеры, — это практически необратимо.

### CSP

`Content-Security-Policy` ограничивает источники скриптов, стилей и других ресурсов. В примере `default-src 'self'` разрешает грузить всё только со своего домена, `object-src 'none'` запрещает плагины, `frame-ancestors 'none'` — встраивание во `<iframe>`.

Главное следствие для XSS: встроенные скрипты (`<script>...</script>` внутри страницы и обработчики `onclick=`) по умолчанию запрещены. Внедрённый через название задачи скрипт не выполнится, а `fetch` на `evil.example` будет заблокирован, потому что домена нет в `connect-src`.

Политику следует адаптировать к приложению: для Vue-сборки, CDN со шрифтами и сервиса аналитики нужны свои директивы. Сначала политику проверяют в режиме `Content-Security-Policy-Report-Only`: браузер ничего не блокирует, но сообщает о нарушениях в консоль и по адресу из `report-to`. Когда отчёты перестают приходить, заголовок переименовывают в боевой.

### X-Content-Type-Options

`nosniff` запрещает браузеру угадывать MIME-тип вопреки `Content-Type`. Без него загруженный пользователем «текстовый» файл с HTML внутри браузер может выполнить как страницу.

### Referrer-Policy

Управляет информацией, передаваемой в `Referer` при переходе на другой сайт. `strict-origin-when-cross-origin` отдаёт чужим сайтам только домен, а не полный URL с идентификаторами и токенами в query-параметрах.

### Permissions-Policy

Отключает ненужные браузерные возможности: камеру, микрофон, геолокацию. Если сайту они не нужны, встроенный скрипт или сторонний виджет не смогут их запросить.

### Встраивание в iframe

`X-Frame-Options: DENY` можно оставить для старых клиентов, но современное управление встраиванием выполняет директива CSP `frame-ancestors`: она умеет перечислять разрешённые домены, а при конфликте браузер отдаёт предпочтение ей.

Защитные заголовки дополняют корректную обработку данных и контроль доступа, но не исправляют уязвимую бизнес-логику.

## Частые ошибки

- **`add_header` в `location` отменяет заголовки из `server`.** В NGINX директивы `add_header` не наследуются, если во вложенном блоке есть хоть одна своя. Выносите общий набор в файл и подключайте через `include` в каждом блоке.
- **Нет `always`.** Страницы ошибок уходят без заголовков, а именно на них часто отражается ввод пользователя.
- **CSP с `'unsafe-inline'` в `script-src`.** Так удобнее мигрировать, но защита от XSS при этом пропадает целиком. Переносите встроенные скрипты в файлы или используйте `nonce`.
- **HSTS включили, а поддомен без HTTPS остался.** С `includeSubDomains` он перестаёт открываться у всех, кто уже побывал на основном сайте, и «выключить» это у пользователей нельзя до истечения `max-age`.
- **Заголовки добавлены и в NGINX, и в приложении.** Два разных `Content-Security-Policy` применяются оба — работает более строгий, и понять, почему сломалось, трудно. Выберите одно место.
- **Полагаться на CSP вместо экранирования.** Старые браузеры и расширения политику могут не соблюдать; CSP — страховка, а не замена.

## Когда не использовать

Для чистого JSON API без HTML-страниц CSP, `Referrer-Policy` и `Permissions-Policy` почти не на что влиять: браузер не исполняет JSON. Там важнее `X-Content-Type-Options`, правильный `Content-Type` и HSTS, а остальное можно оставить минимальным.

Готовый строгий набор из чужой статьи не стоит включать на сайте с устаревшим фронтендом: встроенные обработчики и стили сломаются разом. Сначала `Report-Only`, затем поэтапное ужесточение.

`preload` для HSTS не нужен, пока домен может сменить владельца или потерять HTTPS: из списка браузеров домен удаляется месяцами.
