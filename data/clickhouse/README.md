# ClickHouse

**ClickHouse** — колоночная СУБД для аналитических OLAP-нагрузок, разработанная в Яндексе. Оптимизирована для быстрых запросов по большим объёмам данных: отчётов, агрегаций, дашбордов, логов и событий.

Особенности:
- Колоночное хранение данных
- Очень высокая скорость SELECT по миллиардам строк
- Векторизация и SIMD-инструкции
- Поддержка SQL (с расширениями)
- Движки таблиц (MergeTree, ReplicatedMergeTree, Distributed и др.)
- Репликация и шардирование

## Общая идея

ClickHouse создан не как универсальная база "для всего", а как быстрая аналитическая система.
Он особенно полезен там, где данные в основном добавляются, а запросы читают большие объёмы и считают сводные показатели.

Типичные данные для ClickHouse:
- события пользователей
- логи приложений
- метрики и телеметрия
- клики, просмотры, заказы
- финансовые и продуктовые отчёты

## Структура ClickHouse

На верхнем уровне ClickHouse похож на обычную SQL-базу:

```text
Сервер ClickHouse
└── База данных
    └── Таблица
        ├── Колонки
        ├── Партиции
        ├── Куски данных (parts)
        └── Индексы и метаданные
```

Основные элементы:

- **Сервер** — процесс ClickHouse, который принимает SQL-запросы, читает данные с диска и возвращает результат.
- **База данных** — логическая группа таблиц, примерно как schema/database в других СУБД.
- **Таблица** — набор данных с колонками и типами.
- **Движок таблицы** — важная особенность ClickHouse. Движок определяет, как таблица хранит данные, как они сливаются, реплицируются и читаются.
- **Партиция** — крупный логический кусок данных, обычно по дате: месяц, день, неделя.
- **Part** — физический кусок данных на диске. При вставках ClickHouse создаёт новые parts, а потом постепенно объединяет их в фоне.
- **Primary key / ORDER BY** — в ClickHouse это в первую очередь порядок сортировки данных на диске, а не уникальность строки.

Самое важное семейство движков — **MergeTree**. Большинство обычных таблиц в ClickHouse строятся на нём.

## Движки таблиц

В ClickHouse у каждой таблицы есть **движок** (`ENGINE`). Он определяет, как таблица хранит данные и как с ними работает.

Движок отвечает за:
- где и в каком формате лежат данные;
- как данные сортируются;
- как работают партиции;
- как выполняется фоновое слияние частей данных;
- есть ли репликация;
- является ли таблица локальной или распределённой;
- хранит ли таблица данные вообще.

Пример создания таблицы:

```sql
CREATE TABLE events
(
    id UInt64,
    user_id UInt64,
    event_name String,
    created_at DateTime
)
ENGINE = MergeTree()
PARTITION BY toYYYYMM(created_at)
ORDER BY (user_id, created_at);
```

Здесь:
- `ENGINE = MergeTree()` — таблица хранится на диске через движок MergeTree;
- `PARTITION BY` — крупное разбиение данных, например по месяцу;
- `ORDER BY` — порядок хранения данных на диске, от него сильно зависит скорость фильтрации.

### MergeTree

**MergeTree** — основной движок для обычных таблиц ClickHouse.
Он хранит данные на диске, сортирует их по `ORDER BY`, разбивает на партиции и в фоне объединяет маленькие куски данных в более крупные.

Подходит для:
- событий;
- логов;
- метрик;
- аналитических таблиц;
- больших append-only наборов данных.

Важная мысль: в ClickHouse `ORDER BY` — это не просто сортировка результата, а физический порядок хранения данных.
Если часто фильтровать по `user_id` и `created_at`, эти поля хорошо подходят для `ORDER BY`.

### ReplicatedMergeTree

**ReplicatedMergeTree** — версия MergeTree с репликацией.
Несколько серверов могут хранить копии одной и той же таблицы.

Репликация нужна, чтобы:
- не потерять данные при падении одной ноды;
- распределять чтение между копиями;
- обслуживать кластер без полной остановки.

Для координации реплик обычно используется ZooKeeper или ClickHouse Keeper.

### Distributed

**Distributed** — движок для распределённой таблицы.
Такая таблица сама обычно не хранит данные, а перенаправляет запросы на локальные таблицы других нод кластера.

Пример идеи:

```text
Distributed table
├── shard 1 -> local MergeTree table
└── shard 2 -> local MergeTree table
```

Через `Distributed` удобно делать запрос к кластеру как к одной таблице.
Данные физически лежат в локальных таблицах на шардах, а `Distributed` знает, куда отправить `SELECT` или `INSERT`.

### Другие движки

Кратко:

- **Memory** — хранит данные в памяти. Быстро, но данные пропадают после перезапуска.
- **Log / TinyLog / StripeLog** — простые движки для небольших таблиц и учебных примеров.
- **Null** — принимает данные, но не хранит их. Полезен для тестов и materialized views.
- **Kafka** — читает данные из Kafka.
- **S3** — работает с данными в S3-совместимом хранилище.

Для большинства практических задач сначала стоит разобраться с `MergeTree`, `ReplicatedMergeTree` и `Distributed`.

## Как хранятся данные

В стандартных строковых базах одна строка хранится целиком:

```text
id | user_id | event | created_at
1  | 42      | click | 2026-01-01
```

ClickHouse хранит данные по колонкам:

```text
id:         1, 2, 3, 4, ...
user_id:    42, 42, 17, 88, ...
event:      click, view, click, buy, ...
created_at: ...
```

Это удобно для аналитики. Если запросу нужны только `event` и `created_at`, ClickHouse не читает остальные колонки.

Плюсы колоночного хранения:
- меньше чтения с диска
- лучше сжатие данных
- быстрее агрегации по большим таблицам
- удобно считать `count`, `sum`, `avg`, `min`, `max`, `group by`

Минус: точечные изменения отдельных строк и частые маленькие `UPDATE`/`DELETE` для ClickHouse не являются основной задачей.

## OLTP и OLAP

Чтобы понять ClickHouse, важно различать два типа нагрузки: **OLTP** и **OLAP**.

**OLTP** (Online Transaction Processing) — обработка повседневных операций приложения.
Такая база хранит текущее состояние системы и быстро работает с отдельными записями.

Примеры OLTP:
- создать пользователя
- обновить статус заказа
- списать деньги со счёта
- найти одну запись по `id`
- сохранить комментарий

Для OLTP обычно используют PostgreSQL, MySQL и похожие строковые базы. Здесь важны транзакции, консистентность и быстрые изменения конкретных строк.

**OLAP** (Online Analytical Processing) — аналитическая обработка данных.
Такая база нужна, чтобы читать много строк сразу и отвечать на вопросы по истории данных.

Примеры OLAP:
- сколько заказов было по дням
- какие страницы чаще открывают пользователи
- средний чек по городам
- количество ошибок в логах за час
- конверсия по источникам трафика

ClickHouse относится к OLAP-системам. Он хорошо подходит для больших исторических таблиц, отчётов и агрегаций.

## Чем отличается от обычных БД

Простое сравнение:

| Вопрос | PostgreSQL/MySQL | ClickHouse |
|---|---|---|
| Основная задача | Состояние приложения | Аналитика и отчёты |
| Тип нагрузки | OLTP | OLAP |
| Хранение | По строкам | По колонкам |
| Хорошо умеет | Читать/изменять отдельные записи | Быстро сканировать большие объёмы |
| Частые UPDATE/DELETE | Нормально | Нежелательно |
| JOIN | Обычная часть модели | Есть, но лучше не строить всё вокруг JOIN |
| Транзакции | Важная часть системы | Ограниченная роль |
| Масштабирование | Часто вертикальное, есть репликация | Хорошо подходит для шардирования |

Главное отличие: PostgreSQL/MySQL обычно отвечают на вопрос "что сейчас происходит с конкретной сущностью?", а ClickHouse — "что происходило со многими событиями за период?".

## Когда использовать ClickHouse

ClickHouse стоит рассматривать, если:

- данные в основном добавляются, а не изменяются
- нужно быстро строить отчёты по большим таблицам
- запросы часто используют `count`, `sum`, `avg`, `group by`
- есть события, логи, метрики или история действий пользователей

ClickHouse не лучший выбор, если:

- нужна основная база приложения с частыми транзакциями
- важно часто обновлять отдельные строки
- нужно много точечных запросов по первичному ключу
- данные маленькие и PostgreSQL уже справляется

Частая архитектура: PostgreSQL хранит текущее состояние приложения, а ClickHouse хранит историю событий и данные для аналитики.
