# Атаки на сервер и HTTP-инфраструктуру

К задаче в «Задачнике» можно приложить файл, а в профиль — поставить аватар по ссылке. Обе функции выглядят безобидно, пока имя файла не окажется `../../etc/passwd`, а ссылка на аватар — `http://169.254.169.254/` (адрес облачных метаданных с ключами доступа). В этих атаках мишень — сам сервер и то, что стоит перед ним: прокси, DNS, облачная сеть. Они не требуют участия пользователя, и браузерные защиты от них не помогают.

## Минимальный пример

Уязвимая и исправленная функция, которая по имени вложения находит файл на диске:

```python run
from pathlib import Path

UPLOADS = Path('/srv/tasker/uploads').resolve()


def attachment_path_unsafe(name: str) -> Path:
    return UPLOADS / name


def attachment_path(name: str) -> Path:
    path = (UPLOADS / name).resolve()        # убирает '..' и символические ссылки
    if not path.is_relative_to(UPLOADS):
        raise PermissionError(f'путь выходит за каталог вложений: {name}')
    return path


print(attachment_path_unsafe('../../../etc/passwd'))   # /srv/tasker/uploads/../../../etc/passwd
print(attachment_path('report.pdf'))                    # /srv/tasker/uploads/report.pdf

try:
    attachment_path('../../../etc/passwd')
except PermissionError as error:
    print(error)                                        # путь выходит за каталог вложений: ../../../etc/passwd
```

Первая функция честно склеивает путь, а операционная система честно идёт по `..` вверх. Вторая сначала приводит путь к абсолютному виду, а затем проверяет, что он остался внутри каталога вложений. Ещё надёжнее вообще не брать имя файла от пользователя: хранить файл под случайным id, а настоящее имя — в базе.

## Как это работает

### SSRF

Server-Side Request Forgery возникает, когда сервер запрашивает переданный пользователем URL без достаточных ограничений. Атакующий может обратиться к внутренним сервисам, которые не видны снаружи (база, админка, Redis без пароля), или к облачным metadata endpoints и получить ключи доступа.

Уязвимо: `httpx.get(avatar_url)` с любым адресом из формы. Исправление — разрешать только то, что действительно нужно:

```python
import ipaddress
import socket
from urllib.parse import urlparse

ALLOWED_HOSTS = {'avatars.example.com', 'img.example.com'}


def check_avatar_url(url: str) -> None:
    parsed = urlparse(url)
    if parsed.scheme != 'https' or parsed.hostname not in ALLOWED_HOSTS:
        raise ValueError('аватар можно загрузить только с доверенных сайтов')
    for info in socket.getaddrinfo(parsed.hostname, 443):
        if ipaddress.ip_address(info[4][0]).is_private:
            raise ValueError('адрес указывает во внутреннюю сеть')
```

Защита: allowlist назначений, проверка разрешённого IP после DNS-резолвинга, запрет внутренних диапазонов и неожиданных схем (`file://`, `gopher://`), контроль перенаправлений (`follow_redirects=False` или проверка каждого адреса в цепочке) и сетевые ограничения исходящего трафика. Последнее — самое надёжное: если контейнер приложения не может достучаться до внутренней сети, ошибка в проверке URL не станет уязвимостью.

### Path traversal

Последовательности наподобие `../` позволяют выйти за разрешённый каталог. Варианты обхода: URL-кодирование (`%2e%2e%2f`), двойное кодирование, `..\` на Windows, символические ссылки внутри каталога. Поэтому проверять строку на `..` недостаточно — следует работать с внутренними идентификаторами файлов, нормализовать путь (`resolve()`) и проверять, что итоговый путь остаётся внутри заданного корня, как в примере выше.

### HTTP request smuggling

Если frontend-прокси и backend по-разному определяют границы запроса, злоумышленник может спрятать дополнительный запрос в теле первого. Особенно опасны неоднозначные комбинации `Content-Length` и `Transfer-Encoding`:

```http
POST /tasks HTTP/1.1
Host: tasker.ru
Content-Length: 4
Transfer-Encoding: chunked

0

GET /admin HTTP/1.1
```

Прокси верит `Content-Length` и считает, что тело — это `0\r\n\r`, а бэкенд верит `Transfer-Encoding`, видит конец чанков и принимает `GET /admin` как следующий запрос — уже от имени прокси, минуя его проверки.

Защита: обновлять прокси и серверы, отклонять неоднозначные запросы (современный NGINX и uvicorn это делают), нормализовать сообщения на границе и по возможности использовать однозначный протокол связи с upstream (HTTP/2 или отдельное соединение на запрос).

### Host Header attacks

Непроверенный `Host` может повлиять на абсолютные ссылки, сброс пароля или маршрутизацию. Классика: письмо для сброса пароля собирается как `f'https://{request.host}/reset?token=...'`, атакующий запрашивает сброс для Анны с заголовком `Host: evil.example`, и ссылка с настоящим токеном приходит Анне, но ведёт на чужой домен.

Сервер должен принимать только известные домены (`ALLOWED_HOSTS` в Django, `TrustedHostMiddleware` в FastAPI, `server_name` с запасным `server` блоком в NGINX) и не строить чувствительные URL из произвольного заголовка — только из настройки.

### Отказ в обслуживании

Slowloris удерживает множество соединений, очень медленно передавая запрос. Объёмные тела, дорогие endpoints и всплески запросов также истощают ресурсы.

Защита включает:

- таймауты чтения, отправки и соединения с upstream;
- ограничения размера заголовков и тела;
- лимиты соединений и частоты запросов;
- очереди, кеширование и ограничение конкурентных тяжёлых операций;
- внешний DDoS-фильтр для объёмных сетевых атак.

Базовые ограничения на стороне NGINX:

```nginx
limit_req_zone  $binary_remote_addr zone=login:10m rate=5r/m;
limit_conn_zone $binary_remote_addr zone=per_ip:10m;

server {
    client_max_body_size     10m;
    client_body_timeout      10s;
    client_header_timeout    10s;
    limit_conn per_ip 20;

    location /auth/ {
        limit_req zone=login burst=10 nodelay;
        proxy_pass http://app;
    }
}
```

Rate limiting снижает нагрузку, но сам по себе не заменяет аутентификацию, оптимизацию и внешнюю защиту канала.

## Частые ошибки

- **Проверка URL без разрешения DNS.** Имя `internal.evil.example` может указывать на `127.0.0.1`, а DNS rebinding меняет ответ между проверкой и запросом. Проверяйте IP, а лучше закрывайте исходящую сеть на уровне инфраструктуры.
- **Проверка на `..` в строке вместо нормализации пути.** Обходится кодированием и символическими ссылками.
- **`Host` как источник правды.** Ссылки в письмах и редиректы собираются из заголовка, а не из настройки `BASE_URL`.
- **Лимит частоты только по IP.** За одним NAT сидят сотни пользователей, а атакующий меняет адреса. Для входа лимит нужен ещё и по логину.
- **Нет таймаутов у исходящих запросов.** Зависший внешний сервис держит воркеры приложения, и отказ в обслуживании получается без всякой атаки — см. [таймауты в HTTPX](../../microservices/httpx/basics.md).
- **Стек ошибки в ответе.** Трассировка с путями и версиями библиотек — подарок атакующему. В продакшене ответ об ошибке должен быть общим, а подробности — в логах.

## Когда не использовать

Запрет внутренних адресов ломает функции, которым они нужны: вебхук на соседний сервис, прокси для внутренней админки. Для них делают отдельный клиент с явным списком разрешённых адресов, а не отключают проверку целиком.

Ограничение частоты на уровне приложения лишнее, если перед ним уже стоит NGINX или облачный балансировщик с теми же лимитами: дублировать их — значит дважды отлаживать одну настройку. Исключение — лимиты, которые зависят от пользователя (по логину, по тарифу): их знает только приложение.

Собственный разбор HTTP ради защиты от smuggling — плохая идея. Берите актуальные версии прокси и сервера приложений, они уже отклоняют неоднозначные запросы.
