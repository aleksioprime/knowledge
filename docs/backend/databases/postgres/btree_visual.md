# Поиск по индексу B-tree наглядно

Индекс B-tree — это дерево страниц: корень, один-два уровня внутренних узлов и листья, в которых лежат ключи со ссылками на строки таблицы. Поиск по нему — несколько сравнений и несколько прочитанных страниц, сколько бы строк ни было в таблице. Но только пока нужных строк мало.

## Как PostgreSQL ищет по индексу

Пройдите четыре запроса по шагам: точечный поиск, поиск отсутствующего ключа, узкий и широкий диапазоны.

<BTreeDemo />

Что видно на схеме:

- На каждом уровне достаточно сравнить значение с ключами узла, чтобы выбрать ребёнка. Глубина дерева растёт логарифмически: для миллиона строк это 3–4 уровня, для миллиарда — 5.
- Листья связаны в список. Диапазон читается одним спуском от корня и затем переходами к соседним листьям.
- В листе лежит не строка, а TID — адрес строки в таблице. За каждой найденной записью индекса идёт чтение страницы таблицы: для широкого диапазона эти чтения разбросаны по всей таблице и стоят дороже, чем прочитать её подряд.
- Поэтому планировщик выбирает индекс по оценке: сколько строк подойдёт под условие. Для `id > 5` он возьмёт Seq Scan, хотя индекс есть.

## Попробуйте сами

Таблица на 100 000 задач с индексом по `created_at`. Запросы выполняются в браузере, в настоящем PostgreSQL:

```sql run setup=btree
CREATE TABLE tasks AS
SELECT i AS id,
       'Задача ' || i AS title,
       timestamp '2024-01-01' + (i || ' minutes')::interval AS created_at
FROM generate_series(1, 100000) AS i;

CREATE INDEX tasks_created_at_idx ON tasks (created_at);
ANALYZE tasks;
```

Точечный поиск и узкий диапазон идут через индекс:

```sql run uses=btree
EXPLAIN (COSTS OFF)
SELECT * FROM tasks WHERE created_at = timestamp '2024-01-10 12:00';
```

```sql run uses=btree
EXPLAIN (COSTS OFF)
SELECT * FROM tasks
WHERE created_at BETWEEN timestamp '2024-01-10' AND timestamp '2024-01-11';
```

Широкий диапазон — почти вся таблица, и планировщик читает её подряд, хотя индекс подходит по условию:

```sql run uses=btree
EXPLAIN (COSTS OFF)
SELECT * FROM tasks WHERE created_at > timestamp '2024-01-02';
```

Сравните стоимость сами: `EXPLAIN (ANALYZE, BUFFERS)` покажет число прочитанных страниц (`Buffers: shared hit=...`) — у индексного поиска их единицы, у последовательного чтения сотни:

```sql run uses=btree
EXPLAIN (ANALYZE, BUFFERS, COSTS OFF, TIMING OFF, SUMMARY OFF)
SELECT * FROM tasks WHERE created_at = timestamp '2024-01-10 12:00';
```

## Частые ошибки

- Функция над индексированной колонкой: `WHERE date(created_at) = '2024-01-10'` → индекс по `created_at` не используется → перепишите условие как диапазон или создайте функциональный индекс.
- `LIKE '%текст%'` → B-tree ищет только по началу строки → для поиска по подстроке нужен GIN с `pg_trgm`.
- Индекс есть, а план всё равно Seq Scan → условие выбирает слишком много строк, или статистика устарела → проверьте оценку `rows` в `EXPLAIN` и выполните `ANALYZE`.
- Индекс на каждую колонку «на всякий случай» → каждая вставка и обновление обновляют все индексы → оставляйте индексы, которые реально используются в запросах.
