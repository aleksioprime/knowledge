# Celery: повторы, расписание и цепочки

Фоновые задачи ломаются: почтовый сервер не отвечает, внешний API возвращает 503. Кроме того, их часто нужно запускать по расписанию (каждое утро разослать напоминания) или собирать из нескольких шагов (загрузить данные → построить отчёт → отправить). В Celery для этого есть автоматические повторы, планировщик Beat и «канва» (canvas) — `chain`, `group` и `chord`.

## Минимальный пример

Повтор при сбое. Задача объявлена в том же `tasks.py`, где создан `app = Celery(...)` из заметки о [первой фоновой задаче](first_task.md):

```python
@app.task(bind=True, autoretry_for=(ConnectionError,), retry_backoff=1, retry_jitter=False, max_retries=3)
def flaky_send(self, to: str) -> str:
    print(f'попытка {self.request.retries + 1}')
    if self.request.retries < 2:
        raise ConnectionError('SMTP недоступен')
    return f'отправлено {to} с попытки {self.request.retries + 1}'
```

```text
попытка 1
Task tasks.flaky_send[3e4f...] retry: Retry in 1s: ConnectionError('SMTP недоступен')
попытка 2
Task tasks.flaky_send[3e4f...] retry: Retry in 2s: ConnectionError('SMTP недоступен')
попытка 3
```

```python
flaky_send.delay('anna@example.com').get()  # 'отправлено anna@example.com с попытки 3' — через 3 секунды
```

## Как это работает

### Как работают повторы

- `autoretry_for` — какие исключения считать временными. Повторять стоит только их: сеть, таймауты, 503. Ошибку в данных повтор не исправит.
- `retry_backoff` — пауза растёт экспоненциально: 1, 2, 4, 8… секунд. Так упавший сервис не завалят повторными запросами.
- `retry_jitter` — добавляет к паузе случайность (по умолчанию включён), чтобы тысяча задач не повторялась одновременно. В примере выключен, чтобы паузы были предсказуемыми.
- `max_retries` — после стольких повторов задача окончательно падает с исходным исключением.
- `bind=True` даёт доступ к `self.request`: номеру попытки, id задачи и аргументам.

Отложить выполнение можно и без ошибки — через `countdown` (секунды) или `eta` (момент времени):

```python
send_email.apply_async(args=['boris@example.com', 'Отчёт'], countdown=3)
```

### Расписание: Celery Beat

Beat — отдельный процесс, который в нужное время ставит задачи в очередь. Сам он ничего не выполняет: работают те же воркеры.

```python
# app/worker.py в «Задачнике»
from celery.schedules import crontab

celery_app.conf.update(
    timezone='Europe/Moscow',
    beat_schedule={
        'remind-about-due-tasks': {
            'task': 'app.worker.remind_about_due_tasks',
            'schedule': crontab(hour=9, minute=0),  # каждый день в 9:00
        },
    },
)
```

```bash
celery -A app.worker beat --loglevel=info
```

Расписание можно задать и числом секунд: `'schedule': 300.0` — каждые 5 минут.

В «Задачнике» Beat запущен отдельным сервисом в `docker-compose.yaml`. **Beat должен быть запущен в одном экземпляре.** Две копии поставят каждую задачу дважды.

Почему не ставить напоминание с `eta` в момент создания задачи пользователем? Срок задачи могут изменить, а задачу удалить. Кроме того, с брокером Redis задачи с далёким `eta` ведут себя ненадёжно (подробнее — в `visibility_timeout` в документации Celery). Ежедневная проверка по расписанию проще и всегда работает с актуальными данными.

### Цепочки и группы (canvas)

`.s(...)` — **сигнатура**: вызов задачи, который ещё не отправлен. Из сигнатур собирают сценарии.

**`chain`** — шаги по очереди, результат каждого передаётся первым аргументом в следующий:

```python
from celery import chain

chain(load_tasks.s(1), build_report.s())().get()
# '2 задачи: Купить хлеб, Сдать отчёт'
```

**`group`** — независимые задачи параллельно:

```python
from celery import group

group(count_tasks.s(user_id) for user_id in [1, 2, 3])().get()
# [3, 5, 2]
```

**`chord`** — группа, а когда завершатся все её задачи — итоговая задача со списком их результатов:

```python
from celery import chord

chord(count_tasks.s(user_id) for user_id in [1, 2, 3])(total.s()).get()
# 10
```

`chain` и `chord` передают результаты между задачами, поэтому им нужен result backend.

## Частые ошибки

- Повторы на любую ошибку (`autoretry_for=(Exception,)`) → задача с опечаткой в коде повторяется пять раз и только потом падает → перечислять только временные ошибки: сеть, таймауты, 503.
- Повтор без идемпотентности → письмо ушло, ошибка случилась после, и повтор отправляет второе письмо → отмечать результат (`reminder_sent`) или проверять его перед действием.
- Несколько копий Beat → при масштабировании в Kubernetes или Docker Swarm Beat запускается в каждой копии сервиса, и каждая задача по расписанию ставится несколько раз → выделить Beat в отдельный сервис с одним экземпляром.
- `result.get()` внутри задачи → ожидание результата другой задачи из задачи блокирует воркеры вплоть до полной остановки → собирать шаги через `chain` или `chord`.
- Не задан часовой пояс → `crontab(hour=9)` срабатывает в 9:00 по UTC, а не по местному времени → указывать `timezone` в настройках приложения.

## Когда не использовать

Повторы бесполезны для ошибок в данных и в коде: неверный email и `KeyError` не исправятся от второй попытки, такие задачи должны падать сразу и попадать в логи. Если каждое действие должно выполниться ровно один раз и повтор нельзя сделать безопасным, повторы отключают и обрабатывают сбой руками.

Beat лишний, когда задача одна и запускается раз в сутки: достаточно системного cron, который вызывает команду приложения. Canvas не нужен, если шаги выполняются внутри одного процесса и не требуют параллельности: обычный вызов функций читается проще, а `chain` и `chord` требуют result backend и усложняют отладку. Когда брокер и воркеры Celery в проекте избыточны, посмотрите на [Dramatiq](../dramatiq/README.md).
