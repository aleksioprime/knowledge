# Разбор: чат

Ещё одна классика собеседований: «Спроектируйте мессенджер». В отличие от [сокращателя ссылок](url_shortener.md), здесь сервер должен сам отправлять данные клиенту в момент события, держать миллионы открытых соединений и гарантировать порядок сообщений. Разберём по тем же шагам.

## Минимальный пример

Ядро сервиса сообщений: выдать сообщению номер внутри чата, **сначала сохранить** его в историю и только потом разослать тем, кто в сети. Тот, кто был офлайн, дочитает историю по номеру:

```python run
from collections import defaultdict

history: dict[int, list[dict]] = defaultdict(list)   # источник правды: база
seq: dict[int, int] = defaultdict(int)                # счётчик внутри чата
online: dict[str, list[dict]] = {'boris': []}         # открытые соединения


def send_message(chat_id: int, author: str, text: str) -> dict:
    seq[chat_id] += 1                                 # одно место выдаёт номер
    message = {'chat_id': chat_id, 'seq': seq[chat_id], 'author': author, 'text': text}
    history[chat_id].append(message)                  # сначала сохранить
    for user in ('anna', 'boris'):                    # потом разослать
        if user != author and user in online:
            online[user].append(message)
    return message


send_message(42, 'anna', 'Привет!')
send_message(42, 'anna', 'Отчёт готов?')
print([m['seq'] for m in history[42]])      # [1, 2]
print(online['boris'][-1]['text'])          # Отчёт готов?
print([m['text'] for m in history[42] if m['seq'] > 1])  # ['Отчёт готов?'] — дочитать после seq 1
```

## Как это работает

### 1. Требования

**Функциональные:**

- личные и групповые чаты (до нескольких сотен участников);
- сообщение доставляется собеседнику сразу, если он онлайн;
- история переписки с прокруткой вверх;
- статусы «доставлено» и «прочитано»;
- кто сейчас в сети.

**Нефункциональные:**

- задержка доставки — меньше секунды;
- сообщения не теряются и показываются в одном порядке у всех участников;
- сообщение, отправленное, пока собеседник был не в сети, он получит, когда появится.

### 2. Оценка нагрузки

Пусть 10 млн активных пользователей в день, каждый отправляет 40 сообщений:

```text
сообщений:       10 млн × 40 / 86 400 ≈ 4 600 в секунду, в пик ×3 ≈ 14 000
объём:           400 млн × 300 байт ≈ 120 ГБ в день, ≈ 44 ТБ в год
соединений:      30% онлайн одновременно → 3 млн открытых соединений
                 при 50 тысячах на сервер → 60 серверов соединений
```

Выводы: хранилище истории должно расти горизонтально, а главный вызов — не сообщения в секунду, а миллионы **постоянных соединений**.

### 3. Доставка в реальном времени

Обычный HTTP — это «клиент спросил, сервер ответил». Сервер не может сам сообщить о новом сообщении. Варианты:

- **опрос** (polling) — клиент раз в несколько секунд спрашивает «есть новое?». Просто, но большинство запросов впустую, а задержка — до интервала опроса;
- **долгий опрос** (long polling) — сервер держит запрос открытым, пока не появится событие;
- **WebSocket** — постоянное двустороннее соединение. Обе стороны отправляют сообщения, когда захотят. Стандартный выбор для чата. Как работать с ним в браузере — в заметке [WebSocket в JavaScript](../../languages/javascript/websocket.md).

### 4. Путь сообщения

Пользователи одного чата подключены к **разным** серверам соединений. Сервер Анны должен как-то передать сообщение серверу Бориса.

```text
Анна ──WS──► сервер соединений 1 ──► сервис сообщений ──► база (история)
                                            │
                                            └──► шина событий (Redis Pub/Sub, NATS, Kafka)
                                                       │
Борис ◄──WS── сервер соединений 7 ◄──────────────────┘
```

1. Сервер соединений получает сообщение от Анны и передаёт его сервису сообщений.
2. Сервис **сначала сохраняет** сообщение в базу и присваивает ему порядковый номер в чате. Только после этого отвечает Анне «отправлено».
3. Сервис публикует событие в шину. Каждый сервер соединений подписан на события тех чатов, участники которых к нему подключены.
4. Сервер Бориса отправляет сообщение по его WebSocket.

Для шины подходят [Redis Pub/Sub](../databases/redis/scenarios.md#бонус-публикация-событий) или [NATS](../microservices/broker/nats/README.md). Сообщения в шине не обязаны храниться долго: источник правды — база, а шина нужна только для мгновенной доставки.

### 5. Хранение истории

Запросы к истории однотипные: «последние 50 сообщений чата» и «50 сообщений до этого». Поэтому данные раскладывают по чатам:

```sql
CREATE TABLE messages (
    chat_id    BIGINT NOT NULL,
    seq        BIGINT NOT NULL,          -- порядковый номер внутри чата
    author_id  BIGINT NOT NULL,
    text       TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (chat_id, seq)
);

-- прокрутка вверх: keyset-пагинация, без OFFSET
SELECT * FROM messages
WHERE chat_id = $1 AND seq < $2
ORDER BY seq DESC
LIMIT 50;
```

Ключ `chat_id` — естественный ключ [шардирования](scaling.md#шардирование): вся переписка одного чата в одном шарде. На таком объёме часто берут Cassandra или ScyllaDB, они созданы для записи огромного потока данных, разложенных по ключу. Почему keyset лучше `OFFSET` — в [задачах по PostgreSQL](../databases/postgres/tasks.md).

### 6. Порядок сообщений

Часы на разных серверах расходятся на миллисекунды, поэтому сортировать по `created_at` нельзя: два почти одновременных сообщения могут поменяться местами. Номер `seq` выдаёт одно место для каждого чата — например, `INCR chat:42:seq` в Redis или счётчик в строке чата под блокировкой. У всех участников сообщения выстраиваются по `seq` одинаково.

Пропуск в номерах (пришли 41 и 43) клиент сразу замечает и дозапрашивает недостающее.

### 7. Офлайн, статусы и «в сети»

- **Не в сети.** Если у получателя нет открытого соединения, сообщение всё равно сохранено. Сервис отправляет push-уведомление (APNs, FCM), а при подключении клиент запрашивает всё, что новее последнего известного ему `seq`.
- **«Доставлено» и «прочитано».** Клиент сообщает серверу номер последнего полученного и последнего прочитанного сообщения в каждом чате. Хранить статус для каждого сообщения не нужно — достаточно одного числа на пару «пользователь — чат».
- **Кто в сети.** Клиент раз в 30 секунд отправляет «я здесь», а сервер обновляет ключ в Redis со сроком жизни 60 секунд: `SET presence:anna 1 EX 60`. Ключ есть — пользователь в сети. Ключ истёк — вышел, даже если соединение оборвалось без прощания.

### Итоговая схема

```text
клиенты ⇄ WebSocket ⇄ серверы соединений (60+) ⇄ шина событий (Redis / NATS)
                              │                         ▲
                              ▼                         │
                       сервис сообщений ───────────────┘
                        │        │        │
                 история (по chat_id)  Redis (seq, «в сети»)  push-уведомления
```

## Частые ошибки

- Доставка до сохранения → сообщение ушло собеседнику, а сохранить не успели, и после перезагрузки оно исчезает из истории → сначала сохранить, потом разослать.
- Сортировка по времени сервера → часы расходятся, и сообщения меняются местами у разных участников → порядковый номер внутри чата.
- Один сервер соединений «на всех» → собеседники на разных серверах не видят сообщений друг друга → шина событий между серверами соединений.
- `OFFSET` для истории → прокрутка далеко вверх становится всё медленнее → keyset-пагинация по `seq`.
- Статус для каждого сообщения → «прочитано» на каждое из миллиардов сообщений раздувает базу → хранить номер последнего прочитанного на пару «пользователь — чат».

## Когда не использовать

Для чата поддержки на сайте с сотней одновременных пользователей шестьдесят серверов соединений, шина и Cassandra лишние: одно приложение с WebSocket, таблица `messages` в PostgreSQL и Redis для «в сети» решают задачу. Шину между серверами добавляют, когда соединений становится больше, чем держит один процесс, а шардирование истории — когда таблица перестаёт помещаться на одной базе.

Если сообщения нужны редко и задержка в несколько секунд допустима (уведомления в админке, лента событий), постоянное соединение не обязательно: достаточно [SSE или периодического опроса](../frameworks/fastapi/realtime.md). А если «чат» на деле односторонний — рассылка объявлений пользователям — это задача [системы уведомлений](notifications.md), а не мессенджера.
