# Двухфакторная аутентификация и капча

Пароли утекают: пользователь берёт один и тот же пароль на десяти сайтах, один из них взламывают, и через неделю кто-то входит в «Задачник» с правильной парой логин—пароль. Сам пароль тут не поможет, хоть хешируй его [идеально](crypto.md#хранение-паролей). Двухфакторная аутентификация (2FA) требует ещё одно доказательство, которого у атакующего нет. Капча решает соседнюю задачу: отличить человека от скрипта, который массово регистрирует аккаунты или перебирает пароли.

## Минимальный пример

```python
import time

import pyotp

secret = pyotp.random_base32()       # создаётся на сервере при подключении 2FA
totp = pyotp.TOTP(secret)
print(totp.provisioning_uri(name='anna@example.com', issuer_name='Задачник'))
# otpauth://totp/%D0%97%D0%B0%D0%B4%D0%B0%D1%87%D0%BD%D0%B8%D0%BA:anna%40example.com?secret=E2PFTZLHPS6YOG6M7TVUJ67R626KEJSH&issuer=%D0%97%D0%B0%D0%B4%D0%B0%D1%87%D0%BD%D0%B8%D0%BA

code = totp.now()                     # то же покажет приложение-аутентификатор
print(code, totp.verify(code))        # 021642 True

old_code = totp.at(time.time() - 30)  # код из прошлого 30-секундного окна
print(totp.verify(old_code))                  # False
print(totp.verify(old_code, valid_window=1))  # True
print(totp.verify(totp.at(time.time() - 90), valid_window=1))  # False
```

URI превращают в QR-код (например, библиотекой `qrcode`) и показывают пользователю. Он сканирует его в Яндекс Ключе, Google Authenticator или менеджере паролей, и приложение начинает показывать шестизначные коды.

## Факторы

Фактор — категория доказательства:

- **знание** — пароль, PIN, ответ на секретный вопрос;
- **владение** — телефон, аппаратный ключ, приложение-аутентификатор;
- **свойство** — отпечаток пальца, лицо (обычно не отправляется на сервер, а разблокирует ключ на устройстве).

Двухфакторная — это два **разных** фактора. Пароль плюс секретный вопрос — два знания, их крадут одним и тем же способом (фишинг, утечка), так что это не 2FA.

## SMS

Самый привычный второй фактор: код приходит в SMS. Он лучше, чем ничего, но слабее остальных:

- **SIM-swap** — атакующий убеждает оператора перевыпустить SIM-карту на свой телефон и получает все SMS;
- SMS перехватываются через уязвимости сигнальных сетей (SS7) и вредоносные приложения на телефоне;
- фишинговый сайт просит ввести код из SMS и тут же использует его на настоящем сайте;
- каждое сообщение стоит денег, а массовая отправка на платные номера — отдельный вид мошенничества (SMS pumping).

Поэтому SMS часто оставляют как запасной способ, а основным делают TOTP или ключи доступа.

## TOTP

TOTP (Time-based One-Time Password, RFC 6238) работает без связи между сервером и телефоном. При подключении сервер и приложение получают **общий секрет** (в примере 32 символа base32 = 160 бит). Дальше обе стороны независимо считают:

```text
шаг  = floor(unix_time / 30)
код  = последние 6 цифр от HMAC-SHA1(секрет, шаг)   (с «динамическим усечением» из RFC 4226)
```

Совпадают часы — совпадают коды. Часы на телефоне могут немного расходиться, а пользователь вводит код несколько секунд, поэтому сервер обычно принимает и соседние шаги: **окно ±1** (`valid_window=1`) — это 90 секунд. Шире делать не стоит: каждый дополнительный шаг упрощает подбор.

Секрет нельзя хешировать — серверу нужно считать по нему коды. Его хранят **зашифрованным**, с ключом вне базы ([шифрование полей](crypto.md#шифрование-полей-в-базе)). Утечка секретов вместе с ключом обнуляет 2FA для всех пользователей.

### Повторное использование кода

`totp.verify` принимает один и тот же код сколько угодно раз в течение его окна. Если код подсмотрели через плечо или перехватили на фишинговой странице, им можно войти вторым. RFC 6238 советует запоминать последний принятый шаг и не принимать коды с тем же или более ранним шагом:

```python
import time

import pyotp

STEP = 30


class TwoFactor:
    def __init__(self, secret: str):
        self.totp = pyotp.TOTP(secret, interval=STEP)
        self.last_used_step = -1          # в базе — колонка рядом с секретом

    def check(self, code: str) -> bool:
        current = int(time.time() // STEP)
        for step in (current - 1, current, current + 1):    # окно ±1 шаг
            if step <= self.last_used_step:
                continue                                     # этот или более ранний код уже потрачен
            if pyotp.utils.strings_equal(self.totp.generate_otp(step), code):
                self.last_used_step = step
                return True
        return False


anna = TwoFactor(pyotp.random_base32())
code = anna.totp.now()
print(anna.check(code))          # True
print(anna.check(code))          # False — второй раз тот же код не сработает
print(anna.check('000000'))      # False
```

`strings_equal` из `pyotp` сравнивает за постоянное время, как [`hmac.compare_digest`](crypto.md#сравнение-за-постоянное-время). В многопоточном сервере обновление `last_used_step` должно быть атомарным: `UPDATE ... SET last_used_step = :step WHERE id = :id AND last_used_step < :step` и проверка, что строка обновилась.

Шесть цифр — это миллион вариантов, и с окном ±1 угадать код с одной попытки можно с вероятностью 3 на миллион. Без ограничения числа попыток это подбирается, поэтому ввод кода ограничивают так же, как ввод пароля: несколько ошибок — пауза или блокировка.

## Подключение 2FA

1. Пользователь, уже вошедший по паролю, нажимает «Включить 2FA».
2. Сервер генерирует секрет, сохраняет его как **неподтверждённый** и показывает QR-код (и секрет текстом — на случай, если камера недоступна).
3. Пользователь вводит первый код из приложения. Только после успешной проверки 2FA включается.

Шаг 3 обязателен: без него пользователь, который отсканировал QR не тем приложением или закрыл окно, сразу теряет доступ к аккаунту. Отключение 2FA и смена секрета требуют повторного ввода пароля и текущего кода — иначе украденная сессия позволит снять защиту.

## Резервные коды

Телефон теряют. На этот случай при подключении 2FA выдают 8–10 одноразовых резервных кодов и просят их сохранить. Хранить их нужно как пароли — **только хешами**:

```python
import hashlib
import hmac
import os
import secrets

KEY = os.environ.get('BACKUP_CODES_KEY', 'dev-only-key').encode()   # секрет вне базы


def digest(code: str) -> str:
    return hmac.new(KEY, code.strip().lower().encode(), hashlib.sha256).hexdigest()


def make_backup_codes(count: int = 10) -> tuple[list[str], list[str]]:
    codes = ['-'.join(secrets.token_hex(2) for _ in range(3)) for _ in range(count)]
    return codes, [digest(code) for code in codes]   # коды показать один раз, хеши сохранить


def use_backup_code(code: str, stored: list[str]) -> bool:
    for item in stored:
        if hmac.compare_digest(item, digest(code)):
            stored.remove(item)                       # код одноразовый
            return True
    return False


codes, stored = make_backup_codes()
print(codes[:2], len(stored))                          # ['4297-707b-7278', '4549-4f09-6ccb'] 10
print(use_backup_code(codes[0].upper(), stored), len(stored))  # True 9
print(use_backup_code(codes[0], stored))               # False
```

Коды случайные (48 бит), а не придуманные человеком, поэтому медленная функция здесь не обязательна. Но и голый SHA-256 от 48 бит на видеокартах перебирается за часы-дни, поэтому используется HMAC с ключом вне базы — без ключа украденные хеши бесполезны. Вариант попроще — хешировать тем же argon2id, что и пароли. Каждое использование резервного кода стоит сообщать пользователю письмом.

## Запомненные устройства

Чтобы не спрашивать код при каждом входе, предлагают «Запомнить это устройство на 30 дней». Сервер ставит долгоживущую cookie (`HttpOnly`, `Secure`) со случайным токеном, а в базе хранит его хеш, id пользователя, срок и описание устройства. Пользователь видит список устройств и может отозвать любое; при смене пароля и отключении 2FA список очищается. Запомненное устройство пропускает только второй фактор, пароль спрашивают как обычно.

## WebAuthn и ключи доступа

WebAuthn — стандарт браузера для входа по криптографическому ключу. При регистрации устройство (телефон, ноутбук, аппаратный ключ YubiKey) создаёт пару ключей **для конкретного домена**: закрытый остаётся на устройстве, открытый уходит на сервер. При входе сервер присылает случайную строку, устройство подписывает её закрытым ключом после отпечатка пальца или PIN, сервер проверяет подпись открытым ключом.

Главное преимущество — **защита от фишинга**: ключ привязан к домену, и на `tasker-login.ru` браузер просто не предложит ключ от `tasker.ru`. TOTP и SMS так не умеют — код с фишинговой страницы работает на настоящей. На сервере нет ничего секретного: утечка базы открытых ключей ничего не даёт.

**Ключи доступа (passkeys)** — те же ключи WebAuthn, которые синхронизируются между устройствами через iCloud, Google или менеджер паролей. Они могут заменить пароль целиком: владение устройством плюс биометрия или PIN — уже два фактора. Для Python есть библиотека `webauthn` (py_webauthn).

## Капча

### От картинок к скорингу

1. **Искажённый текст.** Первые капчи (начало 2000-х) показывали кривые буквы. Распознавание текста быстро научилось их читать, а живые люди ошибались всё чаще.
2. **Картинки.** «Выберите все светофоры» — задачи, сложные для машинного зрения того времени. Сейчас нейросети решают их не хуже людей, а за пару копеек решение покупается у людей на фермах капч.
3. **Невидимая капча со скорингом.** reCAPTCHA v3, Yandex SmartCaptcha и Cloudflare Turnstile ничего не спрашивают у большинства пользователей. Скрипт на странице собирает сигналы — поведение мыши, характеристики браузера, репутацию IP — и выдаёт токен. Сервер капчи оценивает запрос (в reCAPTCHA v3 — числом от 0 до 1), и только подозрительным показывают задание.

### Проверка на сервере

Виджет на странице выдаёт **токен**, который отправляется вместе с формой. Сам по себе токен ничего не доказывает — его надо проверить на сервере капчи с серверным ключом. Без этой проверки бот просто пришлёт любую строку. Пример для Yandex SmartCaptcha:

```python
import httpx

VERIFY_URL = 'https://smartcaptcha.yandexcloud.net/validate'


def captcha_passed(client: httpx.Client, token: str, user_ip: str, server_key: str) -> bool:
    try:
        response = client.post(VERIFY_URL, data={'secret': server_key, 'token': token, 'ip': user_ip}, timeout=3)
        response.raise_for_status()
    except httpx.HTTPError:
        return False      # сервис капчи недоступен: здесь не пускаем, но это решение политики
    return response.json().get('status') == 'ok'
```

Функция проверена с подменённым транспортом (`httpx.MockTransport`), запросов к настоящему сервису не было: ответ `{"status": "ok"}` даёт `True`, `{"status": "failed"}` — `False`. У reCAPTCHA адрес `https://www.google.com/recaptcha/api/siteverify`, поля `secret`, `response`, `remoteip`, а в ответе `success`, `score`, `action` и `hostname` — их тоже стоит проверять: токен мог быть получен на другом сайте или для другого действия.

Серверный ключ — секрет, как любой другой: в переменных окружения, не во фронтенде.

### Где ставить

- **Регистрация** — защита от массового создания аккаунтов.
- **Вход после N неудачных попыток** с одного IP или для одного логина. Всем подряд капча на входе не нужна — она раздражает.
- **Восстановление пароля, отправка SMS** — каждое такое действие стоит денег или рассылает письма.
- **Публичные формы** — комментарии, обратная связь.

### Капча не заменяет ограничение частоты

Капчу решают: сервисы-распознаватели продают тысячу решений за доллар-два, а скоринг обходят настоящими браузерами на жилых IP. Капча лишь делает атаку дороже. Ограничение частоты (rate limit) по IP, по логину и по аккаунту, блокировка после серии ошибок и уведомление о входе с нового устройства нужны всегда. Подробнее об ограничении запросов — в [Атаки на сервер](server_attacks.md#отказ-в-обслуживании) и [NGINX](../nginx/README.md).

## Частые ошибки

- **2FA, которую можно обойти.** Код проверяется на форме входа, но API выдаёт токен уже после пароля, или восстановление пароля по почте молча отключает 2FA. Второй фактор должен стоять на всех путях к сессии.
- **Нет защиты от перебора кода.** Шесть цифр без лимита попыток подбираются.
- **Секрет TOTP в открытом виде в базе.** Шифруйте его.
- **Резервные коды в открытом виде** или многоразовые.
- **Включение 2FA без подтверждения первым кодом** — пользователи блокируют сами себя.
- **Токен капчи проверяется только на фронтенде** или не проверяется вовсе.
- **Второй шаг не привязан к первому.** Форма кода берёт `user_id` из запроса, и атакующий, зная свой пароль и свой код, подставляет чужой id. После пароля выдают короткоживущий промежуточный токен «пароль проверен для пользователя N», и форма кода работает только с ним.
