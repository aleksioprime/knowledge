# Гонка потоков и Lock наглядно

Два потока увеличивают один счётчик, а в итоге он меньше, чем должен быть. Это состояние гонки (race condition): результат зависит от того, в какой момент интерпретатор переключил потоки. GIL от неё не защищает — он следит за тем, чтобы байткод выполнял один поток за раз, но переключать потоки может между любыми двумя инструкциями.

## Как теряется обновление

Пройдите оба сценария по шагам. Код отличается одной строкой — `with lock:`.

Что видно на схеме:

- `counter += 1` — три байткод-инструкции: прочитать значение, прибавить единицу, записать обратно. Между любыми из них поток могут снять с выполнения.
- Если оба потока прочитали старое значение, второй записывает своё поверх первого, и одно увеличение пропадает.
- `Lock` закрывает все три шага в критическую секцию: пока блокировка занята, второй поток спит в `acquire()` и даже не тратит GIL.
- Цена — в критической секции потоки работают по очереди. Чем она длиннее, тем меньше выигрыш от потоков.

## Попробуйте сами

В браузере настоящие потоки недоступны, поэтому ниже переключение потоков смоделировано: каждый «поток» — генератор, который отдаёт управление после каждой инструкции, а планировщик переключает их по кругу — как GIL, только предсказуемо. Без блокировки оба потока читают один и тот же `counter`:

```python run
from collections import deque

counter = 0


def worker(name, times):
    global counter
    for _ in range(times):
        value = counter          # 1. читать
        yield f'{name}: прочитал {value}'
        value += 1               # 2. прибавить
        yield f'{name}: прибавил → {value}'
        counter = value          # 3. записать
        yield f'{name}: записал {value}'


def run(threads):
    queue = deque(threads)
    while queue:                 # планировщик: по одной инструкции на поток по кругу
        thread = queue.popleft()
        try:
            print(next(thread))
            queue.append(thread)
        except StopIteration:
            pass


run([worker('T1', 2), worker('T2', 2)])
print(f'counter = {counter}, ожидали 4')
```

Та же модель с блокировкой. Поток, который не смог её взять, пропускает ход, пока блокировку не отдадут:

```python run
from collections import deque

counter = 0
lock_owner = None


def worker(name, times):
    global counter, lock_owner
    for _ in range(times):
        while lock_owner not in (None, name):
            yield f'{name}: lock занят, жду'
        lock_owner = name
        value = counter
        yield f'{name}: прочитал {value}'
        value += 1
        yield f'{name}: прибавил → {value}'
        counter = value
        yield f'{name}: записал {value}'
        lock_owner = None


def run(threads):
    queue = deque(threads)
    while queue:
        thread = queue.popleft()
        try:
            print(next(thread))
            queue.append(thread)
        except StopIteration:
            pass


run([worker('T1', 2), worker('T2', 2)])
print(f'counter = {counter}, ожидали 4')
```

В обычном скрипте с настоящими потоками картина та же, только переключения случайны, поэтому результат без блокировки каждый раз разный:

```python
from threading import Thread, Lock

counter = 0
lock = Lock()


def work():
    global counter
    for _ in range(100_000):
        with lock:          # уберите эту строку — и counter станет меньше 200 000
            counter += 1


threads = [Thread(target=work) for _ in range(2)]
for t in threads:
    t.start()
for t in threads:
    t.join()
print(counter)  # 200000
```

## Частые ошибки

- Надежда на GIL → «один поток за раз» не значит «одна операция за раз»; составные операции (`+=`, проверка и запись, чтение и изменение словаря) всё равно рвутся → закрывайте их `Lock`.
- Блокировка на весь цикл, а не на критическую секцию → потоки работают строго по очереди, параллелизма ввода-вывода нет → держите блокировку только вокруг общих данных.
- Две блокировки в разном порядке в разных потоках → взаимная блокировка (deadlock): каждый ждёт другого → берите блокировки всегда в одном порядке или используйте одну.
- `lock.acquire()` без `release()` при исключении → блокировка остаётся занятой навсегда → используйте `with lock:`.

## Когда не использовать

Если общего состояния нет, блокировка не нужна: потоки, которые только читают данные или пишут каждый в свой объект, не конфликтуют. Для счётчиков и очередей между потоками есть готовые потокобезопасные инструменты — `queue.Queue`, `itertools.count` под блокировкой внутри, атомарные операции в базе данных.
