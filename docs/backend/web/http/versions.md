# Версии HTTP

Страница тянет десятки картинок и скриптов, а браузер по HTTP/1.1 ждёт их по очереди; сервисы внутри системы открывают соединение на каждый вызов. Версия HTTP решает, сколько запросов пойдёт по одному соединению и что случится при потере пакета. Это стоит знать, когда настраиваешь NGINX, выбираешь gRPC или читаешь вывод `curl -v`.

## Минимальный пример

```bash
# Какую версию выбрали клиент и сервер: видно по ALPN и первой строке ответа
curl -sv --http2 https://example.com -o /dev/null 2>&1 | grep -E 'ALPN|using HTTP|^< HTTP'
# * ALPN: curl offers h2,http/1.1
# * ALPN: server accepted h2
# * using HTTP/2
# < HTTP/2 200

# Принудительно HTTP/1.1 — текстовая стартовая строка со словом OK
curl -sI --http1.1 https://example.com | head -1
# HTTP/1.1 200 OK

# HTTP/3, если curl собран с его поддержкой, а сервер объявил Alt-Svc
curl -sI --http3 https://example.com | head -1
# HTTP/3 200
```

## Как это работает

Версии HTTP сохраняют общую семантику методов, статусов и заголовков, но по-разному передают сообщения по сети.

| Версия | Транспорт | Основная особенность |
|---|---|---|
| HTTP/1.1 | TCP | Текстовый формат, постоянные соединения, запросы обычно обслуживаются последовательно |
| HTTP/2 | TCP + обычно TLS | Бинарные кадры, мультиплексирование потоков, сжатие заголовков HPACK |
| HTTP/3 | QUIC поверх UDP + TLS 1.3 | Независимые потоки без блокировки всего соединения при потере пакета |

### HTTP/1.1

Несколько запросов могут переиспользовать одно TCP-соединение (`keep-alive`). Браузеры часто открывают несколько соединений к одному серверу, потому что потеря пакета или долгий ответ задерживает следующие ответы на том же соединении.

### HTTP/2

Одно соединение содержит несколько параллельных потоков. Это уменьшает потребность в отдельных TCP-соединениях, но потеря TCP-пакета временно задерживает все потоки соединения.

### HTTP/3

QUIC реализует надёжную доставку и TLS поверх UDP. Потеря данных в одном потоке не блокирует остальные потоки. Для работы нужны поддержка клиента, сервера и сетевой доступ по UDP.

### Согласование версии

При HTTPS клиент и сервер выбирают HTTP/1.1 или HTTP/2 во время TLS-рукопожатия через ALPN. Поддержка HTTP/3 обычно объявляется сервером заголовком `Alt-Svc`, после чего клиент может установить QUIC-соединение.

## Частые ошибки

- Ожидают HTTP/2 на сайте без TLS → браузеры не поддерживают HTTP/2 без шифрования (h2c), всё идёт по HTTP/1.1 → включить TLS и `http2` в NGINX; проверить через `curl -v`.
- NGINX проксирует на бэкенд по умолчанию через HTTP/1.0 → keep-alive к upstream не работает, на каждый запрос новое соединение → `proxy_http_version 1.1;`, `proxy_set_header Connection "";` и `keepalive` в `upstream`.
- Объявили `Alt-Svc` с HTTP/3, а UDP/443 закрыт на файрволе → клиент пробует QUIC, ждёт и откатывается на TCP, первые запросы медленнее → открыть UDP/443 либо не объявлять HTTP/3.
- Оставили приёмы эпохи HTTP/1.1: доменный шардинг, склейку скриптов и спрайты → на HTTP/2 они мешают: лишние соединения и TLS-рукопожатия, хуже кеширование → убрать, мультиплексирование делает это ненужным.
- Считают, что HTTP/2 ускоряет всё → на мобильной сети с потерями стало хуже, потому что потеря одного TCP-пакета тормозит все потоки → для таких клиентов HTTP/3 или оставить несколько соединений HTTP/1.1.

## Когда не использовать

HTTP/3 не нужен для внутренних вызовов между сервисами в одном дата-центре: сеть там надёжна, а UDP часто закрыт. Там хватает HTTP/2 — на нём работает gRPC (см. [проектирование API](api_design.md#grpc)).

HTTP/1.1 остаётся уместным для простых прокси, старых клиентов, скриптов на `curl` и отладки: текстовый формат читается глазами и через `nc`. Включать HTTP/3 на публичном сайте стоит только после проверки, что балансировщик и CDN его поддерживают, иначе клиенты будут тратить время на неудачные попытки.
