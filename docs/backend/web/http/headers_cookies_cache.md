# Заголовки, cookies и кеширование

Один и тот же адрес отдаёт разным пользователям разные данные, браузер должен помнить, кто вошёл, а повторное открытие страницы не должно заново тянуть мегабайты. Всё это делается заголовками: `Content-Type` и `Accept` договариваются о формате, `Set-Cookie` хранит сессию, `Cache-Control` и `ETag` управляют кешем. Ошибка в одном заголовке — и чужой профиль уедет из кеша другому пользователю.

## Минимальный пример

```http
GET /api/tasks HTTP/1.1
Host: example.com
Accept: application/json

HTTP/1.1 200 OK
Content-Type: application/json
Set-Cookie: session=abc123; Path=/; Secure; HttpOnly; SameSite=Lax
Cache-Control: private, max-age=60
ETag: "tasks-v42"

[{"id": 1, "title": "Купить хлеб"}]

GET /api/tasks HTTP/1.1
Host: example.com
Cookie: session=abc123
If-None-Match: "tasks-v42"

HTTP/1.1 304 Not Modified
ETag: "tasks-v42"
```

Первый ответ ставит cookie сессии и помечает данные как персональные (`private`), которые можно переиспользовать минуту. Второй запрос приносит cookie обратно и спрашивает, изменился ли ресурс; сервер отвечает `304` без тела.

## Как это работает

### Частые заголовки

| Заголовок | Назначение |
|---|---|
| `Host` | Домен, к которому обращается клиент |
| `Content-Type` | Формат тела сообщения |
| `Content-Length` | Размер тела в байтах |
| `Accept` | Предпочтительные форматы ответа |
| `Accept-Encoding` | Поддерживаемое сжатие, например `gzip` или `br` |
| `Authorization` | Учётные данные или токен доступа |
| `User-Agent` | Информация о клиенте |
| `Location` | Адрес созданного ресурса или перенаправления |
| `Vary` | Какие заголовки запроса влияют на вариант кешированного ответа |

Названия заголовков регистронезависимы. Прокси и сервер не должны доверять клиентским `X-Forwarded-*`, если запрос пришёл не от доверенного прокси.

### Cookies

Сервер устанавливает cookie заголовком `Set-Cookie`, а браузер возвращает её в `Cookie`:

```http
Set-Cookie: session=abc123; Path=/; Secure; HttpOnly; SameSite=Lax
```

- `Secure` — отправлять только по HTTPS;
- `HttpOnly` — запретить чтение из JavaScript;
- `SameSite` — ограничить межсайтовую отправку и снизить риск CSRF;
- `Domain` и `Path` — ограничить область действия;
- `Max-Age` или `Expires` — задать срок хранения.

В cookie не стоит хранить секретные данные в открытом виде. Даже подписанное значение пользователь может прочитать.

### Кеширование

```http
Cache-Control: public, max-age=3600
ETag: "version-42"
```

Клиент может проверить актуальность ресурса:

```http
If-None-Match: "version-42"
```

Если ресурс не изменился, сервер возвращает `304 Not Modified` без тела. Для персональных или чувствительных данных обычно используют `Cache-Control: private` или `no-store`. Заголовок `Vary` должен отражать все параметры запроса, от которых зависит представление, иначе прокси может отдать ответ не тому клиенту.

## Частые ошибки

- Персональный ответ отдан с `Cache-Control: public` или без `private` → CDN или прокси показывает чужой профиль другому пользователю → `Cache-Control: private` для личных данных, `no-store` для чувствительных.
- Ответ зависит от `Accept-Language` или `Authorization`, а `Vary` не указан → кеш отдаёт английскую версию русскому пользователю или ответ для другого аккаунта → перечислить в `Vary` все заголовки, от которых зависит ответ.
- Cookie сессии без `Secure` и `HttpOnly` → утекает по HTTP и читается скриптом при XSS → ставить оба флага и подходящий `SameSite`.
- `SameSite=None` без `Secure` → браузер молча отбрасывает cookie, пользователь «не может войти» во встроенном виджете → `SameSite=None; Secure`.
- `no-cache` используют вместо `no-store` → ответ всё равно сохраняется на диск и лишь перепроверяется перед использованием → для секретов и персональных данных `no-store`.
- Сервер верит `X-Forwarded-For` от любого клиента → подделка IP, обход ограничений по адресу → принимать заголовок только от доверенного прокси (в NGINX — `set_real_ip_from`).

## Когда не использовать

Cookie не нужны машинным клиентам и мобильным приложениям, которые ходят в API напрямую: им проще передавать токен в `Authorization: Bearer`, см. [аутентификацию по JWT](../../frameworks/fastapi/auth_jwt.md). Cookie остаются для браузера, где нужны автоматическая отправка и защита `HttpOnly`.

HTTP-кеширование бесполезно для ответов, которые меняются на каждый запрос или зависят от десятка параметров: там `no-store`, а экономят на стороне сервера — кешем запросов к базе. `ETag` и `max-age` окупаются на статике и редко меняющихся справочниках.
