# Разбор: сокращатель ссылок

Классическая задача на собеседовании по проектированию систем: «Спроектируйте сервис вроде bit.ly». Она кажется простой: принять длинную ссылку, выдать короткую, перенаправить. Но на ней удобно показать весь ход рассуждения: требования → оценка нагрузки → API → хранение → генерация кодов → масштабирование.

По этому плану сделан рабочий учебный проект [../../practice/projects/shortener/README.md](../../practice/projects/shortener/README.md): случайные коды base62 с повтором при конфликте, PostgreSQL, кэш кодов и счётчики переходов в Redis.

## 1. Требования

Сначала уточняем, что именно строим. На собеседовании эти вопросы задают интервьюеру.

**Функциональные:**

- по длинной ссылке получить короткую: `https://sho.rt/4c92`;
- по короткой ссылке перенаправить на исходную;
- (опционально) свой код вместо случайного, срок действия ссылки, статистика переходов.

**Нефункциональные:**

- перенаправление быстрое: десятки миллисекунд;
- сервис почти всегда доступен: сломанная ссылка в рассылке на миллион человек — серьёзная проблема;
- короткую ссылку нельзя угадать или перебрать подряд, если ссылки приватные.

## 2. Оценка нагрузки

Грубые прикидки на салфетке (back-of-the-envelope) показывают, какого масштаба нужна система. Допустим, создаётся 100 миллионов ссылок в месяц, а читают их в 100 раз чаще:

```text
запись:  100 000 000 / (30 × 24 × 3600) ≈ 39 в секунду
чтение:  39 × 100 ≈ 3 900 в секунду
за 5 лет: 100 млн × 12 × 5 = 6 млрд ссылок
объём:   6 млрд × 500 байт ≈ 3 ТБ
```

Выводы: запись — не проблема, а чтения много, и его нужно кэшировать. 3 ТБ за пять лет — это много, но не огромно: одна база с репликами справится, шардирование понадобится не сразу.

## 3. API

```text
POST /api/links          {"url": "https://example.com/very/long/path"}
→ 201 {"code": "4c92", "short_url": "https://sho.rt/4c92"}

GET /4c92
→ 302 Location: https://example.com/very/long/path
```

**301 или 302?** `301 Moved Permanently` браузер запомнит и в следующий раз пойдёт на исходный адрес сам, минуя сервис. Это экономит нагрузку, но переходы уже не посчитать, а ссылку не изменить. `302 Found` (или `307`) заставляет каждый раз заходить в сервис. Если нужна статистика — выбирают 302.

## 4. Хранение

```sql
CREATE TABLE links (
    id         BIGSERIAL PRIMARY KEY,
    code       VARCHAR(10) UNIQUE NOT NULL,
    url        TEXT NOT NULL,
    owner_id   BIGINT,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    expires_at TIMESTAMPTZ
);
```

Главный запрос — `SELECT url FROM links WHERE code = $1`. Он идёт по уникальному индексу и выполняется за доли миллисекунды. Связей и сложных запросов нет, поэтому подойдёт и PostgreSQL, и хранилище «ключ → значение» (DynamoDB, Cassandra).

## 5. Генерация коротких кодов

Сколько символов нужно? Буквы обоих регистров и цифры — 62 символа:

```text
6 символов: 62⁶ ≈ 56,8 млрд
7 символов: 62⁷ ≈ 3,5 трлн
```

Семи символов хватит на 6 млрд ссылок с огромным запасом.

**Способ 1: счётчик + base62.** Берём числовой `id` из базы и записываем его в системе счисления с основанием 62:

```python
import string

ALPHABET = string.digits + string.ascii_letters  # 0-9a-zA-Z, 62 символа


def encode(number: int) -> str:
    if number == 0:
        return ALPHABET[0]
    chars = []
    while number:
        number, remainder = divmod(number, 62)
        chars.append(ALPHABET[remainder])
    return ''.join(reversed(chars))


encode(1)                  # '1'
encode(62)                 # '10'
encode(1_000_000)          # '4c92'
encode(3_521_614_606_207)  # 'ZZZZZZZ' — последний семисимвольный код
```

Коды никогда не повторяются. Но они идут подряд: зная свой код `4c92`, можно перебрать соседние `4c91`, `4c93` и найти чужие ссылки. Если ссылки приватные, это недопустимо. Помогает перемешивание: шифровать `id` обратимой функцией перед кодированием.

**Способ 2: случайный код.** Генерируем 7 случайных символов (`secrets.choice`) и пытаемся вставить. Если код занят, уникальный индекс не даст вставить дубль, и мы просто генерируем новый. При 6 млрд ссылок из 3,5 трлн вариантов коллизия случается примерно в одном случае из 600, поэтому повтор почти никогда не нужен.

**Способ 3: хэш от ссылки.** Первые 7 символов от `sha256(url)`. Одна и та же ссылка всегда получает один код, но коллизии разных ссылок всё равно нужно обрабатывать, а два пользователя не смогут получить разные коды для одной ссылки со своей статистикой.

Для большинства сервисов подходит способ 2 — он прост и не раскрывает соседние ссылки.

## 6. Масштабирование чтения

На 3 900 запросов в секунду хватит нескольких копий приложения за балансировщиком и реплик базы. Но проще всего защитить базу [кэшем](caching.md): популярные ссылки читают намного чаще остальных, и сотня тысяч горячих ключей в Redis снимает с базы большую часть нагрузки.

```text
GET /4c92 → Redis: link:4c92 → (промах) → PostgreSQL → записать в Redis на сутки → 302
```

Ссылки почти не меняются, поэтому инвалидация простая: при удалении или изменении ссылки удалить ключ из кэша.

## 7. Статистика переходов

Писать в базу `UPDATE links SET clicks = clicks + 1` на каждый переход — значит превратить быстрое чтение в запись под блокировкой строки. Вместо этого перенаправление публикует событие «переход по 4c92» в [Kafka](../microservices/broker/kafka/fastapi.md) или копит счётчики в Redis, а отдельный обработчик агрегирует их и раз в минуту записывает в аналитическое хранилище, например [ClickHouse](../databases/clickhouse/README.md).

## Итоговая схема

```text
клиент → балансировщик → API (N копий) → Redis (кэш кодов)
                               │             ↓ промах
                               │        PostgreSQL (primary + реплики)
                               └→ Kafka → обработчик статистики → ClickHouse
```

## Частые ошибки

- **Сразу шардирование и пять видов хранилищ.** Сначала оценка нагрузки. Для 39 записей в секунду одной базы достаточно.
- **Коды подряд для приватных ссылок.** Их можно перебрать.
- **301 при нужной статистике.** Браузер перестанет приходить в сервис, и переходы не посчитать.
- **Счётчик переходов обновлением строки.** Популярная ссылка превращается в горячую строку с постоянными блокировками.
- **Нет защиты от злоупотреблений.** Сокращатели любят спамеры и фишеры. Нужны [ограничение частоты](../databases/redis/scenarios.md#3-ограничение-частоты-запросов-rate-limiting) и проверка ссылок по спискам опасных сайтов.
