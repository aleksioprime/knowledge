# CI/CD

Тесты запускают «когда вспомнят», образ собирают на ноутбуке у того, кто сегодня на месте, а выкладка на сервер — набор команд из личных заметок. В результате в `main` попадает сломанный код, а выпуск откладывают, потому что страшно. CI/CD убирает ручные шаги: каждый push автоматически проверяется, из проверенного кода собирается артефакт, и он тем же способом едет на тестовое окружение и в продакшен. Выпуск становится обычным делом, а не событием.

## Содержание

- [GitHub Actions](github/README.md) — линтер, тесты с PostgreSQL и Redis, проверка API в Docker, шаблон деплоя
- [Kubernetes](kubernetes/README.md) — Deployment, Service, Ingress, проверки здоровья, обновление без остановки на k3s в Docker; оркестраторы, устройство кластера, kind, kubeconfig и kubectl
- [Portainer](portainer/README.md) — UI для управления Docker / Kubernetes

## Минимальный пример

Конвейер в GitHub Actions: на каждый push и pull request запускаются линтер и тесты. Файл кладут в `.github/workflows/`, и больше ничего настраивать не нужно.

```yaml
# .github/workflows/ci.yml
name: CI

on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.12'
      - run: pip install -r requirements.txt
      - run: ruff check .      # линтер; ненулевой код возврата — проверка красная
      - run: pytest            # тесты; результат виден в pull request: ✓ test
```

Подробный конвейер с базой, Redis и деплоем — в заметке [GitHub Actions](github/README.md).

## Как это работает

Конвейер (pipeline) — цепочка шагов, которые сервер CI выполняет на каждое изменение в репозитории: проверка кода, сборка артефакта, развёртывание. Пока шаг не прошёл, следующий не начинается, поэтому в продакшен попадает только то, что прошло все проверки.

### CI: Continuous Integration (Непрерывная интеграция)

Разработчики «сливают» свой код в общий репозиторий, каждый коммит автоматически запускает сборку и тесты. Если что-то ломается, команда узнает об этом в течение минут.

### CD: Continuous Delivery/Deployment (Непрерывная доставка/развертывание)

Это подход, автоматизирующий процесс вывода кода в продакшен. В Continuous Delivery код после прохождения автоматических проверок в CI готов к развертыванию, но требует ручного подтверждения (например, нажатия кнопки). В Continuous Deployment новая версия кода автоматически разворачивается на сервере без дополнительных действий.

### Сборка, развёртывание, выпуск

Эти три слова часто смешивают, хотя они означают разные шаги:

- **сборка (build)** — из кода получается артефакт: Docker-образ, wheel, архив. Один и тот же артефакт потом едет на все окружения, его не пересобирают под каждое;
- **развёртывание (deploy)** — артефакт запущен в окружении: тестовом, предпродовом, продакшене;
- **выпуск (release)** — новую функциональность видят пользователи. Выпуск можно отделить от развёртывания: код уже в продакшене, но спрятан за флагом (feature flag) или включён для 5% пользователей (канареечный выпуск). Тогда откат — это выключить флаг, а не срочно развёртывать старую версию.

### Как часто выпускаться

- **Ветка на задачу и частые слияния в основную** (trunk-based): ветки живут часы или дни, основная ветка всегда готова к выпуску, недоделанное прячут за флагами. Подходит для CI/CD в полном смысле.
- **Git Flow**: отдельные ветки `develop`, `release/*`, `hotfix/*`. Удобен, когда версии выпускают редко и поддерживают несколько сразу (библиотеки, коробочные продукты). Для веб-сервиса обычно тяжеловат.
- **Релизные поезда**: выпуск по расписанию (например, раз в неделю), в поезд попадает всё, что успело пройти проверки. Это компромисс для больших команд и мобильных приложений, где каждый выпуск проходит проверку в магазине приложений.

Чем реже выпуск, тем больше изменений в нём, тем сложнее найти причину поломки и тем страшнее выпускаться. Поэтому стремятся к маленьким и частым выпускам.

### Секреты в CI

- Секреты хранят в хранилище CI (GitHub Secrets, GitLab CI/CD Variables) или во внешнем хранилище (Vault, облачный Secret Manager), но не в репозитории и не в Dockerfile: слой образа хранит файл, даже если следующей инструкцией его удалили.
- Секрет передают в шаг через переменную окружения, и только тем шагам, которым он нужен. CI маскирует известные ему секреты в логах, но не их производные: base64 от секрета в лог попадёт.
- Для каждого окружения свои секреты, а у ключей — минимальные права. Ключ деплоя может только деплоить.
- Если секрет попал в историю git, удалить коммит недостаточно: секрет считается раскрытым, его нужно перевыпустить.

## Частые ошибки

- Пересборка артефакта под каждое окружение → в продакшен уходит не тот образ, что проверяли на тестовом стенде → собирать один раз, помечать версией и продвигать тот же образ между окружениями.
- Конвейер зелёный только потому, что тесты не запускаются → `pytest` не находит тестов или шаг с ошибкой не роняет сборку → проверять, что при сломанном тесте проверка краснеет, и не ставить `continue-on-error` на тесты.
- Секрет в репозитории или в аргументе `docker build` → он виден в истории git и в слоях образа → хранить в секретах CI, передавать через переменные окружения и перевыпустить уже раскрытый.
- Редкие большие выпуски → поломку ищут среди сотни изменений, откат страшен → сливать маленькими порциями, прятать недоделанное за флагами.
- Деплой с ноутбука «в обход», потому что конвейер долгий → никто не знает, какая версия в продакшене → ускорять конвейер (кэш зависимостей, параллельные шаги), а не обходить его.

## Когда не использовать

Для личного скрипта или прототипа на один вечер конвейер — лишняя настройка: достаточно запускать тесты руками перед коммитом (например, через pre-commit). Полный Continuous Deployment не подходит там, где каждый выпуск требует согласования или проходит внешнюю проверку — мобильные приложения в магазинах, системы с регуляторными требованиями; там остаются на Continuous Delivery с ручным подтверждением выпуска.

Не стоит и переносить в конвейер всё подряд: долгие нагрузочные тесты или проверка на десяти версиях Python на каждый push растянут обратную связь до часа. Их запускают по расписанию или перед выпуском, а на каждый push оставляют быстрые проверки.
