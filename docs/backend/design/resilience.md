# Устойчивость: таймауты, повторы, идемпотентность, circuit breaker

В распределённой системе что-то всегда ломается: сосед отвечает 30 секунд, сеть теряет пакет, платёжный сервис отвечает 503. Хуже всего, когда сбой одного маленького сервиса роняет всю систему. Сервис рекомендаций завис, а вместе с ним зависли все запросы главной страницы. Несколько простых приёмов локализуют сбой: система работает хуже, но продолжает работать.

## Минимальный пример: circuit breaker

Сервис рекомендаций лежит, и каждый запрос к нему ждёт таймаута 0,2 секунды. **Автоматический выключатель** (circuit breaker) после трёх ошибок подряд перестаёт ходить в сервис и сразу возвращает ошибку:

```python
class CircuitBreaker:
    def __init__(self, failure_threshold: int = 3, reset_timeout: float = 1.0):
        self.failure_threshold = failure_threshold
        self.reset_timeout = reset_timeout
        self.failures = 0
        self.opened_at: float | None = None

    @property
    def state(self) -> str:
        if self.opened_at is None:
            return 'closed'
        if time.monotonic() - self.opened_at >= self.reset_timeout:
            return 'half-open'
        return 'open'

    def call(self, func, *args):
        if self.state == 'open':
            raise CircuitOpenError('сервис временно отключён')
        try:
            result = func(*args)
        except Exception:
            self.failures += 1
            if self.state == 'half-open' or self.failures >= self.failure_threshold:
                self.opened_at = time.monotonic()
            raise
        self.failures = 0
        self.opened_at = None
        return result
```

```text
запрос 1: TimeoutError за 0.21 с, состояние closed
запрос 2: TimeoutError за 0.20 с, состояние closed
запрос 3: TimeoutError за 0.21 с, состояние open
запрос 4: CircuitOpenError за 0.00 с, состояние open
запрос 5: CircuitOpenError за 0.00 с, состояние open
запрос 6: CircuitOpenError за 0.00 с, состояние open
реальных вызовов сервиса: 3

через секунду: half-open
['Сдать отчёт'] closed     — пробный запрос прошёл, выключатель снова замкнут
```

## Как работает выключатель

Три состояния, как у электрического автомата:

- **closed** (замкнут) — запросы идут как обычно, ошибки считаются;
- **open** (разомкнут) — после порога ошибок запросы сразу отклоняются, не дожидаясь таймаута. Упавший сервис получает передышку, а наш сервис не тратит потоки и соединения на ожидание;
- **half-open** (полуоткрыт) — через какое-то время пропускается пробный запрос. Удался — выключатель замыкается, упал — снова размыкается.

Вместо ошибки пользователю часто отдают **запасной вариант** (fallback): нет персональных рекомендаций — покажем популярные задачи, нет сервиса аватаров — покажем инициалы.

Готовые реализации: `pybreaker`, `aiobreaker`, а в инфраструктуре — Envoy и Istio.

## Таймауты

Без таймаута один зависший сосед держит соединение, поток и память бесконечно, и скоро их перестаёт хватать на другие запросы. Таймаут нужен **у каждого** сетевого вызова: HTTP, база, Redis, брокер. Как задать таймауты в HTTPX — в заметке про [HTTPX](../microservices/httpx/basics.md#таймауты).

Таймаут должен быть меньше, чем готов ждать ваш собственный клиент. Если фронтенд ждёт ответа 5 секунд, а вы ждёте соседа 30, пользователь уже ушёл, а ваш сервис всё ещё тратит на него ресурсы.

## Повторы с паузой и разбросом

Временные ошибки (сеть, 503, таймаут) часто проходят со второй попытки. Но повторять нужно аккуратно:

- **нарастающая пауза** (exponential backoff): 0,2 → 0,4 → 0,8 → 1,6 секунды. Упавший сервис не получает стену повторных запросов;
- **случайный разброс** (jitter): если тысяча клиентов упала одновременно, без разброса они и повторят одновременно. Удобный вариант — «полный разброс», случайная пауза от нуля до текущего предела:

```python
def backoff_delays(attempts: int, base: float = 0.2, cap: float = 5.0) -> list[float]:
    return [random.uniform(0, min(cap, base * 2 ** attempt)) for attempt in range(attempts)]


backoff_delays(5)  # [0.03, 0.34, 0.61, 0.41, 1.59]
```

- **ограниченное число попыток** — и затем ошибка или запасной вариант.

Повторы и выключатель работают вместе: повторы справляются с короткими сбоями, выключатель — с долгими.

## Идемпотентность

Повторять можно только то, что безопасно выполнить дважды. Клиент отправил «оплатить 300 ₽», ответ не дошёл из-за таймаута. Платёж прошёл или нет? Если просто повторить, можно списать деньги дважды.

Решение — **ключ идемпотентности**. Клиент генерирует уникальный ключ для операции и передаёт его с каждым повтором (часто в заголовке `Idempotency-Key`). Сервер запоминает результат по ключу и на повтор возвращает сохранённый ответ:

```python
payments: dict[str, dict] = {}  # в реальном сервисе — таблица с уникальным индексом по ключу


def pay(idempotency_key: str, user: str, amount: int) -> dict:
    if idempotency_key in payments:
        return payments[idempotency_key]
    balance[user] -= amount
    result = {'payment_id': new_id(), 'amount': amount, 'balance': balance[user]}
    payments[idempotency_key] = result
    return result


key = str(uuid.uuid4())
pay(key, 'anna', 300)  # {'payment_id': '2a1bde38', 'amount': 300, 'balance': 700}
pay(key, 'anna', 300)  # {'payment_id': '2a1bde38', 'amount': 300, 'balance': 700} — тот же ответ
balance                # {'anna': 700} — списано один раз
```

Так работают платёжные API (Stripe, ЮKassa). В реальном сервисе проверку и запись делают одной транзакцией с уникальным индексом по ключу: иначе два одновременных повтора оба пройдут проверку.

## Перегородки (bulkhead)

Название — от водонепроницаемых отсеков корабля: пробоина в одном не топит весь корабль. Для вызовов разных соседей выделяют **отдельные пулы** соединений и потоков. Если сервис рекомендаций завис и занял все свои 10 соединений, запросы к платёжному сервису всё равно идут через его собственный пул.

## Частые ошибки

- **Повторы на каждом уровне.** Фронтенд повторяет 3 раза, шлюз 3 раза, сервис 3 раза — и упавший сервис получает 27 запросов вместо одного. Повторяют в одном месте, обычно ближе всего к вызову.
- **Повтор неидемпотентной операции.** `POST /orders` без ключа идемпотентности создаёт дубли.
- **Повтор ошибок клиента.** Ответ 400 или 404 не изменится от повтора. Повторяют только временные ошибки: таймауты, 429, 502, 503, 504.
- **Выключатель без мониторинга.** Если выключатель разомкнулся, об этом должна узнать команда: это [метрика и алерт](../../infrastructure/monitoring/prometheus/README.md), а не строчка в логе.
- **Таймаут больше, чем готов ждать клиент.** Работа продолжается, когда результат уже никому не нужен.
