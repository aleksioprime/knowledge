# Архитектура приложения: слои, луковица, порты и адаптеры, события

Пока сервис маленький, неважно, где лежит код: обработчик запроса сам лезет в базу, сам считает и сам отправляет письмо. Когда кода становится много, без договорённости «что от чего зависит» каждое изменение задевает всё подряд. Нельзя протестировать логику без настоящей базы, а переезд с одной базы на другую превращается в переписывание половины проекта. Архитектурный паттерн — такая договорённость. Ниже четыре самых распространённых паттерна на одном примере: отметить задачу выполненной и уведомить владельца.

## Минимальный пример

Порты и адаптеры (гексагональная архитектура) в одном файле. Ядро описывает, *что* ему нужно от внешнего мира, а внешний мир подключается снаружи:

```python
from dataclasses import dataclass, field
from typing import Protocol


# Ядро: доменная модель и порты. Ничего не знает о базе, HTTP и фреймворках
@dataclass
class Task:
    id: int
    title: str
    done: bool = False

    def complete(self) -> None:
        if self.done:
            raise ValueError('Задача уже выполнена')
        self.done = True


class TaskRepository(Protocol):  # порт: что ядру нужно от хранилища
    def get(self, task_id: int) -> Task: ...
    def save(self, task: Task) -> None: ...


class Notifier(Protocol):  # порт: как ядро сообщает о событиях
    def send(self, text: str) -> None: ...


class CompleteTask:  # сценарий использования (use case)
    def __init__(self, tasks: TaskRepository, notifier: Notifier):
        self.tasks = tasks
        self.notifier = notifier

    def __call__(self, task_id: int) -> Task:
        task = self.tasks.get(task_id)
        task.complete()
        self.tasks.save(task)
        self.notifier.send(f'Выполнена: {task.title}')
        return task


# Адаптеры: конкретные реализации портов. Их можно менять, не трогая ядро
@dataclass
class InMemoryTasks:
    rows: dict[int, Task] = field(default_factory=dict)

    def get(self, task_id: int) -> Task:
        return self.rows[task_id]

    def save(self, task: Task) -> None:
        self.rows[task.id] = task


class ConsoleNotifier:
    def send(self, text: str) -> None:
        print('→', text)


tasks = InMemoryTasks({1: Task(1, 'Сдать отчёт')})
complete_task = CompleteTask(tasks, ConsoleNotifier())
print(complete_task(1))
# → Выполнена: Сдать отчёт
# Task(id=1, title='Сдать отчёт', done=True)
```

В рабочем коде вместо `InMemoryTasks` подключается адаптер к PostgreSQL, вместо `ConsoleNotifier` — отправка письма. Класс `CompleteTask` при этом не меняется, а в тестах остаются адаптеры в памяти: тест не требует ни базы, ни почтового сервера.

## Слоистая архитектура

Приложение режется на горизонтальные слои, и каждый обращается только к слою под собой:

```text
представление   (HTTP-обработчики, шаблоны, сериализаторы)
      ↓
бизнес-логика   (сервисы: «отметить задачу выполненной»)
      ↓
доступ к данным (репозитории, ORM)
      ↓
база данных
```

Это самый понятный паттерн, и большинство фреймворков подталкивают именно к нему. В Django это шаблоны и view, модели с ORM и база.

**Плюсы:** просто объяснить и начать. Понятно, куда класть новый код.

**Минусы:** зависимости направлены вниз, к базе. Бизнес-логика импортирует ORM и без базы не работает, её трудно тестировать и трудно перенести. Каждый запрос проходит через все слои, даже если слой ничего не добавляет. Прыгать через слой, например из view сразу в базу, запрещено правилами паттерна, но на практике так делают постоянно, и слои размываются.

## Луковичная архитектура

Луковичная архитектура (onion) переворачивает главное правило: в центре не база, а **доменная модель** — сущности и правила предметной области. Вокруг неё лежат сценарии использования, а снаружи — база, веб и внешние сервисы:

```text
┌──────────────────────────────────────────┐
│  инфраструктура: БД, HTTP, очереди, почта │
│   ┌──────────────────────────────────┐   │
│   │  сценарии: CompleteTask          │   │
│   │   ┌──────────────────────────┐   │   │
│   │   │  домен: Task.complete()  │   │   │
│   │   └──────────────────────────┘   │   │
│   └──────────────────────────────────┘   │
└──────────────────────────────────────────┘
        зависимости направлены только внутрь
```

Внутренние круги ничего не знают о внешних. Если сценарию нужно сохранить задачу, он объявляет интерфейс `TaskRepository`, а реализует его внешний слой. Это **инверсия зависимостей**, буква D из [SOLID](principles.md). Разработка тоже начинается изнутри: сначала сущности и правила, потом способ показать их наружу.

**Плюсы:** ядро не зависит от базы и фреймворка, его легко тестировать и переносить. Смену базы или переход с REST на gRPC ядро не замечает.

**Минусы:** больше кода и абстракций. Для CRUD-сервиса без сложных правил это лишняя церемония.

Близкие названия той же идеи — «чистая архитектура» (Clean Architecture) и подход DDD (Domain-Driven Design, проектирование от предметной области).

## Гексагональная архитектура (порты и адаптеры)

Та же идея, но описанная через границу приложения, а не через слои. У ядра есть **порты** — интерфейсы, через которые оно общается с миром. **Адаптеры** подключают к портам конкретные технологии:

- **входящие** (driving) адаптеры вызывают ядро: HTTP-обработчик, консольная команда, обработчик сообщения из очереди, тест;
- **исходящие** (driven) адаптеры вызываются ядром: репозиторий PostgreSQL, клиент почты, клиент внешнего API.

Шестиугольник на схемах ничего не означает. Это просто фигура с несколькими сторонами, к которым удобно рисовать адаптеры. В минимальном примере `TaskRepository` и `Notifier` — порты, `InMemoryTasks` и `ConsoleNotifier` — адаптеры, а вызов `complete_task(1)` выполняет роль входящего адаптера.

**Плюсы:** компоненты не зависят друг от друга, адаптеры легко заменить или подделать в тестах. Удобно, когда разные части разрабатывают разные команды.

**Минусы:** на каждый внешний сервис приходится заводить порт и адаптер. Лишний слой абстракции стоит времени на чтение кода.

## Событийно-ориентированная архитектура

Здесь в центре не сущности, а **события**: «задача выполнена», «пользователь зарегистрировался». Тот, кто публикует событие, не знает, кто на него реагирует. На каждый тип события подписаны свои обработчики:

```python
from collections import defaultdict
from dataclasses import dataclass


@dataclass
class TaskCompleted:
    task_id: int
    title: str


handlers = defaultdict(list)


def subscribe(event_type):
    def decorator(func):
        handlers[event_type].append(func)
        return func
    return decorator


def publish(event) -> None:
    for handler in handlers[type(event)]:
        handler(event)


@subscribe(TaskCompleted)
def notify_owner(event: TaskCompleted) -> None:
    print(f'Письмо: задача «{event.title}» выполнена')


@subscribe(TaskCompleted)
def update_stats(event: TaskCompleted) -> None:
    print(f'Статистика: +1 выполненная задача ({event.task_id})')


publish(TaskCompleted(task_id=1, title='Сдать отчёт'))
# Письмо: задача «Сдать отчёт» выполнена
# Статистика: +1 выполненная задача (1)
```

Это шина событий внутри одного процесса, по той же схеме работают сигналы Django. Между сервисами вместо словаря обработчиков стоит брокер сообщений ([Kafka](../../microservices/broker/kafka/README.md), [RabbitMQ](../../microservices/broker/rabbitmq/README.md)), и обработчики живут в разных процессах.

**Плюсы:** новая реакция на событие добавляется без правки того, кто его публикует. Обработчики масштабируются независимо. Подходит для систем с большим потоком событий: стриминг, аналитика, уведомления.

**Минусы:** поток выполнения не виден в коде, отлаживать трудно. Обработка асинхронная, поэтому данные согласуются не сразу, а сообщения могут прийти повторно или не по порядку (см. [распределённые транзакции](transactions.md)).

## Как выбрать

| Ситуация | Что подходит |
|---|---|
| CRUD-сервис, мало бизнес-правил, нужно быстро | слоистая, как предлагает фреймворк |
| сложная предметная область, правила важнее хранилища, долгая жизнь проекта | луковичная / чистая |
| много внешних интеграций, нужно подменять их в тестах, несколько команд | порты и адаптеры |
| много независимых реакций на одно действие, поток событий, слабая связь между сервисами | событийная |

Паттерны совмещаются. Типичный сервис на FastAPI устроен так: роутеры (входящие адаптеры) → сервисы (сценарии) → репозитории за интерфейсами (исходящие адаптеры), а наружу он публикует события в брокер.

## Частые ошибки

- **Абстракции ради абстракций.** Интерфейс с единственной реализацией и без тестов, которым нужна подмена, только добавляет прыжок по коду. Начинайте проще и выделяйте порт, когда появилась вторая реализация или тест.
- **Модель ORM вместо доменной модели.** Если «ядро» принимает и возвращает модели Django или SQLAlchemy, оно всё равно зависит от базы. Луковица на словах, слои на деле.
- **Бизнес-логика в обработчиках запросов.** Правило «задачу нельзя выполнить дважды» живёт во view, и консольная команда или обработчик из очереди его обходят. Правила должны жить в домене или в сценарии.
- **События вместо явных вызовов там, где нужен результат.** Если без ответа обработчика нельзя продолжить, это обычный вызов функции, а не событие.
