# ETL из PostgreSQL в Elasticsearch

Данные живут в PostgreSQL, а искать по ним нужно в Elasticsearch. Пользователь поправил задачу или переименовал метку, и через несколько секунд это должно появиться в поиске. Перекачивать всю базу целиком нельзя: большой запрос мешает остальной работе PostgreSQL, Elasticsearch плохо принимает огромные пачки, а процесс съест всю память. Нужен процесс, который забирает только изменения, небольшими пачками, переживает падение любой из баз и продолжает с того места, где остановился. Такой процесс называют **ETL** (Extract — Transform — Load).

Рабочий пример целиком лежит в [examples/etl](../examples/etl/README.md): PostgreSQL и Elasticsearch в Docker, схема с тестовыми данными и скрипт `etl.py`. Ниже — его главные части.

## Минимальный пример

Ядро ETL — цикл «прочитать пачку изменений → дособрать данные → загрузить → запомнить, где остановились»:

```python
cursor = state.get_state('task', START)          # где остановились в прошлый раз
rows = conn.execute("""
    SELECT id, modified FROM content.task
    WHERE (modified, id) > (%(modified)s, %(id)s)
    ORDER BY modified, id
    LIMIT 100
""", cursor).fetchall()

docs = [transform(row) for row in conn.execute(ENRICH, ([r['id'] for r in rows],))]
helpers.bulk(es, docs)                            # одна пачка — один HTTP-запрос

last = rows[-1]
state.set_state('task', {'modified': last['modified'].isoformat(), 'id': str(last['id'])})
```

```text
INFO Загружено документов: 100
INFO Загружено документов: 100
...
```

Повторный запуск без изменений в базе ничего не загружает: курсор уже стоит на последней записи.

## Как это работает

Процесс делится на три шага, и у каждого своя ответственность:

- **Extract** читает из PostgreSQL пачками, начиная с последней обработанной записи, и спокойно переживает падение базы;
- **Transform** превращает строки из нескольких таблиц в один JSON-документ;
- **Load** загружает документы пачками, задаёт `_id` и переживает падение Elasticsearch.

### Что считать изменением

Приложение при каждом изменении записи обновляет поле `modified`. ETL выбирает записи, у которых `modified` больше сохранённого. Без индекса по этому полю каждая пачка превращается в полный проход по таблице.

Курсором служит **пара `(modified, id)`**, а не одно время. Если пачка закончилась на записи с `modified = 12:00:00`, а у следующей записи то же время, условие `modified > '12:00:00'` её пропустит. Сравнение пар `(modified, id) > (...)` такого не допускает: это та же [keyset-пагинация](../../postgres/docs/tasks.md).

### Нормализованная база → денормализованный индекс

В PostgreSQL задача, метки и связь между ними лежат в трёх таблицах. В Elasticsearch нужен один документ на задачу, в котором уже есть названия меток. Поэтому изменения в разных таблицах влияют по-разному:

| Что изменилось | Какие документы обновить |
|---|---|
| задача | только эту задачу |
| метка (например, переименовали) | все задачи с этой меткой — их могут быть тысячи, поэтому тоже пачками |
| связь задача–метка | эту задачу; проще всего, если приложение заодно обновляет `task.modified` |

В примере для каждой таблицы-источника хранится свой курсор. Изменённые метки превращаются в список задач, и дальше путь общий: дособрать данные и загрузить.

### Как собрать документ

Есть три подхода:

1. **Один большой запрос** с агрегацией. Мало кода на Python, но сложный SQL, который надо оптимизировать.
2. **Несколько простых запросов**: изменённые id, затронутые задачи, полные данные. Запросы легко читать и отлаживать, нагрузка на базу дробится, но кода больше.
3. **Перечитывать всё по кругу** без учёта изменений. Очень просто, но свежие правки доходят с задержкой, которая растёт с объёмом данных. Хорошо работает как подстраховка поверх первых двух: раз в сутки догоняет то, что могло потеряться.

В примере используется второй подход, а данные задачи дособираются одним запросом с `array_agg`:

```sql
SELECT
    t.id, t.title, t.description, t.done, t.owner, t.modified,
    COALESCE(array_agg(g.name ORDER BY g.name) FILTER (WHERE g.id IS NOT NULL), '{}') AS tags
FROM content.task AS t
LEFT JOIN content.task_tag AS tt ON tt.task_id = t.id
LEFT JOIN content.tag AS g ON g.id = tt.tag_id
WHERE t.id = ANY(%s)
GROUP BY t.id
```

`FILTER (WHERE g.id IS NOT NULL)` убирает `NULL` у задач без меток, а `COALESCE` превращает пустой результат в пустой массив. Если нужен список объектов, а не строк, используют `json_agg(jsonb_build_object('id', g.id, 'name', g.name))`.

### Состояние

Курсоры нужно хранить вне памяти процесса, иначе после перезапуска ETL начнёт с нуля. Хватает словаря «источник → курсор» в JSON-файле. Также подойдут Redis или таблица в той же базе.

```python
class JsonFileStorage:
    def retrieve_state(self) -> dict:
        if not self.path.exists():
            return {}
        return json.loads(self.path.read_text())

    def save_state(self, state: dict) -> None:
        tmp = self.path.with_suffix('.tmp')
        tmp.write_text(json.dumps(state, ensure_ascii=False))
        tmp.replace(self.path)  # атомарная замена: при падении не останется полузаписанного файла
```

Главное правило: **сначала загрузить, потом сохранить курсор**. Если ETL упадёт между этими шагами, пачка загрузится повторно. Это безопасно, потому что документ с тем же `_id` просто перезапишется. Обратный порядок теряет данные.

### Повторы при падении баз

ETL постоянно ходит в обе базы. Если одна из них упала, процесс не должен падать вместе с ней. Он должен ждать и повторять, но не заваливать восстанавливающуюся базу запросами. Для этого пауза между попытками растёт экспоненциально до предела, а к ней добавляется случайный разброс (jitter), чтобы несколько процессов не стучались одновременно:

```python
def backoff(exceptions, start_sleep=0.1, factor=2, border_sleep=10):
    def decorator(func):
        @wraps(func)
        def wrapper(*args, **kwargs):
            attempt = 0
            while True:
                try:
                    return func(*args, **kwargs)
                except exceptions as error:
                    delay = random.uniform(0, min(border_sleep, start_sleep * factor ** attempt))
                    logger.warning('%s: %r, повтор через %.1f с', func.__name__, error, delay)
                    time.sleep(delay)
                    attempt += 1
        return wrapper
    return decorator


@backoff((psycopg.OperationalError, ESConnectionError))
def run_once(state): ...
```

Так выглядит лог, если остановить PostgreSQL посреди работы и через несколько секунд запустить снова:

```text
WARNING run_once: OperationalError('connection failed: ... Connection refused'), повтор через 0.0 с
WARNING run_once: OperationalError('connection failed: ...'), повтор через 0.3 с
WARNING run_once: OperationalError('connection failed: ...'), повтор через 2.2 с
WARNING run_once: OperationalError('connection failed: ...'), повтор через 4.2 с
INFO Загружено документов: 1
```

Декоратор висит на всём проходе, а не на отдельном запросе. После ошибки соединение открывается заново, и обработка продолжается с сохранённого курсора.

Повторять стоит не всё:

- **серверные и сетевые ошибки** (`ConnectionError`, таймаут соединения, HTTP 502/503) — повторять: база может вернуться;
- **ошибки в самом запросе или данных** (синтаксис SQL, неверный маппинг, HTTP 400/405) — не повторять: лучше не станет. Процессу вроде ETL нужно записать ошибку в лог и остановиться либо пропустить документ.

Поэтому декоратор принимает список исключений. Так же устроена библиотека [backoff](https://pypi.org/project/backoff/). Подробнее о повторах и разбросе — в [заметке про устойчивость](../../../design/docs/resilience.md).

**Таймауты** задаются для каждого обращения: `connect_timeout` в psycopg, `request_timeout` в клиенте Elasticsearch. Без них зависший запрос ждёт вечно, и никакой повтор не наступит. Значение подбирают по обычному времени ответа (смотрят на перцентили, а не на среднее) и по тому, сколько процесс готов ждать.

### Загрузка пачками: bulk

Загружать по одному документу медленно: на каждый уходит отдельный HTTP-запрос. В Elasticsearch для этого есть `_bulk`: тело запроса в формате NDJSON, где строка-команда чередуется со строкой-документом, а в конце обязателен перевод строки:

```bash
curl -XPOST localhost:9200/_bulk -H 'Content-Type: application/x-ndjson' --data-binary $'
{"index": {"_index": "tasks", "_id": "1"}}
{"title": "Купить хлеб"}
{"index": {"_index": "tasks", "_id": "2"}}
{"title": "Подготовить отчёт"}
'
```

Ответ содержит `"errors": true/false` и результат по каждому документу. Параметр `?filter_path=items.*.error` оставит в ответе только ошибки. В Python то же самое делает `helpers.bulk`:

```python
ok, errors = helpers.bulk(es, docs, raise_on_error=False)
for error in errors:
    logger.error('Документ не загружен: %s', error)
```

`_id` берём из первичного ключа в PostgreSQL. Тогда повторная загрузка обновляет документ, а не создаёт дубль. Размер пачки выносим в настройку: сотни или тысячи документов, но не десятки тысяч.

### Два процесса одновременно

Если ETL запускается по cron, а проход не успел закончиться к следующему запуску, два процесса будут грузить одно и то же и спорить за файл состояния. Простая защита — [advisory lock](https://postgrespro.ru/docs/postgresql/16/explicit-locking#ADVISORY-LOCKS) в PostgreSQL. Блокировку берёт только один процесс, а при закрытии соединения она снимается сама:

```python
if not conn.execute('SELECT pg_try_advisory_lock(42) AS ok').fetchone()['ok']:
    logger.warning('ETL уже запущен в другом процессе')
    return
```

### Мониторинг

Фоновый процесс может месяцами работать молча, а потом так же молча перестать загружать данные. Минимум, за которым нужно следить: число проходов, число загруженных документов, время последней успешной загрузки. Алерт ставят на «за последний час не загружено ничего, хотя изменения в базе были». Метрики удобно отдавать в [Prometheus](../../../analyze/prometheus/README.md).

## Частые ошибки

- **Курсор только по времени.** Записи с одинаковым `modified` на границе пачки теряются. Используйте пару `(modified, id)`.
- **Курсор сохраняется до загрузки.** При падении между шагами пачка потеряется навсегда. Сначала `bulk`, потом `set_state`.
- **Приложение не обновляет `modified`.** ETL не увидит изменение. Особенно часто это забывают при массовых `UPDATE` и при изменении связей «многие ко многим».
- **Учтены только изменения задач.** После переименования метки в индексе остаются старые названия. Для каждой таблицы, данные которой попадают в документ, нужен свой источник изменений.
- **`fetchall()` по всей таблице** при первом запуске съедает память. Всегда используйте `LIMIT` и курсор.
- **Повторы без предела и без разброса.** Восстановившуюся базу тут же кладёт волна одинаковых запросов.
- **Повтор при ошибке в данных.** Неверный маппинг повторяется бесконечно, а остальные данные стоят в очереди.
- **Нет удалений.** Пример ловит только изменения. Удалённая задача останется в индексе, пока ETL не узнает об удалении: нужен признак `deleted` (мягкое удаление) или отдельный журнал удалений.

## Когда не использовать

- **Данных немного, и задержка не важна.** Ночная полная перезаливка в новый индекс с переключением алиаса проще и надёжнее.
- **Изменений очень много или нужна задержка в доли секунды.** Опрос по `modified` нагружает базу и всё равно отстаёт. Тогда читают журнал изменений самой базы (CDC, Change Data Capture): Debezium читает WAL PostgreSQL и пишет события в Kafka, оттуда их забирает коннектор Elasticsearch. Триггеры, которые пишут изменения в отдельную таблицу, — промежуточный вариант, но их тяжело отлаживать и сопровождать.
- **Много разных пайплайнов по расписанию.** Логику загрузки оставляют своей, а запуск, повторы и историю отдаёт оркестратору вроде [Airflow](../../airflow/README.md).
