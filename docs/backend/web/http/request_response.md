# Структура HTTP-запроса и ответа

Чтобы читать логи и вывод `curl -v`, понимать, почему API вернул `422` или `502`, и правильно выбирать метод и код ответа для своего эндпоинта, нужно знать, из чего состоит HTTP-сообщение. Здесь — стартовая строка, заголовки и тело, таблица методов, группы кодов и части URL.

## Минимальный пример

```python run
from email.parser import Parser
from http import HTTPStatus

raw = (
    'POST /api/tasks?notify=true HTTP/1.1\r\n'
    'Host: example.com\r\n'
    'Content-Type: application/json\r\n'
    'Content-Length: 33\r\n'
    '\r\n'
    '{"title":"Купить хлеб"}'
)
start_line, rest = raw.split('\r\n', 1)
method, target, version = start_line.split(' ')
message = Parser().parsestr(rest)
print(method, target, version)              # POST /api/tasks?notify=true HTTP/1.1
print(message['content-type'])              # application/json
print(len(message.get_payload().encode()))  # 33 — совпадает с Content-Length
print(HTTPStatus(404).phrase)               # Not Found
```

## Как это работает

### Запрос

HTTP/1.1-запрос состоит из стартовой строки, заголовков, пустой строки и необязательного тела:

```http
POST /api/users?notify=true HTTP/1.1
Host: example.com
Content-Type: application/json
Authorization: Bearer <token>
Content-Length: 25

{"name":"Alex","age":30}
```

Стартовая строка содержит:

- метод — какое действие запрашивается;
- target — путь и query-параметры;
- версию протокола.

Основные методы:

| Метод | Назначение | Идемпотентный |
|---|---|---|
| `GET` | Получить ресурс | Да |
| `HEAD` | Получить только заголовки | Да |
| `POST` | Создать ресурс или запустить операцию | Обычно нет |
| `PUT` | Полностью заменить ресурс | Да |
| `PATCH` | Частично изменить ресурс | Не обязательно |
| `DELETE` | Удалить ресурс | Да |
| `OPTIONS` | Узнать доступные возможности | Да |

Идемпотентность означает, что повтор одного и того же запроса должен приводить к тому же состоянию сервера. Это важно для безопасных повторов после сетевых ошибок.

### Ответ

```http
HTTP/1.1 201 Created
Content-Type: application/json
Location: /api/users/42
Content-Length: 23

{"id":42,"name":"Alex"}
```

Ответ содержит строку статуса, заголовки и необязательное тело. Группы кодов:

- `1xx` — промежуточная информация;
- `2xx` — успешная обработка;
- `3xx` — перенаправление или использование кеша;
- `4xx` — ошибка запроса клиента;
- `5xx` — ошибка сервера или прокси.

Частые коды: `200 OK`, `201 Created`, `204 No Content`, `301/308` для постоянного перенаправления, `304 Not Modified`, `400 Bad Request`, `401 Unauthorized`, `403 Forbidden`, `404 Not Found`, `409 Conflict`, `422 Unprocessable Content`, `429 Too Many Requests`, `500 Internal Server Error`, `502 Bad Gateway`, `503 Service Unavailable`, `504 Gateway Timeout`.

### URL

```text
https://user@example.com:443/products/42?color=black#reviews
└─scheme─┘     └─host────┘port└──path────┘└─query────┘└fragment┘
```

Фрагмент после `#` обрабатывает браузер: в обычный HTTP-запрос он не отправляется. Секреты не следует помещать в URL, потому что URL попадают в историю, логи и заголовок `Referer`.

## Частые ошибки

- `Content-Length` посчитан в символах, а не в байтах → для кириллицы сервер ждёт недостающие байты и обрывает запрос по таймауту либо читает лишние байты как начало следующего запроса → считать длину после кодирования в UTF-8 или доверить заголовок HTTP-библиотеке.
- Данные передают в теле `GET` → прокси и кеши тело отбрасывают, сервер его не читает → параметры в строке запроса, данные для изменения — в `POST`/`PUT`/`PATCH`.
- Сервер ждёт фрагмент `#reviews` → в логах и маршрутах его нет, нужная вкладка не открывается → фрагмент живёт только в браузере; то, что нужно серверу, передавать в пути или query.
- Токен в URL (`?token=...`) → утекает в историю браузера, логи NGINX и `Referer` → передавать в заголовке `Authorization` или в cookie.
- Ответ `200` с ошибкой в теле (`{"error": "not found"}`) → клиентская библиотека не выбросит исключение, кеш сохранит ответ, мониторинг не увидит ошибку → ошибка меняет код: `404`, `422`, `500`.

## Когда не использовать

Разбирать и собирать HTTP-сообщения руками, как в примере, в рабочем коде не нужно: сервер (FastAPI, Django) и клиент (HTTPX, `requests`) делают это сами, заодно обрабатывая chunked-кодирование, сжатие и HTTP/2, где текстовой стартовой строки нет вообще. Ручной разбор — для учёбы, отладки и тестов.

Если серверу нужно самому присылать события клиенту (чат, прогресс задачи), модель «запрос — ответ» неудобна: берите WebSocket или SSE, разобранные в заметке про [реальное время в FastAPI](../../frameworks/fastapi/realtime.md).
