# Кэширование

Самый быстрый запрос к базе — тот, которого не было. Если тяжёлый отчёт строится полсекунды и его открывают тысячу раз в минуту, проще посчитать его один раз и раздавать готовый результат. Кэш — это копия данных в более быстром месте. Ускорение бывает огромным, но у любой копии есть главная проблема: она может устареть.

## Минимальный пример

Тот же отчёт, который строится полсекунды. Сто запросов приходят одновременно, а кэш пуст — например, сразу после истечения срока жизни:

```python
cache: dict[str, str] = {}


def get_report_naive() -> str:
    if 'report' not in cache:
        cache['report'] = load_report_from_db()
    return cache['report']

# 100 одновременных запросов → запросов к базе — 100
```

Все сто увидели пустой кэш и пошли в базу одновременно. Это **cache stampede** (лавина промахов): база получает удар именно тогда, когда кэш должен был её защищать. Решение — пускать к базе только один запрос, а остальным дождаться результата:

```python
lock = threading.Lock()


def get_report_with_lock() -> str:
    if 'report' in cache:
        return cache['report']
    with lock:
        # Пока ждали блокировку, другой поток мог уже заполнить кэш
        if 'report' not in cache:
            cache['report'] = load_report_from_db()
    return cache['report']

# 100 одновременных запросов → запросов к базе — 1
```

Между несколькими серверами вместо `threading.Lock` используют [распределённую блокировку в Redis](../databases/redis/scenarios.md#4-распределённая-блокировка).

## Где живут кэши

От клиента к базе:

- **браузер** — заголовки `Cache-Control`, `ETag` ([HTTP-кэширование](../web/http/headers_cookies_cache.md));
- **CDN** — копии статики и публичных страниц на серверах рядом с пользователями;
- **обратный прокси** — NGINX может кэшировать ответы API;
- **приложение** — словарь или `functools.lru_cache` в памяти процесса. Самый быстрый, но у каждой копии свой, и он пропадает при перезапуске;
- **общий кэш** — [Redis](../databases/redis/README.md): один на все копии приложения;
- **сама база** — кэширует горячие страницы данных в памяти.

## Стратегии

**Cache-aside** (ленивое заполнение) — самая распространённая. Приложение смотрит в кэш; если там пусто — читает из базы и кладёт в кэш. При изменении данных запись в кэше удаляется. Так устроена [статистика в «Задачнике»](../databases/redis/fastapi.md).

```text
чтение:    кэш → (промах) → база → записать в кэш
изменение: база → удалить из кэша
```

**Write-through** (сквозная запись) — при каждом изменении данные пишутся и в базу, и в кэш. Кэш всегда свежий, но каждая запись дороже, а в кэш попадают и данные, которые никто не прочитает.

**Write-behind** (отложенная запись) — изменения пишутся в кэш, а в базу уходят позже, пачками. Запись очень быстрая, но если кэш упадёт до сброса, данные пропадут. Подходит для счётчиков просмотров и лайков, где потеря пары значений не страшна.

## Инвалидация

> «В информатике есть только две сложные вещи: инвалидация кэша и придумывание названий», — Фил Карлтон.

Способы держать кэш свежим:

- **срок жизни (TTL)** — запись исчезнет сама. Это страховка, которая нужна почти всегда: даже если где-то забыли сбросить кэш, данные исправятся сами;
- **удаление при изменении** — сразу после записи в базу. Именно удаление, а не обновление: при обновлении два параллельных запроса могут записать в кэш значения в неправильном порядке;
- **версия в ключе** — `report:v42`. При изменении данных версия растёт, а старые ключи просто перестают использоваться и истекают сами.

Чтобы тысячи ключей не истекали одновременно (тоже лавина), к сроку жизни добавляют случайный разброс: `ex=300 + random.randint(0, 60)`.

## Что кэшировать

Хорошие кандидаты: данные, которые **часто читают и редко меняют**, а также результаты **дорогих** вычислений. Профили пользователей, справочники, статистика, результаты поиска.

Плохие кандидаты: данные, которые меняются при каждом запросе; данные, где устаревание недопустимо (остаток денег на счёте перед списанием); данные, которые и так быстро достаются по индексу.

## Частые ошибки

- **Кэш без срока жизни.** Память кончается, а устаревшие данные живут вечно.
- **Обновление кэша вместо удаления.** Параллельные запросы перезапишут значения в неправильном порядке, и в кэше останется старое.
- **Сброс кэша до записи в базу.** Между сбросом и записью другой запрос успеет положить в кэш старые данные.
- **Один ключ на всех.** Кэш списка задач без `user_id` в ключе покажет одному пользователю задачи другого.
- **Кэш как основное хранилище.** Redis может потерять данные при сбое. В кэше — только то, что можно восстановить из базы.
