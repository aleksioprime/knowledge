# Kafka изнутри: надёжность и хранение

Пока Kafka работает на одном брокере в docker compose, кажется, что это просто очередь с историей. Вопросы начинаются в бою: брокер перезагрузился — потерялись ли события «задача выполнена»? Почему продюсер вдруг получает `NotEnoughReplicasError`? Куда делось место на диске и почему потребитель отстал на миллион сообщений? Ответы — в том, как Kafka хранит журнал и копирует его между брокерами.

Основные понятия (топик, партиция, ключ, группа потребителей) — в [README](README.md) и заметке [Kafka в FastAPI](fastapi.md). Здесь — что под капотом. Пример с кластером из трёх брокеров — [examples/cluster](examples/cluster/README.md).

## Минимальный пример

Кластер из трёх брокеров, топик с тремя копиями каждой партиции и требованием «минимум две копии в строю»:

```bash
cd docs/backend/microservices/broker/kafka/examples/cluster
docker compose -p kb-kafka up -d
docker compose -p kb-kafka exec kafka-1 /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 --create --topic task-events --partitions 3

docker compose -p kb-kafka exec kafka-1 /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 --describe --topic task-events
```

```text
Topic: task-events  PartitionCount: 3  ReplicationFactor: 3  Configs: min.insync.replicas=2
  Partition: 0  Leader: 102  Replicas: 102,103,101  Isr: 102,103,101
  Partition: 1  Leader: 103  Replicas: 103,101,102  Isr: 103,101,102
  Partition: 2  Leader: 101  Replicas: 101,102,103  Isr: 101,102,103
```

Каждая партиция лежит на трёх брокерах (`Replicas`), у каждой свой лидер (`Leader`), и все три копии сейчас синхронны (`Isr`). Остановим два брокера из трёх — запись с `acks=all` перестанет проходить, а с `acks=1` пройдёт, но потом потеряется. Как именно — ниже.

## Брокеры, кластер и контроллер

**Брокер** — процесс Kafka, который хранит партиции на диске и обслуживает клиентов. Несколько брокеров образуют **кластер**. Клиенту достаточно знать адрес любого брокера (`bootstrap_servers`): он спросит у него метаданные — какие есть топики, где лидер каждой партиции — и дальше будет ходить напрямую к нужным брокерам.

Кто-то должен решать, какой брокер лидер, кто жив и где лежат копии. Это делает **контроллер**. Он хранит метаданные кластера: список брокеров, топики, партиции, лидеров и ISR (о нём ниже), настройки.

Раньше метаданные лежали в **ZooKeeper** — отдельной системе координации. Kafka хранила в нём список живых брокеров (через временные узлы, которые исчезают вместе с сессией), конфигурацию топиков и выбирала через него контроллера. Неудобства: ещё один кластер со своим мониторингом и настройкой, а при большом числе партиций новый контроллер долго перечитывал всё из ZooKeeper.

Сейчас используется **KRaft** (Kafka Raft): метаданные хранятся в служебном журнале `__cluster_metadata` внутри самой Kafka, а несколько узлов-контроллеров договариваются по протоколу Raft, кто из них главный. В Kafka 4.0 ZooKeeper удалён совсем. Каждый узел получает роль через `process.roles`: `broker`, `controller` или обе сразу.

```bash
docker compose -p kb-kafka exec kafka-1 /opt/kafka/bin/kafka-metadata-quorum.sh \
  --bootstrap-server localhost:9092 describe --status
```

```text
LeaderId:               1
CurrentVoters:          [{"id": 1, "endpoints": ["CONTROLLER://controller:9093"]}]
CurrentObservers:       [{"id": 102, ...}, {"id": 101, ...}, {"id": 103, ...}]
```

`Voters` — контроллеры, которые голосуют, `Observers` — брокеры, которые только читают метаданные. Контроллеров должно быть нечётное число (обычно три): Raft нужна живая **половина плюс один**. В учебном кластере контроллер один, чтобы можно было останавливать брокеры, не задевая кворум. Если в кластере из трёх совмещённых узлов (`broker,controller`) остановить два, кластер потеряет кворум и не сможет даже выбрать нового лидера партиции.

## Партиция — это журнал сегментов на диске

Партиция на брокере — каталог `<топик>-<номер>`. Внутри — **сегменты**: журнал режется на файлы, чтобы старое можно было удалять целиком, а не вырезать из середины.

```bash
docker compose -p kb-kafka exec kafka-1 ls -la /var/lib/kafka/data/task-events-2
```

```text
00000000000000000000.index       # смещение → позиция в .log
00000000000000000000.log         # сами сообщения
00000000000000000000.timeindex   # время → смещение
leader-epoch-checkpoint
partition.metadata
```

Имя файла — смещение первого сообщения в сегменте. Новые сообщения пишутся только в последний, **активный** сегмент. Когда он дорастает до `segment.bytes` (по умолчанию 1 ГБ) или стареет на `segment.ms` (по умолчанию 7 дней), открывается следующий. Файлы `.index` и `.timeindex` разреженные: по ним Kafka быстро находит место в `.log`, когда потребитель просит «с смещения 9» или «с 10:00 вчера».

**Смещение** (offset) — порядковый номер сообщения внутри партиции. Оно никогда не переиспользуется. Что лежит в журнале, видно утилитой `kafka-dump-log.sh`:

```bash
docker compose -p kb-kafka exec kafka-1 /opt/kafka/bin/kafka-dump-log.sh --print-data-log \
  --files /var/lib/kafka/data/task-events-2/00000000000000000000.log
```

```text
baseOffset: 0 lastOffset: 2 count: 3 ... producerId: 0 producerEpoch: 0 ... compresscodec: none
| offset: 0 ... key: user-1 payload: {"type":"task.created","task_id":1}
| offset: 1 ... key: user-2 payload: {"type":"task.created","task_id":2}
| offset: 2 ... key: user-1 payload: {"type":"task.done","task_id":1}
```

Сообщения хранятся **пачками** (batch) — в том виде, в каком их прислал продюсер, вместе со сжатием. Брокер не распаковывает и не перекладывает их, а отдаёт потребителю те же байты прямо из файла (через `sendfile`, минуя память процесса). Отсюда скорость Kafka: последовательная запись в конец файла и последовательное чтение.

## Репликация: лидер, фолловеры и ISR

У каждой партиции `replication.factor` копий (реплик) на разных брокерах. Одна из них **лидер**: через него идут вся запись и (по умолчанию) всё чтение. Остальные — **фолловеры**: они постоянно запрашивают у лидера новые сообщения, как обычные потребители, и дописывают их к себе.

**ISR** (in-sync replicas, синхронные реплики) — лидер плюс фолловеры, которые не отстают от него дольше `replica.lag.time.max.ms` (30 секунд). Отстал или упал — лидер просит контроллер исключить его из ISR. Догнал — возвращают.

**High watermark** — смещение, до которого сообщение есть у всех реплик из ISR. Потребители видят только сообщения ниже этой отметки. Сообщение, которое пока есть только у лидера, читать нельзя: если лидер упадёт, его может не оказаться у нового.

Три настройки определяют надёжность записи:

| Настройка | Где | Что значит |
|---|---|---|
| `replication.factor` | топик | Сколько копий партиции хранить. В продакшене обычно 3 |
| `min.insync.replicas` | топик или брокер | Сколько реплик из ISR (включая лидера) должно быть живо, чтобы принять запись с `acks=all`. Обычно 2 |
| `acks` | продюсер | Когда считать запись успешной |

Значения `acks`:

- `acks=0` — продюсер не ждёт ответа вообще. Самый быстрый и самый ненадёжный: сообщение могло не дойти даже до лидера;
- `acks=1` — ответ приходит, когда лидер записал сообщение к себе. Фолловеры могли его ещё не скопировать;
- `acks=all` (то же, что `-1`) — ответ приходит, когда сообщение есть у всех реплик в ISR, а их не меньше `min.insync.replicas`. С Kafka 3.0 это значение по умолчанию в Java-клиенте; в `aiokafka` по умолчанию `acks=1`, его нужно указывать явно.

### Что теряется: опыт на трёх брокерах

Топик `task-events`: `replication.factor=3`, `min.insync.replicas=2`. Скрипт [produce.py](examples/cluster/produce.py) шлёт события с нужным `acks` и печатает результат.

**Все три брокера живы.** `acks=all` записывается.

**Остановили `kafka-3`.** ISR сократился до двух — ровно `min.insync.replicas`, запись идёт:

```text
Partition: 2  Leader: 101  Replicas: 101,102,103  Isr: 102,101

task 1: записано, партиция 2, смещение 7
task 2: записано, партиция 2, смещение 8
```

**Остановили ещё и `kafka-2`.** В ISR остался один лидер:

```text
Partition: 2  Leader: 101  Replicas: 101,102,103  Isr: 101  Elr: 102
```

```bash
python produce.py --acks all --count 2    # примерно 11 секунд на повторы
# task 1: ошибка NotEnoughReplicasError
# task 2: ошибка NotEnoughReplicasError

python produce.py --acks 1 --count 2
# task 1: записано, партиция 2, смещение 9
# task 2: записано, партиция 2, смещение 10

python produce.py --acks 0 --count 2
# task 1: отправлено, подтверждения нет
# task 2: отправлено, подтверждения нет
```

`acks=all` честно отказывает: копий меньше двух, гарантировать сохранность нельзя. Продюсер получает ошибку и может повторить позже, сохранить событие у себя или вернуть клиенту 503. `acks=1` и `acks=0` записались на лидера — продюсер считает, что всё хорошо.

При этом прочитать эти четыре сообщения нельзя: `kafka-get-offsets.sh` показывает конец партиции `9`, потребитель получает сообщения до смещения 8 включительно и дальше ждёт. High watermark не двигается, пока ISR меньше `min.insync.replicas` (так вела себя Kafka 4.1.0 на стенде, где включён механизм ELR — о нём ниже; в старых версиях high watermark двигался, и такие сообщения сразу становились видны).

**Теперь упал лидер.** Останавливаем `kafka-1` и поднимаем `kafka-2`. Новым лидером становится `kafka-2` — у него есть всё до high watermark, но нет смещений 9–12:

```text
Partition: 2  Leader: 102  Replicas: 101,102,103  Isr: 102  Elr: 101
task-events:2:9
```

Возвращаем `kafka-1` — он становится фолловером и **обрезает свой журнал** до версии нового лидера:

```text
INFO [UnifiedLog partition=task-events-2, dir=/var/lib/kafka/data] Truncating to offset 9
```

В журнале на `kafka-1` остались пачки со смещениями 0–8. Два события, на которые продюсер с `acks=1` получил «записано», исчезли без следа, так же как два события с `acks=0`. Следующие события, отправленные уже с `acks=all` после восстановления кластера, получили те же смещения 9, 10, 11 — номер «смещение 9» теперь означает другое событие.

Итог по комбинациям (при `replication.factor=3`):

| `acks` | `min.insync.replicas` | Что будет |
|---|---|---|
| `0` | любое | Теряется при любом сбое сети или брокера, продюсер не узнает |
| `1` | любое | Теряется, если лидер упал раньше, чем фолловеры скопировали сообщение |
| `all` | `1` | Если в ISR остался один лидер, `all` превращается в `1`: запись принята одной копией и пропадёт вместе с ней |
| `all` | `2` | Подтверждённое не теряется, пока не умерли сразу два диска. Переживает падение одного брокера без остановки записи |
| `all` | `3` | Самое надёжное, но падение любого брокера останавливает запись |

Рабочая настройка — `replication.factor=3`, `min.insync.replicas=2`, `acks=all`.

### Unclean leader election и ELR

Что делать, если все реплики из ISR умерли, а жива только отстающая? Решает `unclean.leader.election.enable`:

- `false` (по умолчанию) — ждать, пока вернётся кто-то из ISR. Партиция недоступна, зато подтверждённые данные не теряются;
- `true` — сделать лидером отстающую реплику. Партиция снова работает, но всё, чего у этой реплики не было, потеряно, а вернувшиеся реплики обрежут журнал под неё.

Включают это там, где доступность важнее полноты: метрики, логи. Для событий «оценка задачи» или платежей — нет.

В Kafka 4.x к ISR добавился список **ELR** (eligible leader replicas) — колонка `Elr` в выводе выше. Когда реплика выпадает из ISR, но ISR уже меньше `min.insync.replicas`, контроллер запоминает её в ELR: у неё гарантированно есть всё до high watermark. Такую реплику можно сделать лидером без потерь подтверждённых данных — именно так в опыте выше `kafka-2` стал лидером, хотя в ISR его уже не было. Сообщения выше high watermark при этом не гарантированы, поэтому записанное с `acks=1` и пропало.

## Хранение: сколько и что держать

По умолчанию Kafka удаляет старые данные, а не прочитанные. Политика задаётся `cleanup.policy`.

### `cleanup.policy=delete`

Сегмент удаляется целиком, когда выполнено одно из условий:

- `retention.ms` — все сообщения в сегменте старше этого срока (по умолчанию 7 дней, `-1` — хранить вечно);
- `retention.bytes` — партиция больше этого размера (по умолчанию без ограничения). Лимит на **партицию**, а не на топик: топик из 12 партиций с `retention.bytes=1GB` займёт до 12 ГБ на каждую реплику.

Активный сегмент не удаляется никогда. Поэтому `retention.ms=60000` при `segment.ms` в 7 дней ничего не удалит, пока сегмент не закроется.

```bash
docker compose -p kb-kafka exec kafka-1 /opt/kafka/bin/kafka-configs.sh --bootstrap-server localhost:9092 \
  --alter --entity-type topics --entity-name task-events --add-config retention.ms=259200000
```

### `cleanup.policy=compact`

Компакция хранит **последнее значение для каждого ключа**. Это журнал состояния, а не событий: «текущий статус задачи», «настройки пользователя». Новый сервис читает топик с начала и получает актуальный снимок без всей истории изменений.

```bash
kafka-topics.sh --create --topic task-status --partitions 1 \
  --config cleanup.policy=compact --config segment.ms=5000 --config min.cleanable.dirty.ratio=0.01
```

Записали шесть сообщений, потом ещё одно, чтобы первый сегмент закрылся:

```text
task-1:new  task-2:new  task-1:in_progress  task-3:new  task-1:done  task-2:done   |   task-4:new
```

Через полминуты фоновый процесс очистки (log cleaner) переписал закрытый сегмент:

```text
Dumping .../task-status-0/00000000000000000000.log
| offset: 3 ... key: task-3 payload: new
| offset: 4 ... key: task-1 payload: done
| offset: 5 ... key: task-2 payload: done
Dumping .../task-status-0/00000000000000000006.log
| offset: 6 ... key: task-4 payload: new
```

Старые значения `task-1` и `task-2` пропали, смещения остались прежними — в журнале появились дырки, и это нормально. Активный сегмент (`task-4`) не трогается. Чтобы удалить ключ совсем, пишут сообщение с этим ключом и пустым значением (tombstone, «надгробие»): через `delete.retention.ms` исчезнет и оно.

`segment.ms=5000` и `min.cleanable.dirty.ratio=0.01` нужны только для опыта, чтобы очистка началась сразу. В бою оставляют значения по умолчанию, иначе брокер будет постоянно переписывать файлы. Политики можно совместить: `cleanup.policy=compact,delete` — компакция плюс удаление по сроку.

## Группы потребителей и ребалансировка

Группа делит партиции топика между участниками: каждая партиция читается ровно одним потребителем группы. Распределением занимается **координатор группы** — один из брокеров. Смещения группы он хранит в служебном топике `__consumer_offsets` (тоже реплицированном, отсюда настройка `offsets.topic.replication.factor`).

**Ребалансировка** — перераспределение партиций. Происходит, когда потребитель вошёл в группу, вышел, упал (перестал слать heartbeat дольше `session.timeout.ms`) или слишком долго обрабатывал пачку (дольше `max.poll.interval.ms` между запросами). В классическом протоколе на время ребалансировки вся группа останавливает чтение. Смягчения:

- `partition.assignment.strategy=cooperative-sticky` — отбирают только те партиции, которые реально переезжают;
- `group.instance.id` (статическое членство) — перезапуск пода с тем же id не вызывает ребалансировку, если он вернулся за `session.timeout.ms`;
- новый протокол групп (KIP-848, включён на брокерах Kafka 4.0, клиент выбирает его через `group.protocol=consumer`) — распределением управляет брокер, участники не останавливаются все сразу. В Java-клиенте он есть, в `aiokafka` 0.15 пока нет.

После ребалансировки новый владелец партиции продолжает с последнего **зафиксированного** смещения. Всё, что старый владелец обработал, но не зафиксировал, придёт ещё раз — поэтому обработка должна выдерживать повторы.

### Лаг потребителя

**Лаг** — сколько сообщений записано, но ещё не прочитано группой. Главная метрика здоровья потребителя.

```bash
docker compose -p kb-kafka exec kafka-1 /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 --describe --group stats
```

```text
Consumer group 'stats' has no active members.

GROUP  TOPIC        PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG  CONSUMER-ID
stats  task-events  2          4               14              10   -
stats  task-events  1          0               2               2    -
stats  task-events  0          0               0               0    -
```

Консольный потребитель прочитал четыре сообщения из партиции 2 и вышел.

- `CURRENT-OFFSET` — до какого места группа зафиксировала чтение;
- `LOG-END-OFFSET` — конец партиции (точнее, high watermark);
- `LAG` — разница. Стабильно небольшой лаг — норма. Растущий — потребитель не успевает: добавить потребителей (если партиций хватает), ускорить обработку, писать в базу пачками;
- `CONSUMER-ID` пустой — в группе сейчас никого нет, смещения просто хранятся.

## Гарантии доставки в Kafka

Общие определения — в заметке [о брокерах](../README.md). Что они значат в Kafka:

- **At most once** (не больше одного раза) — потребитель фиксирует смещение **до** обработки или продюсер шлёт с `acks=0` без повторов. Упал — сообщение пропущено;
- **At least once** (хотя бы один раз) — продюсер с `acks=all` и повторами, потребитель фиксирует смещение **после** обработки. Сбой → повтор → возможны дубли. Самый частый выбор, дубли гасят идемпотентной обработкой (уникальный `event_id`, `INSERT ... ON CONFLICT DO NOTHING`);
- **Exactly once** (ровно один раз) — внутри Kafka достижимо двумя механизмами.

**Идемпотентный продюсер** (`enable.idempotence=true`, в Java-клиенте по умолчанию с Kafka 3.0) решает проблему дублей при повторах. Каждый продюсер получает `producerId`, каждая пачка — порядковый номер (`sequence`, видно в выводе `kafka-dump-log` выше). Если ответ брокера потерялся и продюсер прислал ту же пачку снова, брокер видит уже записанный номер и не пишет дубль. Работает в рамках одной сессии продюсера и одной партиции.

**Транзакции** — атомарная запись в несколько партиций и топиков. Продюсер с `transactional.id` открывает транзакцию, пишет сообщения, фиксирует смещения потребителя (`send_offsets_to_transaction`) и подтверждает всё разом. Потребители с `isolation.level=read_committed` не видят сообщения незавершённых и отменённых транзакций. Так строят цепочку «прочитал из топика A → посчитал → записал в топик B» без потерь и дублей (на этом работают Kafka Streams с `exactly_once_v2`).

Граница у этих гарантий одна: они действуют, пока данные внутри Kafka. Если потребитель пишет в PostgreSQL или ClickHouse, Kafka-транзакция не охватывает внешнюю базу. Там exactly once собирают из at least once и идемпотентной записи: ключ события, дедупликация, хранение смещения в той же транзакции базы.

## Сколько партиций выбирать

Партиция — единица параллелизма: в группе не может читать больше потребителей, чем есть партиций. Отсюда оценка:

```text
партиций ≥ max(целевой поток / поток одного потребителя, целевой поток / поток записи в одну партицию)
```

Например, нужно 30 тыс. событий в секунду, один потребитель с записью в базу успевает 5 тыс. — нужно минимум 6 партиций, берут с запасом 12.

Что ещё учитывать:

- **Добавить партиции можно, уменьшить нельзя.** И при добавлении меняется соответствие «ключ → партиция»: события пользователя 42 начнут попадать в другую партицию, порядок между старыми и новыми нарушится. Поэтому число партиций для топика с ключами закладывают с запасом сразу;
- **Слишком много — тоже плохо.** Каждая партиция — открытые файлы, место в метаданных, больше работы при выборе лидеров. Ориентир: тысячи партиций на брокер — нормально, сотни тысяч на кластер требуют внимания;
- **Мало ключей — мало пользы от партиций.** Если ключей три, используются максимум три партиции, остальные пустуют;
- **Число, кратное потребителям.** 12 партиций одинаково ровно делятся на 2, 3, 4 и 6 потребителей.

Для учебного проекта и небольшого сервиса хватает 3–6 партиций.

## Частые ошибки

- **`acks=1` (по умолчанию в aiokafka) для важных событий.** Падение лидера в неудачный момент теряет подтверждённые события, и об этом никто не узнаёт. Явно ставьте `acks='all'`.
- **`min.insync.replicas=1` при `replication.factor=3`.** Выглядит надёжно, но когда в ISR остаётся один брокер, `acks=all` перестаёт защищать. Ставьте 2.
- **Настройки топиков по умолчанию в KRaft берутся у контроллера.** В учебном кластере `KAFKA_MIN_INSYNC_REPLICAS=2` сначала был задан только брокерам — новые топики создались с `min.insync.replicas=1`. Задавайте значение и контроллерам, а для важных топиков — явно при создании (`--config min.insync.replicas=2`).
- **`replication.factor` у служебных топиков.** `__consumer_offsets` с одной копией: потеряли брокер — группы потеряли смещения. В кластере задавайте `offsets.topic.replication.factor=3` и `transaction.state.log.replication.factor=3` до первого запуска: служебный топик создаётся один раз.
- **Ждать, что `retention.ms` освободит место сразу.** Удаляются только закрытые сегменты, поэтому реальный срок хранения — до `retention.ms + segment.ms`.
- **Компакция как способ удалить данные.** Компакция не трогает активный сегмент и работает с задержкой, а без tombstone ключ не удаляется никогда. Для персональных данных этого мало: нужны tombstone и контроль сроков.
- **Долгая обработка пачки.** Дольше `max.poll.interval.ms` — потребителя выкидывают из группы, начинается ребалансировка, пачка приходит снова другому потребителю. Уменьшайте `max.poll.records` или выносите тяжёлую работу.

## Когда не использовать

Если события нужны одному потребителю и после обработки не нужны никому, кластер Kafka с репликацией — лишняя сложность: хватит RabbitMQ или очереди в Redis. Сравнение — в [заметке о брокерах](../README.md). Для учебного стенда и локальной разработки хватает одного брокера с `replication.factor=1`, как в [примере fastapi](examples/fastapi/README.md).
