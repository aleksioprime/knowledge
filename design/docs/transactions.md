# Распределённые транзакции: Saga и Outbox

Оформление заказа в интернет-магазине затрагивает три сервиса: склад резервирует товар, платёжный сервис списывает деньги, служба доставки создаёт заявку. У каждого своя база, и общей транзакции, которая откатит всё при ошибке, нет. Если оплата не прошла, товар нужно снять с резерва. Если заказ сохранён, а сообщение о нём не дошло до склада, товар так и не зарезервируют. Saga и Outbox — два паттерна, которые решают эти проблемы.

## Минимальный пример: Saga

Saga разбивает большую операцию на шаги. У каждого шага есть **компенсация** — действие, которое отменяет его результат. Если шаг упал, выполняются компенсации уже сделанных шагов в обратном порядке:

```python
STEPS = [
    (reserve_stock, release_stock),
    (charge, refund),
    (create_delivery, cancel_delivery),
]


def place_order(order) -> bool:
    done = []
    for action, compensate in STEPS:
        try:
            action(order)
            done.append(compensate)
        except Exception as error:
            print(f'ошибка: {error}, откатываем')
            for compensate_step in reversed(done):
                compensate_step(order)
            return False
    return True
```

```text
place_order({'item': 'книга', 'amount': 500})
склад: зарезервировано книга
оплата: списано 500 ₽
доставка: заявка создана
→ True

place_order({'item': 'ноутбук', 'amount': 90000})
склад: зарезервировано ноутбук
ошибка: недостаточно средств, откатываем
склад: резерв ноутбук снят
→ False
```

## Как работает Saga

Компенсация — это не откат транзакции, а **новое действие**: «вернуть деньги», «снять резерв». Между шагами система находится в промежуточном состоянии (товар зарезервирован, но ещё не оплачен), и другие запросы его видят. Это и есть цена отказа от общей транзакции: согласованность становится [итоговой](consistency.md#base-и-итоговая-согласованность).

Saga бывает двух видов:

- **оркестрация** — один сервис-оркестратор знает весь сценарий и по очереди вызывает остальные, как функция `place_order` выше. Сценарий виден в одном месте, его легко менять и отлаживать;
- **хореография** — центра нет: склад публикует событие «товар зарезервирован», платёжный сервис на него подписан и списывает деньги, затем публикует «оплачено», и так далее. Сервисы слабее связаны, но общий сценарий приходится собирать по кусочкам из разных сервисов.

Компенсация тоже может упасть. Поэтому компенсации повторяют, пока они не пройдут, и делают **идемпотентными**: повторный «возврат денег» по тому же заказу не должен вернуть деньги дважды (см. [устойчивость](resilience.md)).

## Почему не двухфазная фиксация (2PC)

Классический ответ на распределённые транзакции — **двухфазная фиксация**: координатор спрашивает всех участников «готовы?», и если все ответили «да», командует «фиксируйте». Это даёт настоящую атомарность, но:

- пока координатор не ответил, участники держат блокировки;
- если координатор упал между фазами, участники зависают в неизвестности;
- все сервисы должны поддерживать один протокол, а внешние API (платёжные системы, почта) его не поддерживают.

Поэтому между микросервисами 2PC почти не используют, а выбирают Saga.

## Минимальный пример: Outbox

Сервис заказов сохраняет заказ в свою базу и публикует событие `order.created` в брокер. Это две разные системы, и между ними может случиться сбой:

- заказ сохранён, а публикация упала — склад ничего не узнает;
- событие опубликовано, а транзакция откатилась — склад резервирует товар для заказа, которого нет.

**Outbox** решает это так: событие записывается в специальную таблицу **той же базы и той же транзакцией**, что и заказ. А отдельный процесс-ретранслятор потом читает таблицу и публикует события в брокер:

```python
def create_order(item: str) -> None:
    # Заказ и событие о нём — в одной транзакции: либо оба, либо ничего
    with db:
        cursor = db.execute('INSERT INTO orders (item) VALUES (?)', (item,))
        event = {'order_id': cursor.lastrowid, 'item': item}
        db.execute(
            'INSERT INTO outbox (id, topic, payload) VALUES (?, ?, ?)',
            (str(uuid.uuid4()), 'order.created', json.dumps(event, ensure_ascii=False)),
        )


def relay() -> None:
    rows = db.execute('SELECT id, topic, payload FROM outbox WHERE published = 0 ORDER BY rowid').fetchall()
    for event_id, topic, payload in rows:
        try:
            publish(topic, payload)
        except ConnectionError as error:
            print('не отправлено:', error)
            return
        with db:
            db.execute('UPDATE outbox SET published = 1 WHERE id = ?', (event_id,))
```

```text
create_order('книга'); create_order('лампа')

relay()           # брокер недоступен
не отправлено: брокер недоступен
ждут отправки: 2

relay()           # брокер снова работает
опубликовано order.created {"order_id": 1, "item": "книга"}
опубликовано order.created {"order_id": 2, "item": "лампа"}
ждут отправки: 0
```

События не потерялись, пока брокер лежал: они ждали в таблице. А если упадёт сама транзакция заказа, вместе с ней исчезнет и событие:

```text
заказов: 2, событий: 2   — заказ «стол» откатился вместе со своим событием
```

## Как работает Outbox

- Ретранслятор запускается периодически (раз в секунду, [Celery Beat](../../framework/celery/docs/retries_beat_canvas.md)) или читает журнал изменений базы (Debezium для PostgreSQL).
- Если ретранслятор опубликовал событие, но упал до отметки `published = 1`, событие уйдёт ещё раз. Outbox даёт гарантию **«хотя бы один раз»**, поэтому получатель должен уметь пропускать повторы по `id` события:

```python
processed = set()  # в реальном сервисе — таблица в базе


def handle(event_id, payload):
    if event_id in processed:
        print('повтор пропущен')
        return
    processed.add(event_id)
    ...


handle(event_id, payload)  # обработано
handle(event_id, payload)  # повтор пропущен
```

Это зеркальный паттерн — **Inbox**: получатель запоминает обработанные события в той же транзакции, что и результат обработки.

## Частые ошибки

- **Публикация события прямо в транзакции.** `session.add(order); publish(event); session.commit()` — если `commit` упадёт, событие уже ушло.
- **Компенсации, которые нельзя повторить.** Компенсация упала на середине, её повторили — и деньги вернулись дважды.
- **Saga без состояния.** Если оркестратор упал посреди сценария, после перезапуска он должен знать, какие шаги уже сделаны. Шаги и их результаты сохраняют в базу.
- **Распределённая транзакция там, где хватит одной базы.** Если заказы и склад — один сервис с одной базой, обычная транзакция проще и надёжнее любой Saga. Сначала проверьте, нужно ли вообще разделять.
