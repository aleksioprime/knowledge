# Модули

Когда вся программа лежит в одном файле, любая функция видит любую другую, имена сталкиваются, а понять, что от чего зависит, невозможно. Модуль — файл с собственной областью видимости: он явно экспортирует значения, которыми разрешено пользоваться другим файлам, и импортирует только необходимые зависимости. Так проект делится на части с понятными границами, а связи между ними видны в первых строках каждого файла.

## Минимальный пример

```js
// tasks.js
export const MAX_TITLE_LENGTH = 100

export function createTask(title) {
  return { title, done: false }
}

export default function completeTask(task) {
  return { ...task, done: true }
}

// app.js
import completeTask, { createTask, MAX_TITLE_LENGTH } from './tasks.js'

const task = createTask('Купить хлеб')
console.log(task) // { title: 'Купить хлеб', done: false }
console.log(completeTask(task)) // { title: 'Купить хлеб', done: true }
console.log(MAX_TITLE_LENGTH) // 100
```

Чтобы запустить пример в Node.js, сохраните файлы с расширением `.mjs` (и поправьте путь в `import`) или добавьте `"type": "module"` в `package.json`.

## Как это работает

### Именованные export и import

Именованный экспорт удобен, когда модуль предоставляет несколько независимых значений. Имя при импорте должно совпадать с именем экспорта, но его можно изменить через `as`.

```js
// math.js
export const PI = 3.14

export function sum(a, b) {
  return a + b
}
```

```js
// app.js
import { PI, sum as add } from './math.js' // в этом файле sum доступна под именем add

console.log(PI) // 3.14
console.log(add(2, 3)) // 5
```

Импорты являются «живыми связями». Если экспортируемая переменная изменится внутри исходного модуля, импортирующий код увидит новое значение. При этом присваивать новое значение непосредственно импортированной переменной нельзя.

### Default export

У модуля может быть не более одного default-экспорта. При импорте ему можно дать любое локальное имя, поэтому такой экспорт обычно используют для одного главного значения файла.

```js
// user-service.js
export default class UserService {
  getUser(id) {
    return { id }
  }
}
```

```js
// app.js
import Service from './user-service.js'

const service = new Service()
service.getUser(42) // { id: 42 }
```

Именованные экспорты обычно проще автоматически переименовывать и искать по проекту. Default-экспорт полезен, если у файла действительно есть одно очевидное главное значение.

### Динамический импорт

Обычные `import` записываются на верхнем уровне и загружаются вместе с модулем. Выражение `import()` возвращает Promise и позволяет загрузить код только в тот момент, когда он понадобился.

```js
const module = await import('./chart.js')
const chart = module.createChart(data)
```

Динамический импорт применяют для тяжёлых или редко используемых частей приложения: редактора, графиков, административной страницы. Сборщик проекта может вынести такой модуль в отдельный файл и не загружать его до вызова `import()`.

### Модули в браузере и Node.js

В браузере входной файл подключают с атрибутом `type="module"`. Такие скрипты выполняются в строгом режиме, имеют собственную область видимости и по умолчанию откладываются до разбора HTML.

```html
<script type="module" src="./app.js"></script>
```

Node.js поддерживает ES-модули через расширение `.mjs` или настройку `"type": "module"` в `package.json`. В старых Node.js-проектах можно встретить систему CommonJS с `require()` и `module.exports`; это другой формат модулей, и смешивать два формата без настройки среды нельзя.

### Организация модулей

Хороший модуль решает одну понятную задачу. Например, файл `api/users.js` отвечает за запросы пользователей, а `format/date.js` — только за форматирование дат. Если файлы начинают импортировать друг друга по кругу, стоит пересмотреть границы ответственности: циклические зависимости усложняют порядок инициализации и тестирование.

Не создавайте общий файл `utils.js` для несвязанных функций. Папки и названия модулей должны объяснять назначение кода без чтения его содержимого.

### Полифилы

Полифил — код, который добавляет в старую среду отсутствующую стандартную возможность. Например, приложение может подключить реализацию нового метода массива, если целевые браузеры его ещё не поддерживают.

Полифил отличается от транспиляции. Полифил добавляет отсутствующий API во время выполнения, а транспилятор заранее преобразует новый синтаксис в более старый. Перед подключением полифила проверяют требования проекта и поддержку целевых браузеров: лишние полифилы увеличивают размер приложения.

## Частые ошибки

- Default-экспорт импортирован в фигурных скобках (`import { completeTask } from './tasks.js'`) → `SyntaxError: does not provide an export named` → импортировать default без скобок, а именованные — в скобках.
- В браузере или Node.js путь указан без расширения (`'./tasks'`) → модуль не найден, хотя в сборщике такой импорт работал → писать полный относительный путь с `./` и `.js`.
- Скрипт подключён без `type="module"` → `SyntaxError: Cannot use import statement outside a module` → добавить атрибут `type="module"` или настроить `"type": "module"` в `package.json`.
- Присваивание импортированной переменной (`PI = 3`) → `TypeError: Assignment to constant variable` → менять значение внутри экспортирующего модуля через экспортированную функцию.
- Два модуля импортируют друг друга → один из них на момент инициализации получает `undefined` вместо ожидаемого значения → вынести общую часть в третий модуль и разорвать цикл.

## Когда не использовать

Для короткого скрипта на одной странице или сниппета в консоли модульная система лишняя: достаточно одного файла или обычного `<script>`. Разделение на модули окупается, когда у кода появляются несколько независимых частей и их хочется тестировать и переиспользовать отдельно.

Не дробите проект слишком мелко: модуль на одну строку или папка `utils` из десятков несвязанных функций усложняют навигацию так же, как один огромный файл. Если несколько функций всегда используются вместе, им место в одном модуле.
