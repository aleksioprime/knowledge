# TCP-соединения и порты

Прежде чем отправить HTTP-запрос, клиент открывает TCP-соединение (для HTTP/3 используется QUIC поверх UDP). Удобно знать, как система отличает одно соединение от другого: от этого зависит, сколько клиентов выдержит сервер и почему иногда «заканчиваются порты».

## Минимальный пример

```bash
# Три соединения к одному серверу: порт сервера одинаковый,
# а пара «IP клиента + порт клиента» у каждого своя
ss -tn state established '( dport = :443 )'
# Recv-Q Send-Q Local Address:Port   Peer Address:Port
# 0      0      192.168.1.10:51820   93.184.216.34:443
# 0      0      192.168.1.10:51821   93.184.216.34:443
# 0      0      192.168.1.10:51822   93.184.216.34:443

# Два запроса в одном вызове curl идут по одному соединению (keep-alive)
curl -sv https://example.com https://example.com -o /dev/null -o /dev/null 2>&1 \
  | grep -E 'Connected|Re-using|left intact'
# * Connected to example.com (93.184.216.34) port 443
# * Connection #0 to host example.com left intact
# * Re-using existing connection with host example.com
# * Connection #0 to host example.com left intact
```

## Как это работает

### Как различаются соединения

Каждое соединение однозначно задаётся пятью значениями:

- IP-адрес клиента;
- порт клиента;
- IP-адрес сервера;
- порт сервера;
- протокол (TCP или UDP).

Сервер слушает один фиксированный порт, например `0.0.0.0:443`. Клиенты приходят к нему со своих адресов и случайных исходящих портов:

```text
192.168.1.10:51820 -> 93.184.216.34:443
192.168.1.11:39214 -> 93.184.216.34:443
192.168.1.12:60017 -> 93.184.216.34:443
```

Порт сервера во всех строках одинаковый, но в каждой строке есть хотя бы одно отличающееся значение. Для системы это три разных соединения.

### Сколько соединений возможно

**Со стороны клиента.** Номер порта занимает 16 бит, поэтому портов не больше 65 535. На деле исходящих портов меньше: в Linux по умолчанию это диапазон `32768–60999`, около 28 тысяч. Значит, с одного IP-адреса к одному адресу и порту сервера можно держать примерно столько же одновременных соединений.

```bash
cat /proc/sys/net/ipv4/ip_local_port_range
# 32768   60999
```

Эта граница встречается чаще, чем кажется. Например, если NGINX или сервис-посредник открывает к бэкенду новое соединение на каждый запрос и не переиспользует их, при высокой нагрузке свободные порты кончаются. Помогает keep-alive и пул соединений.

**Со стороны сервера.** Ограничения по портам здесь нет: у каждого клиента свой IP и свои порты, поэтому сервер на одном порту `443` может обслуживать миллионы соединений. Упираться он будет в память, лимит открытых файлов (`ulimit -n`) и процессор.

## Частые ошибки

- Прокси или сервис открывает новое соединение к бэкенду на каждый запрос → под нагрузкой ошибки `Cannot assign requested address`, тысячи соединений в `TIME_WAIT` → включить keep-alive и пул соединений (в NGINX — `keepalive` в блоке `upstream` и `proxy_http_version 1.1`).
- Сервер упёрся в лимит открытых файлов → в логах `Too many open files`, новые клиенты получают отказ, хотя процессор свободен → поднять `ulimit -n` для процесса (`LimitNOFILE` в systemd) и `worker_connections` в NGINX.
- Считают, что сервер не выдержит больше 65 535 соединений → неверные расчёты ёмкости → лимит 65 535 относится к исходящим портам одного клиента к одному адресу; сервер ограничен памятью и дескрипторами.
- Приложение в контейнере слушает `127.0.0.1` → снаружи контейнера `connection refused`, хотя внутри всё работает → слушать `0.0.0.0`.
- Клиент создаёт HTTP-клиент на каждый запрос (`httpx.Client()` внутри цикла) → каждый вызов платит за TCP- и TLS-рукопожатие, порты расходуются впустую → один клиент на приложение с пулом соединений.

## Когда не использовать

Для обычного веб-приложения на сотни клиентов об этих лимитах думать не нужно: их не достичь. Проблема возникает у прокси, балансировщиков, нагрузочных тестов и сервисов, которые сами делают много исходящих запросов.

Писать работу с сокетами руками тоже не стоит: HTTP-клиент с пулом соединений ([HTTPX](../../microservices/httpx/README.md), `requests.Session`) или NGINX уже решают переиспользование соединений и таймауты. Сокеты нужны для своих протоколов и для понимания, что происходит под капотом.
