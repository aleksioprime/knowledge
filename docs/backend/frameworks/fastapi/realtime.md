# Уведомления в реальном времени: WebSocket, SSE, long polling

Борис назначил Анне задачу «Подготовить отчёт» и оставил к ней комментарий. Анна сидит в открытой вкладке «Задачника» и должна увидеть это сразу, без перезагрузки страницы. Обычный HTTP устроен как «клиент спросил — сервер ответил»: сервер не может сам заговорить первым. Значит, нужно либо держать открытым запрос, на который сервер ответит позже, либо держать постоянное соединение.

В заметке — серверная сторона на FastAPI. Как WebSocket выглядит в браузере, разобрано в [заметке про JavaScript](../../../languages/javascript/websocket.md), как устроен чат целиком — в [разборе чата](../../design/chat.md). Весь код ниже — из [учебного примера](examples/realtime/README.md): два экземпляра сервиса, Redis и nginx в Docker Compose.

## Минимальный пример

Соединение по WebSocket: принять, проверить токен, запомнить пользователя и ждать сообщений, пока клиент не уйдёт.

```python
# app/ws.py (сокращённо)
@router.websocket('/ws')
async def notifications_ws(websocket: WebSocket, token: str | None = None):
    settings = websocket.app.state.settings
    manager = websocket.app.state.manager
    await websocket.accept()
    user_id = user_from_token(token, settings.jwt_secret)
    if user_id is None:
        await websocket.close(code=status.WS_1008_POLICY_VIOLATION, reason='invalid token')
        return

    manager.add(user_id, websocket)
    try:
        while True:
            text = await websocket.receive_text()
            await handle(websocket, text)
    except WebSocketDisconnect:
        pass
    finally:
        manager.remove(user_id, websocket)
```

Другой сервис (например, тот, где назначают задачи) отправляет уведомление через `POST /notify`. Анна подключена к первому экземпляру, а запрос пришёл на второй — и всё равно дошёл:

```text
tests/integration/test_cluster.py::test_notification_crosses_instances
подключение к app1, уведомление отправлено через app2: {'id': '1793268018343-0', 'event': 'task_assigned', 'data': {'task_id': 42, 'title': 'Подготовить отчёт'}, 'from': 'app2'}
PASSED
```

## Как это работает

### Четыре способа доставить событие

**Частый опрос (polling).** Клиент раз в несколько секунд спрашивает: «есть новое?». Просто и работает везде, но почти все запросы пустые, а задержка — до интервала опроса. Тысяча открытых вкладок с опросом раз в 2 секунды — 500 запросов в секунду ради нескольких уведомлений в минуту.

**Долгий опрос (long polling).** Клиент спрашивает, а сервер не отвечает сразу: держит запрос, пока не появится событие или не выйдет таймаут (обычно 20–30 секунд). Получив ответ, клиент тут же отправляет следующий запрос. Задержка почти нулевая, запросов мало, и это всё ещё обычный HTTP — работает через любые прокси.

**Server-Sent Events (SSE).** Клиент отправляет один GET, а сервер отвечает потоком `text/event-stream` и не закрывает его, дописывая события по мере появления. Поток односторонний: от сервера к клиенту. Браузерный `EventSource` сам переподключается при обрыве и присылает заголовок `Last-Event-ID` с номером последнего полученного события — сервер может догрузить пропущенное. Это обычный HTTP-ответ, поэтому прокси, HTTP/2 и куки работают как всегда.

**WebSocket.** Клиент отправляет HTTP-запрос с заголовком `Upgrade: websocket`, сервер отвечает `101 Switching Protocols`, и дальше по тому же TCP-соединению обе стороны шлют сообщения когда хотят. Двусторонний канал с минимальными накладными расходами на сообщение. Переподключение и догрузку пропущенного придётся писать самим.

| | Polling | Long polling | SSE | WebSocket |
|---|---|---|---|---|
| Направление | клиент → сервер | клиент → сервер | сервер → клиент | в обе стороны |
| Задержка | до интервала опроса | почти нет | почти нет | почти нет |
| Протокол | HTTP | HTTP | HTTP | свой поверх TCP после `Upgrade` |
| Переподключение | не нужно | цикл на клиенте | встроено в `EventSource` | пишется вручную |
| Догрузка пропущенного | параметр запроса | параметр запроса | `Last-Event-ID` | пишется вручную |
| Данные | любые | любые | только текст | текст и двоичные |
| Через строгие прокси | да | да | обычно да (нужно отключить буферизацию) | не всегда |
| Нагрузка на сервер | много пустых запросов | запрос на каждое событие | одно соединение | одно соединение |

Правило выбора:

- нужно только «сервер сообщает клиенту» — уведомления, прогресс задачи, лента — берите **SSE**;
- клиент тоже часто пишет — чат, совместное редактирование, игра — **WebSocket**;
- события редкие, а инфраструктура неизвестна (корпоративный прокси, старые балансировщики) — **long polling**;
- данные обновляются раз в минуты и задержка не важна — хватит **обычного опроса**.

В «Задачнике» уведомления идут только к клиенту, так что SSE хватило бы. WebSocket в примере нужен, чтобы показать двусторонний канал: клиент отмечает уведомление прочитанным (`{"type": "read", "id": ...}`) по тому же соединению.

**Изящная деградация.** Клиент пробует WebSocket; если соединение не устанавливается (прокси режет `Upgrade`) — переключается на SSE, а если и поток не доходит (прокси буферизует ответ) — на long polling. Чтобы это было дёшево, все три точки входа в примере читают из одного источника: `/ws`, `/events` и `/poll` получают события от одного менеджера соединений и догружают пропущенное из одного хранилища. Готовые библиотеки (Socket.IO, SignalR, Centrifugo) делают такой откат сами, но требуют своего клиента.

### Менеджер соединений

У Анны открыто три вкладки — это три соединения. Поэтому менеджер хранит не «пользователь → соединение», а «пользователь → набор соединений», и уведомление уходит во все вкладки:

```python
# app/manager.py (сокращённо)
class ConnectionManager:
    def __init__(self, send_timeout: float = 2.0):
        self.send_timeout = send_timeout
        self.sockets: dict[str, set[WebSocket]] = defaultdict(set)

    def add(self, user_id: str, websocket: WebSocket) -> None:
        self.sockets[user_id].add(websocket)

    def remove(self, user_id: str, websocket: WebSocket) -> None:
        connections = self.sockets.get(user_id)
        if connections is None:
            return
        connections.discard(websocket)
        if not connections:
            del self.sockets[user_id]

    async def deliver(self, user_id: str, message: dict) -> None:
        sockets = list(self.sockets.get(user_id, ()))
        results = await asyncio.gather(
            *(self._send(ws, message) for ws in sockets), return_exceptions=True
        )
        for ws, result in zip(sockets, results):
            if result is not True:
                self.remove(user_id, ws)

    async def _send(self, websocket: WebSocket, message: dict) -> bool:
        await asyncio.wait_for(websocket.send_json(message), self.send_timeout)
        return True
```

Три детали, без которых менеджер течёт или зависает:

- **Удаление в `finally`.** Клиент может уйти как угодно: закрыть вкладку (`WebSocketDisconnect`), потерять сеть, нарушить лимит. Если убирать соединение только в `except WebSocketDisconnect`, остальные выходы оставят в словаре мёртвые объекты. Пустой набор тоже удаляется, иначе словарь растёт на каждого когда-либо заходившего пользователя.
- **Копия набора перед рассылкой.** Пока `await` отправляет одной вкладке, другая может отключиться и изменить набор. Перебор живого `set` в этот момент падает с `RuntimeError: Set changed size during iteration`.
- **Таймаут и параллельная отправка.** `send_json` ждёт, пока данные уйдут в сокет. У клиента с плохой сетью буфер переполняется, и `await` повисает. Последовательная рассылка с таким клиентом в середине задержит всех после него. Поэтому отправка идёт через `gather`, каждая — с таймаутом, а не уложившиеся соединения выбрасываются: клиент переподключится и догрузит пропущенное.

Методы `receive_text`, `receive_json`, `receive_bytes` ждут сообщения от клиента, `send_text`, `send_json`, `send_bytes` — отправляют. Когда клиент закрыл соединение, `receive_*` бросает `WebSocketDisconnect` с кодом закрытия. Отключение замечается только на `receive_*` или на неудачной отправке, поэтому цикл чтения нужен, даже если клиент ничего не пишет.

### Аутентификация

В обычном API токен передают в заголовке `Authorization` (см. [авторизацию по JWT](auth_jwt.md)). Браузерный `new WebSocket(url)` не умеет ставить свои заголовки — у конструктора есть только адрес и список подпротоколов. `EventSource` тоже. Остаются три способа:

1. **Токен в адресе**: `/ws?token=...`. Просто, но адрес с токеном попадает в журналы nginx и в историю браузера. Смягчают коротким сроком жизни: клиент перед подключением получает одноразовый токен на 30–60 секунд обычным запросом с `Authorization`.
2. **Первое сообщение**: соединение открывается без токена, клиент первым делом отправляет `{"type": "auth", "token": "..."}`. Токен не попадает в журналы. Сервер должен ждать его ограниченное время, иначе неаутентифицированные соединения будут висеть бесконечно.
3. **Кука**: браузер сам отправит куку при рукопожатии. Удобно, если сайт и так работает на сессионных куках, но открывает дорогу CSWSH (о нём ниже).

В примере работают первые два: токен из адреса, а если его нет — из первого сообщения за `auth_timeout` секунд:

```python
# app/ws.py
async def authenticate(websocket: WebSocket, token: str | None, settings: Settings) -> str | None:
    if token is None:
        try:
            first = await asyncio.wait_for(websocket.receive_json(), settings.auth_timeout)
        except (TimeoutError, ValueError, KeyError):
            return None
        if not isinstance(first, dict) or first.get('type') != 'auth':
            return None
        token = first.get('token')
    return user_from_token(token, settings.jwt_secret)
```

Неверный токен — закрытие с кодом **1008** (policy violation). Важно, *когда* закрывать. Если вызвать `close` до `accept`, рукопожатие не состоится: клиент получит HTTP 403, а браузер покажет лишь код 1006 без причины. Если сначала `accept`, а потом `close(1008, reason=...)`, клиент увидит код и причину и сможет отличить «токен истёк, обнови» от «сеть пропала, переподключись»:

```text
# клиент на websockets: подключение с Origin: https://evil.example, затем без токена (ждёт auth_timeout)
InvalidStatus server rejected WebSocket connection: HTTP 403
ConnectionClosedError received 1008 (policy violation) invalid token; then sent 1008 (policy violation) invalid token
```

Токен проверяется один раз при подключении. Если соединение живёт дольше, чем токен, сервер должен либо закрывать его по истечении срока, либо принимать от клиента новый токен по тому же каналу.

**Проверка `Origin` (CSWSH).** Политика одного источника (same-origin policy) на WebSocket не распространяется: страница злоумышленника может открыть соединение к вашему серверу, и браузер приложит куки пользователя. Это называется cross-site WebSocket hijacking. Защита — сверять заголовок `Origin`, который браузер ставит сам и который скрипт подделать не может:

```python
origin = websocket.headers.get('origin')
if origin is not None and origin not in settings.allowed_origins:
    await websocket.close(code=status.WS_1008_POLICY_VIOLATION)  # до accept: HTTP 403
    return
```

Отсутствие `Origin` пропускается: его не присылают серверные клиенты, а им куки браузера всё равно недоступны. При токене в адресе или первом сообщении атака не работает и без проверки — у чужой страницы нет токена. Но проверка дешёвая и страхует, если кто-то позже добавит вход по куке.

### Несколько экземпляров: общая шина

Сервис запущен в двух экземплярах за балансировщиком. Анна подключилась к `app1`, а сервис задач отправил `POST /notify` на `app2`. Менеджер соединений у каждого процесса свой, и `app2` об Анне ничего не знает.

```text
Анна ──WS──► app1 ◄──┐
                     │ PUBLISH notifications
                Redis pub/sub
                     │
сервис задач ──POST /notify──► app2
```

Решение — общая шина событий. Каждый экземпляр при старте подписывается на канал Redis, а `POST /notify` публикует в него. Сообщение получают все экземпляры, и каждый доставляет его тем, кто подключён к нему:

```python
# app/bus.py (сокращённо)
async def listen(self) -> None:
    while True:
        try:
            async with self.redis.pubsub() as pubsub:
                await pubsub.subscribe(CHANNEL)
                self.ready.set()
                async for raw in pubsub.listen():
                    if raw['type'] != 'message':
                        continue
                    message = json.loads(raw['data'])
                    user_id = message.pop('user_id')
                    await self.manager.deliver(user_id, message)
        except asyncio.CancelledError:
            raise
        except Exception:
            logger.exception('Подписка на Redis оборвалась, переподключаемся')
            await asyncio.sleep(1)
```

Слушатель запускается в `lifespan` фоновой задачей. Приложение начинает принимать запросы только после `bus.ready`, иначе уведомление, отправленное сразу после старта, уйдёт в пустоту. Используется асинхронный клиент `redis.asyncio`: синхронный `redis.Redis` внутри `async def` остановил бы весь процесс.

Здесь один канал на всех: каждый экземпляр получает все уведомления и выбрасывает те, чьих получателей у него нет. Для тысяч событий в секунду это нормально. Когда событий больше, заводят канал на пользователя (`notifications:anna`) и подписываются на него при первом подключении пользователя к экземпляру, а отписываются при последнем отключении.

**Чем плох pub/sub.** Redis pub/sub ничего не хранит: сообщение получают те, кто подписан прямо сейчас. Анна закрыла ноутбук на минуту, экземпляр перезапустился, оборвалась подписка — уведомление потеряно навсегда. Поэтому шина отвечает только за мгновенную доставку, а источником правды служит хранилище. В примере — Redis Stream на пользователя: запись получает возрастающий идентификатор, и по нему легко выбрать всё, что новее:

```python
# app/bus.py
async def publish(self, user_id: str, event: str, data: dict) -> str:
    event_id = await self.redis.xadd(
        stream_key(user_id),
        {'event': event, 'data': json.dumps(data, ensure_ascii=False)},
        maxlen=self.maxlen,
        approximate=True,
    )
    message = {'user_id': user_id, 'id': event_id, 'event': event, 'data': data, 'from': self.instance}
    await self.redis.publish(CHANNEL, json.dumps(message, ensure_ascii=False))
    return event_id

async def missed(self, user_id: str, after_id: str, limit: int = 100) -> list[dict]:
    rows = await self.redis.xrange(stream_key(user_id), min=f'({after_id}', count=limit)
    return [
        {'id': row_id, 'event': fields['event'], 'data': json.loads(fields['data'])}
        for row_id, fields in rows
    ]
```

Порядок важен: сначала сохранить, потом опубликовать. Клиент запоминает `id` последнего полученного уведомления и при переподключении передаёт его (`/ws?last_id=...`, заголовок `Last-Event-ID` для SSE, `/poll?after=...`). Сервер сначала регистрирует соединение в менеджере и только потом читает историю: иначе событие, пришедшее между чтением истории и регистрацией, потеряется. Обратная сторона — одно и то же событие может прийти дважды (из истории и из шины), поэтому клиент или сервер отбрасывает повторы по `id`. `maxlen` ограничивает поток последними 1000 записями: кто отсутствовал дольше, загрузит остальное обычным запросом к API.

В настоящем сервисе уведомления обычно лежат в основной базе (таблица `notifications` с флагом «прочитано»), а Redis Stream или Kafka служат буфером. Модель «сначала база, потом шина» подробнее разобрана в [разборе чата](../../design/chat.md#4-путь-сообщения).

### SSE в FastAPI

В свежих версиях FastAPI (в примере 0.143) есть встроенный SSE: `response_class=EventSourceResponse` и генератор, который отдаёт `ServerSentEvent`. FastAPI сам кодирует события в формат потока, раз в 15 секунд простоя вставляет комментарий-пинг и ставит заголовки `Cache-Control: no-cache` и `X-Accel-Buffering: no` (последний просит nginx не буферизовать ответ). Поэтому в примере нет ни ручного `StreamingResponse`, ни пакета `sse-starlette`: на версиях без `fastapi.sse` выбор был бы между ними, и `sse-starlette` удобнее тем, что пинги и отключение клиента он уже обрабатывает.

```python
# app/sse.py (сокращённо)
@router.get('/events', response_class=EventSourceResponse)
async def notifications_sse(
    request: Request,
    user_id: UserId,
    last_event_id: Annotated[str | None, Header()] = None,
) -> AsyncIterable[ServerSentEvent]:
    manager = request.app.state.manager
    queue = manager.listen(user_id)
    try:
        yield ServerSentEvent(comment='connected', retry=3000)
        sent = last_event_id
        if last_event_id:
            for item in await request.app.state.bus.missed(user_id, last_event_id):
                yield to_event(item)
                sent = item['id']
        while True:
            try:
                item = await asyncio.wait_for(queue.get(), timeout=5)
            except TimeoutError:
                if await request.is_disconnected():
                    break
                continue
            if item is None:
                break
            if is_newer(item['id'], sent):
                yield to_event(item)
                sent = item['id']
    finally:
        manager.unlisten(user_id, queue)
```

`UserId` — зависимость, которая берёт токен из адреса и отвечает 401 до начала потока. Ошибку нужно выдать именно в зависимости: после первого `yield` заголовки уже ушли со статусом 200, и поменять его нельзя.

Вот что видит клиент — каждое событие состоит из строк `поле: значение` и заканчивается пустой строкой. Строка, начинающаяся с `:`, — комментарий, браузер его игнорирует, а прокси видит, что соединение живое. `retry:` говорит браузеру, через сколько миллисекунд переподключаться:

```text
$ curl -sN -D - --max-time 17 "localhost:41801/events?token=$TOKEN"   # уведомления отправлены через :41802
HTTP/1.1 200 OK
date: Thu, 29 Oct 2026 09:58:21 GMT
server: uvicorn
content-type: text/event-stream; charset=utf-8
cache-control: no-cache
x-accel-buffering: no
transfer-encoding: chunked

: connected
retry: 3000

event: task_assigned
data: {"task_id": 42, "title": "Подготовить отчёт"}
id: 1793267902435-0

event: comment_added
data: {"task_id": 42, "author": "boris", "text": "Добавил цифры за сентябрь"}
id: 1793267902474-0

: ping
```

`event:` задаёт тип: в браузере на него подписываются через `source.addEventListener('task_assigned', ...)`. Без `event:` событие приходит в `onmessage`. `data` в примере передаётся через `raw_data=json.dumps(..., ensure_ascii=False)`: обычный `data=` тоже кодирует в JSON, но экранирует кириллицу в `П...`, и поток раздувается в несколько раз.

**Отключение клиента.** Генератор ждёт очередь и сам не узнает, что клиент закрыл вкладку. Под uvicorn Starlette слушает отключение и отменяет генератор — срабатывает `finally`. `request.is_disconnected()` в цикле — страховка для серверов и промежуточного ПО, где этого не происходит: раз в 5 секунд простоя генератор сам проверяет, жив ли клиент. Проверка в тесте: после закрытия потока на экземпляре не остаётся слушателей.

**Медленный клиент.** Очередь у каждого слушателя ограничена (`maxsize=100`). Если клиент не успевает читать и очередь переполнилась, менеджер кладёт в неё `None`, поток завершается, а браузер переподключится с `Last-Event-ID` и заберёт пропущенное из хранилища. Неограниченная очередь вместо этого копила бы события в памяти сервера.

Переподключение с догрузкой из теста: первое событие получено на `app1`, затем поток закрыт, пришли два уведомления, и клиент подключился уже к `app2` с `Last-Event-ID`:

```text
tests/integration/test_cluster.py::test_sse_catches_up_with_last_event_id
первое событие: {'event': 'comment_added', 'data': {'task_id': 7, 'text': 'Первый комментарий'}, 'id': '1793268018613-0'}
после переподключения: [{'event': 'comment_added', 'data': {'task_id': 7, 'text': 'Пока не было: 1'}, 'id': '1793268018621-0'}, {'event': 'comment_added', 'data': {'task_id': 7, 'text': 'Пока не было: 2'}, 'id': '1793268018631-0'}]
PASSED
```

Long polling (`/poll?after=...&timeout=25`) устроен так же, только вместо потока отдаёт одно событие или пустой список по таймауту, после чего клиент сразу спрашивает снова с `after` = последний `id`.

### Живость соединения

Соединение может умереть молча: ноутбук ушёл в сон, мобильная сеть сменила адрес, NAT-маршрутизатор забыл о простаивающем соединении. TCP об этом не узнает часами. Поэтому стороны периодически обмениваются пингами.

**Ping/pong в протоколе.** В WebSocket есть служебные кадры ping и pong. Браузер отвечает на ping сам, JavaScript их не видит. uvicorn шлёт ping каждые `--ws-ping-interval` секунд (по умолчанию 20) и закрывает соединение, если pong не пришёл за `--ws-ping-timeout`. Код в приложении для этого не нужен. Пинг на уровне приложения (`{"type": "ping"}` → `{"type": "pong"}`) нужен клиенту: браузер не может отправить протокольный ping и не узнает, что соединение умерло, пока не попробует что-то отправить.

**Таймауты прокси.** nginx по умолчанию закрывает проксируемое соединение, если 60 секунд (`proxy_read_timeout`) от сервера ничего не приходило. Пинги каждые 20 секунд (WebSocket) или 15 секунд (комментарий SSE) держат его открытым. Для WebSocket nginx должен передать заголовки `Upgrade` и `Connection` — сам он их не проксирует, потому что они относятся к одному «прыжку», а не ко всему пути:

```nginx
# nginx/default.conf (фрагмент)
location /ws {
    proxy_pass http://notifications;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection $connection_upgrade;
    proxy_read_timeout 75s;
}

location /events {
    proxy_pass http://notifications;
    proxy_http_version 1.1;
    proxy_set_header Connection '';
    proxy_buffering off;
    proxy_read_timeout 75s;
}
```

`$connection_upgrade` и остальные настройки — в заметке [Reverse proxy](../../web/nginx/reverse_proxy.md#websocket). Для SSE главное — `proxy_buffering off`: иначе nginx копит ответ в буфере, и события приходят пачками с задержкой. Через этот конфиг в примере проходит отдельный тест:

```text
tests/integration/test_cluster.py::test_through_nginx
через nginx: WebSocket на app1, SSE получил {'event': 'task_assigned', 'data': {'task_id': 9}, 'id': '1793268019649-0'}
PASSED
```

Липкие сессии (`ip_hash`) для WebSocket не нужны: соединение одно и живёт на одном экземпляре, пока не оборвётся. После обрыва клиент может попасть на другой экземпляр — с общей шиной и хранилищем это не важно.

**Переподключение клиента.** Если сервер перезапустился, все его клиенты отключились одновременно. Переподключись они сразу и одновременно, новый экземпляр получит тысячи рукопожатий за секунду. Поэтому пауза растёт после каждой неудачи (1, 2, 4, 8 секунд, но не больше 30) и к ней добавляется случайный разброс (jitter), чтобы клиенты не приходили волнами. Браузерный `EventSource` переподключается сам через `retry`, но без разброса; для WebSocket цикл пишут вручную — пример в [заметке про WebSocket в браузере](../../../languages/javascript/websocket.md). Если сервер закрыл соединение с кодом 1008, переподключаться с тем же токеном бессмысленно: сначала нужен новый токен.

### Защита от флуда

Открытое соединение — это канал, по которому клиент может слать что угодно и сколько угодно. Обычный rate limit на балансировщике считает HTTP-запросы и внутрь WebSocket не заглядывает. Поэтому лимиты ставят на само соединение.

**Частота.** У каждого соединения своя корзина с токенами (token bucket, подробнее — в [ограничении частоты запросов](../../design/rate_limiting.md#корзина-с-токенами-token-bucket)): 5 сообщений в секунду с запасом 10 на всплеск. Корзина живёт в памяти процесса, Redis не нужен: соединение целиком обслуживает один экземпляр.

```python
limiter = TokenBucket(settings.messages_per_second, settings.messages_burst)
while True:
    text = await websocket.receive_text()
    if len(text.encode()) > settings.max_message_bytes:
        await websocket.close(code=status.WS_1009_MESSAGE_TOO_BIG, reason='message too big')
        break
    if not limiter.allow():
        await websocket.close(code=status.WS_1008_POLICY_VIOLATION, reason='too many messages')
        break
    await handle(websocket, text)
```

```text
tests/integration/test_cluster.py::test_flood_client_is_disconnected
отправлено 11 сообщений, код закрытия: 1008, причина: too many messages
PASSED
```

**Размер.** Проверка длины в коде срабатывает, когда сообщение уже собрано в памяти. Поэтому есть ещё лимит уровня протокола: `uvicorn --ws-max-size 65536` закрывает соединение с кодом 1009, не дочитав огромный кадр. По умолчанию он 16 МиБ — сотня клиентов с такими сообщениями съест 1,6 ГиБ. Число соединений на одного пользователя тоже стоит ограничить: иначе один токен откроет десять тысяч вкладок.

### Масштаб

Каждое открытое соединение — это файловый дескриптор (сокет), буферы чтения и записи и асинхронная задача, которая ждёт в `receive_text`. Ожидание ничего не стоит процессору: event loop спит в `epoll`, пока не придут данные. Поэтому один процесс держит тысячи соединений — в отличие от модели «поток на соединение», где каждый поток занимает свой стек.

Замер на примере: 2000 клиентов подключены к `app1`, каждому отправлено уведомление через `app2`.

```text
$ docker stats --no-stream --format '{{.Name}} {{.MemUsage}} {{.PIDs}}' kb-ws-app1-1   # до подключения
kb-ws-app1-1 45.54MiB / 3.825GiB 6
$ python -m scripts.many_clients 2000 8   # пока соединения открыты:
$ docker stats --no-stream --format '{{.Name}} {{.MemUsage}} {{.PIDs}}' kb-ws-app1-1
kb-ws-app1-1 187.9MiB / 3.825GiB 6
$ docker exec kb-ws-app1-1 sh -c 'ls /proc/1/fd | wc -l'
2016
# вывод скрипта:
подключено: 2000
доставлено: 2000 за 9.9 с
```

Около 70 КиБ на соединение и по дескриптору на каждое, а процессов и потоков столько же, сколько без клиентов. Время доставки здесь — это 2000 последовательных `POST /notify` из скрипта, а не задержка самой рассылки. На практике упираются в лимит дескрипторов (`ulimit -n`, у контейнера обычно большой, у процесса на хосте бывает 1024) и в память, а не в процессор.

Обратная сторона: все эти соединения обслуживает **один** поток. Блокирующий вызов в любом обработчике — `time.sleep`, синхронный `requests.get`, синхронный клиент базы, тяжёлый расчёт — останавливает event loop, и на это время замирают все тысячи соединений: не уходят уведомления, не отвечают пинги, и uvicorn может начать закрывать соединения по `ws-ping-timeout`. Почему так происходит — в [заметке о многозадачности](../../../languages/python/concurrency/README.md#асинхронные-веб-фреймворки). Блокирующий код выносят в `asyncio.to_thread` или в отдельный сервис.

Несколько воркеров uvicorn (`--workers 4`) — это несколько независимых процессов со своими менеджерами соединений, то есть те же «несколько экземпляров». Шина нужна и тут.

## Частые ошибки

- **Менеджер соединений в памяти при нескольких экземплярах.** Локально всё работает, а в продакшене уведомления доходят через раз — к тому экземпляру, куда случайно попал `POST`. Нужна общая шина (Redis pub/sub, NATS) между экземплярами.
- **Только pub/sub, без хранения.** Пользователь без сети или в момент перезапуска сервиса теряет уведомления насовсем. Сохраняйте события и догружайте пропущенное по последнему `id`.
- **Соединение убирается только в `except WebSocketDisconnect`.** Закрытие по лимиту, ошибка в обработчике или таймаут оставляют мёртвые соединения в менеджере, и память растёт. Убирайте в `finally`.
- **Рассылка по очереди без таймаута.** Один клиент с плохой сетью задерживает доставку всем, кто идёт после него. Отправляйте параллельно и с таймаутом.
- **`close` до `accept` при неверном токене.** Клиент получает HTTP 403, браузер видит 1006 и бесконечно переподключается. Принимайте соединение и закрывайте с 1008 и причиной.
- **Токен в адресе без короткого срока жизни.** Долгоживущий токен оседает в журналах прокси. Выдавайте одноразовый токен для подключения или передавайте токен первым сообщением.
- **SSE за nginx с буферизацией.** События приходят пачками раз в несколько секунд или только при закрытии потока. Нужны `proxy_buffering off` или заголовок `X-Accel-Buffering: no`.
- **Нет пингов.** Соединение молча закрывает прокси через 60 секунд простоя, а клиент считает, что подключён. Пинг чаще, чем таймаут самого короткого звена.
- **SSE по HTTP/1.1 в нескольких вкладках.** Браузер держит не больше 6 соединений на домен по HTTP/1.1, и седьмая вкладка с `EventSource` зависает вместе с остальными запросами к сайту. Включайте HTTP/2 на балансировщике или держите один поток на браузер (через `SharedWorker`).
- **Синхронный вызов в обработчике.** Под нагрузкой замирают все соединения процесса разом, хотя процессор почти свободен.

## Когда не использовать

Если обновления редкие и минутная задержка не страшна — счётчик непрочитанных, статус сборки — хватит обычного опроса раз в 30–60 секунд: ни шины, ни долгих соединений, ни настройки прокси. Если уведомление должно дойти до пользователя, у которого сайт закрыт, WebSocket и SSE не помогут: это задача email, push-уведомлений через сервисы браузера и мобильных платформ или SMS. Для тысяч соединений с комнатами, историей и готовыми клиентами под все платформы проще взять готовый сервер соединений (Centrifugo, Mercure, облачные сервисы) и отправлять ему события из FastAPI по HTTP, чем развивать свой.
