# Память в Python: ссылки, сборщик мусора, `__slots__`

В Python не нужно вручную освобождать память, и обычно о ней можно не думать. Но однажды сервис начинает потреблять всё больше памяти, кэш не очищается или миллион маленьких объектов съедает гигабайт. Тогда полезно понимать, как Python решает, что объект больше не нужен.

Краткое введение есть в [заметках про память](../basics/memory.md) и [про интерпретатор и сборщик мусора](../basics/interpreter.md). Здесь — подробнее и с практикой.

## Минимальный пример

```python run
import sys

tasks = ['Купить хлеб']
print(sys.getrefcount(tasks))  # 2

same = tasks
print(sys.getrefcount(tasks))  # 3

del same
print(sys.getrefcount(tasks))  # 2
```

У каждого объекта есть счётчик ссылок: сколько переменных, списков и атрибутов на него указывают. `getrefcount` показывает на одну ссылку больше, чем кажется: временную ссылку создаёт сам вызов функции.

## Как это работает

**Подсчёт ссылок — основной механизм.** Присвоили объект переменной — счётчик +1. Переменная исчезла (`del`, выход из функции, новое значение) — счётчик −1. Как только счётчик стал нулём, объект удаляется **сразу**. Поэтому файл, открытый внутри функции, обычно закрывается уже при выходе из неё.

`del x` удаляет не объект, а имя `x`. Объект исчезнет, только если на него больше никто не ссылается.

**Сборщик мусора — для циклов.** Подсчёт ссылок не справляется, если объекты ссылаются друг на друга:

```python
import gc


class Node:
    def __init__(self, name):
        self.name = name
        self.other = None

    def __del__(self):
        print('удалён', self.name)


gc.disable()  # выключаем сборщик, чтобы увидеть проблему

a, b = Node('a'), Node('b')
a.other, b.other = b, a  # цикл: a → b → a
del a, b
print('после del ничего не удалено')

gc.collect()
# удалён a
# удалён b
```

После `del` у каждого узла остаётся по одной ссылке — друг от друга, поэтому счётчики не обнулились. Сборщик мусора (модуль `gc`) периодически ищет такие группы объектов, недостижимые из программы, и удаляет их. Объекты он делит на поколения: новые проверяет часто, а пережившие несколько проверок — редко, ведь долгоживущие объекты обычно и дальше нужны.

Сборщик включён по умолчанию, вызывать его вручную почти никогда не нужно.

### Слабые ссылки: кэш, который не держит объекты

Обычный словарь-кэш держит объекты вечно: пока объект лежит в кэше, его счётчик не обнулится. Слабая ссылка (`weakref`) указывает на объект, но не увеличивает счётчик:

```python
import weakref


class Task:
    def __init__(self, title):
        self.title = title


cache = weakref.WeakValueDictionary()

task = Task('Отчёт')
cache[1] = task
print(cache.get(1).title)  # Отчёт

del task
print(cache.get(1))  # None — объект удалён, и кэш забыл его сам
```

### `__slots__`: меньше памяти на каждый объект

Обычно атрибуты объекта хранятся в отдельном словаре `__dict__`. `__slots__` заранее перечисляет атрибуты, и Python хранит их компактнее. На миллионах маленьких объектов это заметно:

```python
import tracemalloc


class WithDict:
    def __init__(self, x, y):
        self.x, self.y = x, y


class WithSlots:
    __slots__ = ('x', 'y')

    def __init__(self, x, y):
        self.x, self.y = x, y


for cls in (WithDict, WithSlots):
    tracemalloc.start()
    objects = [cls(i, i) for i in range(100_000)]
    current, _ = tracemalloc.get_traced_memory()
    tracemalloc.stop()
    print(cls.__name__, round(current / 1024 / 1024, 1), 'МБ')

# WithDict 11.4 МБ
# WithSlots 8.4 МБ
```

Цифры получены на Python 3.12; в новых версиях обычные объекты тоже стали компактнее, поэтому разница меньше, чем в старых статьях. Цена `__slots__`: нельзя добавить атрибут, которого нет в списке. В dataclass то же самое включается флагом [`slots=True`](../typing/dataclasses.md).

### Как найти, что съедает память

**`sys.getsizeof`** показывает размер самого объекта, но не того, на что он ссылается:

```python
sys.getsizeof([1, 2, 3])        # 88
sys.getsizeof([[1] * 1000])     # 64 — вложенный список на 1000 элементов не учтён
```

**Генератор вместо списка**, если значения нужны по одному:

```python
sys.getsizeof([i * i for i in range(1_000_000)])  # 8448728 — около 8 МБ
sys.getsizeof((i * i for i in range(1_000_000)))  # 200 — значения считаются на лету
```

**`tracemalloc`** показывает, какие строки кода выделили больше всего памяти:

```python
import tracemalloc

tracemalloc.start()
# ... код, который подозреваем ...
for stat in tracemalloc.take_snapshot().statistics('lineno')[:5]:
    print(stat)
```

## Частые ошибки

- **Кэш без ограничения.** Глобальный словарь, в который только добавляют, — самая частая «утечка» в Python. Ограничьте размер (`functools.lru_cache(maxsize=...)`) или используйте слабые ссылки.
- **`is` вместо `==`.** `is` сравнивает объекты, а не значения. `256 is int('256')` — `True`, а `257 is int('257')` — `False`: маленькие числа CPython хранит заранее и переиспользует. Для сравнения значений всегда `==`; `is` — только для `None`.
- **Надежда на `__del__`.** Когда именно он вызовется, не гарантируется. Для освобождения ресурсов используйте `with` и контекстные менеджеры.

## Когда не использовать

`__slots__`, слабые ссылки и ручная настройка `gc` — инструменты для случаев, когда память уже измерена и проблема найдена. В обычном скрипте или веб-обработчике, который создаёт тысячи объектов, а не миллионы, они только усложняют код: `__slots__` мешает добавлять атрибуты и ломает `__dict__`, а `weakref` возвращает `None` в самый неожиданный момент. Сначала `tracemalloc`, потом оптимизация.

Для больших массивов чисел экономить на объектах тоже бессмысленно: сто тысяч экземпляров класса с полями `x` и `y` всё равно займут в десятки раз больше, чем `array` или NumPy-массив той же длины. Вызывать `gc.collect()` вручную нужно разве что в тестах на утечки: в рабочем коде сборщик справляется сам, а принудительный вызов лишь добавляет паузы.
