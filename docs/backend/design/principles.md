# Принципы проектирования: SOLID, DRY, KISS, YAGNI

Код, который легко написать, не всегда легко менять. Через полгода выясняется, что ради нового способа уведомлений нужно править класс отчёта, а для теста — настоящий почтовый сервер. Принципы проектирования — это сжатый опыт того, как избегать таких ловушек. Это не законы: каждый принцип полезен, пока помогает менять код, и вреден, когда применяется ради галочки.

## Минимальный пример

Отчёт по задачам, разделённый по ответственности: подсчёт отдельно, канал отправки — за интерфейсом, а в тесте вместо почты передаётся подделка.

```python run
from dataclasses import dataclass
from typing import Protocol


@dataclass
class Task:
    title: str
    done: bool = False


def build_report(tasks: list[Task]) -> str:  # считает и ничего не отправляет
    done = sum(task.done for task in tasks)
    return f'Выполнено {done} из {len(tasks)}'


class Notifier(Protocol):  # от канала нужен только send
    def send(self, text: str) -> None: ...


class EmailNotifier:
    def send(self, text: str) -> None:
        print('Письмо:', text)


class FakeNotifier:  # подделка для теста
    def __init__(self):
        self.sent = []

    def send(self, text: str) -> None:
        self.sent.append(text)


def send_daily_report(tasks: list[Task], notifier: Notifier) -> None:
    notifier.send(build_report(tasks))


tasks = [Task('Сдать отчёт', done=True), Task('Купить хлеб')]
send_daily_report(tasks, EmailNotifier())  # Письмо: Выполнено 1 из 2

fake = FakeNotifier()
send_daily_report(tasks, fake)
print(fake.sent)  # ['Выполнено 1 из 2']
```

Новый канал — это новый класс с методом `send`, например `TelegramNotifier`; функция `send_daily_report` при этом не меняется.

## Как это работает

Для сравнения — тот же отчёт классом, который делает всё сразу:

```python
class TaskReport:
    def __init__(self, tasks):
        self.tasks = tasks

    def build(self):
        done = sum(task.done for task in self.tasks)
        text = f'Выполнено {done} из {len(self.tasks)}'
        with open('report.txt', 'w', encoding='utf-8') as f:
            f.write(text)
        print(f'Отправляем письмо: {text}')
```

Чтобы поменять формат, сохранить отчёт в S3 или отправить в Telegram, придётся править этот класс. Протестировать подсчёт без записи в файл и отправки письма нельзя. В минимальном примере подсчёт, сохранение и отправка разделены, поэтому каждую часть можно менять и проверять отдельно.

### SOLID

**S — единственная ответственность** (Single Responsibility). У модуля должна быть одна причина для изменения. В примере выше подсчёт, сохранение и отправка меняются по разным причинам, поэтому разделены.

**O — открытость для расширения, закрытость для изменения** (Open/Closed). Новое поведение добавляется новым кодом, а не правкой старого. Новый канал уведомлений — это новый класс с методом `send`, а `send_daily_report` при этом не меняется.

**L — подстановка Лисков** (Liskov Substitution). Наследник должен работать везде, где работает родитель. Плохой пример:

```python
class Storage:
    def save(self, key: str, value: str) -> None: ...


class ReadOnlyStorage(Storage):
    def save(self, key, value):
        raise PermissionError('только для чтения')


def backup(storage: Storage):
    storage.save('backup', 'данные')


backup(ReadOnlyStorage())  # PermissionError: только для чтения
```

Формально `ReadOnlyStorage` — это `Storage`, но код, который рассчитывает на `Storage`, с ним ломается. Значит, наследование здесь неверное: «только для чтения» — не разновидность «хранилища с записью».

**I — разделение интерфейсов** (Interface Segregation). Лучше несколько маленьких интерфейсов, чем один большой. `Notifier` требует только `send`. Если бы он требовал ещё `send_file`, `get_history` и `delete`, каждому новому каналу пришлось бы реализовывать то, что ему не нужно.

**D — инверсия зависимостей** (Dependency Inversion). Код верхнего уровня зависит от абстракции (`Notifier`), а не от конкретной реализации (`EmailNotifier`). Конкретную реализацию передают снаружи. В FastAPI это делают [зависимости](../frameworks/fastapi/dependencies.md): эндпоинт получает сессию БД, не зная, откуда она взялась, и тест подменяет её через `dependency_overrides`.

### DRY, KISS, YAGNI

**DRY — не повторяйся** (Don't Repeat Yourself). Одно знание — в одном месте. Если правило «название задачи от 1 до 200 символов» записано в схеме API, в модели и во фронтенде, однажды его поменяют в двух местах из трёх.

Но DRY касается **знаний**, а не похожих строк. Два куска кода, которые сегодня совпадают, но меняются по разным причинам, лучше не объединять: иначе общая функция обрастает флагами `if is_admin and not legacy_mode`.

**KISS — делай проще** (Keep It Simple, Stupid). Из двух решений, которые решают задачу, выбирайте то, которое поймёт коллега без объяснений. Словарь вместо иерархии из пяти классов, функция вместо паттерна «Стратегия» с фабрикой.

**YAGNI — тебе это не понадобится** (You Aren't Gonna Need It). Не пишите код «на будущее»: поддержку пяти баз данных, когда используется одна, или плагинную систему для двух отчётов. Будущее обычно оказывается другим, а неиспользуемый код всё равно приходится поддерживать.

Принципы иногда спорят друг с другом. SOLID подталкивает выделять абстракции, а KISS и YAGNI — их не вводить, пока нет реальной необходимости. Хороший ориентир: абстракцию выделяют, когда появилась **вторая** реализация или когда без неё не получается написать тест.

## Частые ошибки

- Интерфейс с одной реализацией «по SOLID» → пока уведомления только по почте, `Notifier`, `NotifierFactory` и `NotifierRegistry` только добавляют прыжки по коду → оставить функцию, а абстракцию выделить, когда появится вторая реализация или тест.
- Наследование ради повторного использования кода → наследник не может честно заменить родителя (пример со `Storage`), и код, рассчитанный на родителя, падает → использовать композицию: передать нужный объект внутрь.
- Объединение похожего, но разного кода → сегодня проверка пароля и проверка промокода похожи, через месяц у них разные правила, и общая функция превращается в клубок условий → объединять только общее знание, а не совпадающие строки.
- Принципы как цель → в код-ревью спорят о «соблюдении SOLID», а код не стал проще читать и менять → мерить принципы пользой: легко ли читать, тестировать и менять.

## Когда не использовать

В скрипте на пятьдесят строк, прототипе или одноразовой миграции абстракции по SOLID лишние: протокол, фабрика и подмена в тестах стоят больше, чем сам код. Там работают KISS и YAGNI: одна функция, которая решает задачу, и никакой подготовки к будущему, которое может не наступить.

Не стоит и выделять интерфейс «про запас», пока реализация одна и тесты обходятся без подмены. Начинайте с простого кода, а принципы применяйте в момент, когда изменение стало болезненным: появилась вторая реализация, тест требует настоящего сервиса, правка расползается по нескольким местам.
