# Метрики качества

«Модель хорошая» — это не ответ. Хорошая по какому критерию? Модель цены квартиры может в среднем ошибаться на миллион и при этом иногда промахиваться на десять. Модель, которая ищет дорогие квартиры, может быть права в 91% случаев и не найти ни одной. Метрика — это способ превратить «хорошо или плохо» в число, и выбирать её нужно по тому, какие ошибки обходятся дороже.

Данные и модели — из заметки [Первая модель](first_model.md).

## Минимальный пример

Ловушка точности. Попробуем найти дорогие квартиры: дороже 20 млн ₽. Таких в наборе 8,6%. Сравним модель с «моделью», которая всегда отвечает «не дорогая»:

```python
from sklearn.dummy import DummyClassifier
from sklearn.metrics import accuracy_score, recall_score

df['expensive'] = (df['price'] > 20_000_000).astype(int)

always_no = DummyClassifier(strategy='most_frequent').fit(X_train, y_train)
accuracy_score(y_test, always_no.predict(X_test))  # 0.915
recall_score(y_test, always_no.predict(X_test))    # 0.0
```

Доля правильных ответов (accuracy) — 91,5%, хотя модель не нашла **ни одной** дорогой квартиры. Когда один класс встречается редко (дорогие квартиры, мошеннические платежи, болезни), accuracy почти ничего не говорит.

## Как это работает

### Классификация

Настоящая модель на тех же данных:

```python
from sklearn.ensemble import HistGradientBoostingClassifier
from sklearn.metrics import confusion_matrix, f1_score, precision_score

clf = make_pipeline(preprocess, HistGradientBoostingClassifier(random_state=42)).fit(X_train, y_train)
predicted = clf.predict(X_test)

confusion_matrix(y_test, predicted)
# [[357   8]
#  [  7  27]]
```

**Матрица ошибок** показывает, как именно модель ошибается:

| | предсказано «не дорогая» | предсказано «дорогая» |
|---|---|---|
| **на самом деле не дорогая** | 357 — верно | 8 — ложная тревога |
| **на самом деле дорогая** | 7 — пропуск | 27 — верно |

Из неё считаются главные метрики:

- **precision (точность)** — из того, что модель назвала дорогим, какая доля действительно дорогая: 27 / (27 + 8) = **0,771**. Важна, когда ложная тревога дорого стоит: блокировка честного платежа;
- **recall (полнота)** — какую долю всех дорогих квартир модель нашла: 27 / (27 + 7) = **0,794**. Важна, когда пропуск дорого стоит: пропущенная болезнь или мошенничество;
- **F1** — среднее гармоническое precision и recall: **0,783**. Одно число, когда важно и то и другое.

**Порог.** Модель выдаёт вероятность, а «дорогая» — это вероятность выше 0,5. Порог можно двигать:

```python
proba = clf.predict_proba(X_test)[:, 1]

# порог 0.2: precision 0.725, recall 0.853 — находим больше, но чаще ошибаемся
# порог 0.5: precision 0.771, recall 0.794
# порог 0.8: precision 0.880, recall 0.647 — ошибаемся реже, но многое пропускаем
```

Precision и recall почти всегда тянут в разные стороны. Порог выбирают из того, что важнее бизнесу.

**ROC AUC** оценивает модель сразу по всем порогам: насколько хорошо она ставит дорогие квартиры выше недорогих. 0,5 — случайное угадывание, 1,0 — идеал. Здесь — **0,986**.

```python
from sklearn.metrics import roc_auc_score

roc_auc_score(y_test, proba)  # 0.986
```

### Регрессия

Для числовых предсказаний:

- **MAE** — средняя абсолютная ошибка в единицах цели: «в среднем ошибаемся на 932 тысячи рублей». Самая понятная;
- **MAPE** — средняя ошибка в процентах: 7,5%. Удобна, когда цены сильно различаются, но ломается, если среди настоящих значений есть нули;
- **RMSE** — корень из средней квадратичной ошибки. Сильнее штрафует **большие** промахи;
- **R²** — доля разброса цен, которую объясняет модель: 1 — идеально, 0 — не лучше среднего, ниже нуля — хуже среднего.

Разница между MAE и RMSE на двух прогнозах для пяти квартир:

```python
# ошибается на 1 млн в каждой квартире:  MAE 1.0 млн, RMSE 1.0 млн
# угадывает четыре, в одной мимо на 5 млн: MAE 1.0 млн, RMSE 2.24 млн
```

MAE у них одинаковый, а RMSE показывает, что во втором случае есть крупная ошибка. Если большой промах особенно неприятен (оценка залога для кредита), смотрите на RMSE.

## Частые ошибки

- Accuracy на несбалансированных данных → 91,5% у модели, которая не нашла ни одной дорогой квартиры → смотреть на precision, recall, F1 и матрицу ошибок, сравнивать с `DummyClassifier`.
- Одна метрика на всё → модель с лучшей F1 оказывается хуже по тому, что действительно важно бизнесу → договориться о главной метрике заранее, исходя из цены ошибок.
- Метрика на обучающих данных → высокие цифры, которые не повторяются на новых данных: это проверка памяти, а не умения обобщать → считать метрики на отложенной выборке, подробнее — в заметке про [переобучение](overfitting.md).
- Без стратификации → редкий класс случайно почти не попал в тестовую выборку, и метрики скачут от запуска к запуску → для классификации делить с `train_test_split(..., stratify=y)`.
- MAPE при нулевых значениях → деление на ноль даёт огромные или бесконечные ошибки → брать MAE или RMSE, либо считать MAPE только по ненулевым значениям.

## Когда не использовать

Метрики из этой заметки измеряют модель на отложенной выборке и ничего не говорят о том, что произойдёт в продукте. Если решение влияет на поведение пользователей (рекомендации, цены, ранжирование), офлайн-метрика — только фильтр кандидатов, а выбирать нужно по бизнес-метрике на A/B-тесте: выручке, конверсии, доле возвратов.

Не стоит подбирать метрику ради красивой цифры: accuracy на сбалансированных классах — нормальный выбор, а на редком классе она вводит в заблуждение. Если цена ложной тревоги и пропуска известна в деньгах, честнее считать ожидаемые потери напрямую, чем спорить о F1.
