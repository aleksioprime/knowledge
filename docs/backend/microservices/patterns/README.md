# Паттерны микросервисной архитектуры

«Задачник» вырос: комментарии пишут чаще, чем создают задачи, уведомления рассылаются тысячами, и над кодом работают уже три команды. Появилась идея вынести комментарии и уведомления в отдельные сервисы. Сразу возникают вопросы: стоит ли вообще дробить, по каким границам резать, как переехать, не переписывая всё, где хранить данные и как сервисы найдут друг друга. Паттерны ниже — проверенные ответы на эти вопросы. Что такое микросервисы и их общие плюсы и минусы — в [обзоре раздела](../README.md).

Пример — в папке [examples](examples/README.md): переезд комментариев из монолита в новый сервис через шлюз и скрипт с CQRS и Event Sourcing на SQLite.

## Минимальный пример: душитель

Монолит отдаёт задачи и комментарии. Рядом запущен новый сервис комментариев, а перед ними — шлюз Traefik. Пока все пути ведут в монолит:

```yaml
# example/routes/dynamic.yml
http:
  routers:
    comments:
      rule: "PathRegexp(`^/api/tasks/[0-9]+/comments`)"
      service: monolith  # переключатель: monolith → comments
    everything-else:
      rule: "PathPrefix(`/`)"
      service: monolith
```

```bash
cd example
docker compose -p kb-patterns up -d --build
./check.sh
```

```text
$ http://localhost:47080/api/tasks/1
HTTP/1.1 200 OK
X-Served-By: monolith
{"id":1,"ttl":"Сдать отчёт","st":1,"usr_id":10}

$ http://localhost:47080/api/tasks/1/comments
HTTP/1.1 200 OK
X-Served-By: monolith
[{"cid":100,"tsk":1,"usr_id":11,"txt":"Когда дедлайн?","ts":1761728400},{"cid":101,"tsk":1,"usr_id":10,"txt":"В пятницу","ts":1761732000}]
```

Меняем одну строку — `service: comments` в роутере `comments`. Traefik следит за папкой с маршрутами и подхватывает правку без перезапуска:

```text
$ http://localhost:47080/api/tasks/1
HTTP/1.1 200 OK
X-Served-By: monolith
{"id":1,"ttl":"Сдать отчёт","st":1,"usr_id":10}

$ http://localhost:47080/api/tasks/1/comments
HTTP/1.1 200 OK
X-Served-By: comments
{"task":{"id":1,"title":"Сдать отчёт","status":"in_progress"},"comments":[{"id":"legacy-100","task_id":1,"author_id":11,"text":"Когда дедлайн?","created_at":"2025-10-29T09:00:00Z"},{"id":"legacy-101","task_id":1,"author_id":10,"text":"В пятницу","created_at":"2025-10-29T10:00:00Z"}]}
```

Задачи по-прежнему отдаёт монолит, а комментарии — новый сервис. Клиент этого не заметил: адрес тот же. Старые комментарии новый сервис прочитал из монолита и перевёл в свою модель: `txt` стал `text`, `usr_id` — `author_id`, время из числа секунд стало датой, а статус задачи `1` — строкой `in_progress`. Новый комментарий сохраняется уже только в новом сервисе:

```bash
curl -s -X POST localhost:47080/api/tasks/1/comments \
  -H 'Content-Type: application/json' -d '{"author_id": 11, "text": "Успею к четвергу"}'
```

```text
HTTP/1.1 201 Created
X-Served-By: comments
{"id":"12aaa0d1-6126-4b51-b25e-360f74d37d07","task_id":1,"author_id":11,"text":"Успею к четвергу","created_at":"2026-10-29T10:27:01.835287Z"}
```

Откат — та же строка обратно, и комментарии снова отдаёт монолит. Но комментария «Успею к четвергу» он не знает: всё, что записано после переключения, живёт только в новом сервисе. Об этом ниже, в разделе про [переход с монолита](#переход-с-монолита).

## Как это работает

### Монолит или микросервисы

Микросервисы решают организационную проблему больше, чем техническую: несколько команд мешают друг другу в одном коде, выпуск одной фичи ждёт чужих, а одна часть системы нагружена в десятки раз сильнее остальных. Если этих проблем нет, распределённая система добавит сеть, повторы, итоговую согласованность и отдельный мониторинг на каждый сервис, а взамен ничего не даст.

Для «Задачника» вынос уведомлений оправдан: они живут своим ритмом (очереди, повторы, внешние почтовые сервисы), нагрузка у них пиковая, а падение почтового провайдера не должно мешать создавать задачи. С комментариями сложнее: если каждый экран задачи показывает комментарии, а права на комментарий зависят от прав на задачу, сервисы будут постоянно ходить друг к другу.

Промежуточный вариант — **модульный монолит**: одно приложение и один выпуск, но код разбит на модули с явными границами. Модуль `comments` не лезет в таблицы модуля `tasks`, а вызывает его публичные функции. Если границы выбраны верно, такой модуль потом легко вынести в сервис, а если неверно — их дёшево перенести, пока всё в одном репозитории.

| | Монолит | Модульный монолит | Микросервисы |
|---|---|---|---|
| Вызов соседней части | функция | функция публичного API модуля | сетевой запрос, который может упасть |
| Изменение на две части | один коммит и выпуск | один коммит и выпуск | два выпуска и совместимый контракт |
| Цена ошибки в границах | почти нулевая | переместить код | переносить данные между базами |
| Транзакция на две части | обычная | обычная | [Saga](../../design/transactions.md) |
| Кому подходит | одна команда, продукт ищет себя | несколько команд, границы ещё уточняются | много команд, границы устоялись |

Худший исход — **распределённый монолит**: сервисы разделены по сети, но не по ответственности. Признаки: нельзя выпустить один сервис без другого; сервисы читают таблицы друг друга; одна пользовательская операция проходит цепочку из пяти синхронных вызовов, и падение любого звена ломает всё. Получаются все минусы микросервисов без их главного плюса — независимости.

### Декомпозиция

Резать систему по техническим слоям («сервис базы», «сервис API», «сервис валидации») — верный путь к распределённому монолиту: любая фича задевает все слои, а значит, все сервисы. Резать нужно по тому, что делает бизнес.

**По бизнес-возможностям** (business capability): что система умеет делать для пользователя. У «Задачника» это «вести задачи», «обсуждать задачи», «оповещать», «управлять доступом». Каждой возможности — свой сервис и своя команда. Возможности меняются редко, поэтому и границы получаются устойчивыми.

**По поддоменам** — тот же вопрос, но с инструментами DDD (проектирование от предметной области, см. [архитектура приложения](../../design/architecture.md)):

- **ограниченный контекст** (bounded context) — часть системы, внутри которой у каждого слова одно точное значение;
- **единый язык** (ubiquitous language) — эти слова одинаково понимают разработчики и заказчики внутри контекста и пишут их прямо в коде.

Одно и то же слово в разных контекстах — разные модели. «Пользователь» в авторизации — это логин, хэш пароля, роли и второй фактор. В уведомлениях — адрес почты, идентификатор в Telegram, часовой пояс и «не беспокоить ночью». В комментариях — только `author_id` и отображаемое имя. Попытка сделать одну общую модель `User` на всех заканчивается классом с сорока полями, который боятся трогать все команды сразу. Каждый контекст хранит свою модель, а связывает их общий идентификатор.

Два принципа помогают проверить границы:

- **единственная ответственность** (SRP, буква S из [SOLID](../../design/principles.md)) на уровне сервиса: у сервиса одна причина меняться — изменились правила одной бизнес-возможности;
- **согласованное изменение** (Common Closure Principle): что меняется вместе, живёт вместе. Если каждая правка формата комментария требует правки сервиса уведомлений, граница проведена не там: либо уведомлениям нужна своя модель с [совместимым контрактом](../contracts.md), либо эти части должны быть одним сервисом.

### Переход с монолита

Переписать всё с нуля заманчиво, но опасно. Пока новая система пишется месяцами, старая продолжает меняться, и новую приходится догонять. Выпускается всё одним большим скачком, и ошибки находятся сразу в продакшене. А правила, которые нигде не описаны и живут только в старом коде, теряются.

#### Душитель

**Душитель** (strangler fig) назван в честь фикуса-душителя: он прорастает вокруг дерева-хозяина и постепенно заменяет его собой. Перед монолитом ставят фасад — обычно [API Gateway](../api_gateway/README.md) или обратный прокси. Порядок такой:

1. Весь трафик идёт через фасад, но пока в монолит.
2. Пишется новый сервис для одной возможности, например комментариев.
3. Фасад переводит в него пути этой возможности. Остальное по-прежнему идёт в монолит.
4. Новое по этой возможности пишется только в сервисе. Старый код в монолите удаляют, когда трафик на него перестал приходить.
5. Повторяется для следующей возможности, пока от монолита ничего не останется или не останется то, что выносить невыгодно.

Каждый шаг маленький, и его можно откатить переключением маршрута. Но откат простой только для чтения. В примере после отката монолит не увидел комментарий, записанный в новом сервисе. Поэтому на время переезда данные синхронизируют в обе стороны (например, через события из [Outbox](../../design/transactions.md)) или сначала переносят только чтение, а запись — когда новый сервис уже проверен.

Душитель лишний, если монолит маленький: его быстрее разделить внутри (модульный монолит) или переписать за пару недель, чем строить фасад и синхронизацию данных.

#### Предохранительный слой

У старой системы своя модель, часто неудачная: сокращённые поля, статусы числами, время в секундах. Если новый сервис начнёт работать с ней напрямую, старая модель расползётся по его коду, и через год новый сервис будет выглядеть как старый.

**Предохранительный слой** (anti-corruption layer) — единственное место нового сервиса, которое знает старый формат. Он ходит в старую систему и переводит ответы в модель нового сервиса:

```python
# example/app/legacy.py
LEGACY_STATUS = {0: 'new', 1: 'in_progress', 2: 'done'}


def task_from_legacy(raw: dict) -> TaskRef:
    return TaskRef(id=raw['id'], title=raw['ttl'], status=LEGACY_STATUS.get(raw['st'], 'unknown'))


def comment_from_legacy(raw: dict) -> Comment:
    return Comment(
        id=f'legacy-{raw["cid"]}',  # префикс, чтобы старые id не пересеклись с новыми
        task_id=raw['tsk'],
        author_id=raw['usr_id'],
        text=raw['txt'],
        created_at=datetime.fromtimestamp(raw['ts'], tz=timezone.utc),
    )
```

Остальной код сервиса видит только `TaskRef` и `Comment`. Когда монолит исчезнет, удаляется один файл. В терминах [гексагональной архитектуры](../../design/architecture.md#гексагональная-архитектура-порты-и-адаптеры) это исходящий адаптер, который вдобавок переводит модель.

Новый сервис ходит в монолит по внутреннему адресу (`http://monolith:8000`), а не через шлюз: шлюз уже отправляет пути комментариев в новый сервис, и запрос вернулся бы к нему самому.

### Данные

#### База на сервис

Каждый сервис владеет своими данными, и другие получают их только через его API или события. Тогда сервис может менять схему, не согласовывая это с соседями. Это **логическое** разделение: у сервиса своя схема в PostgreSQL или своя коллекция в MongoDB с отдельным пользователем, у которого нет прав на чужие схемы. Отдельный сервер базы нужен только при разных требованиях к нагрузке или надёжности.

**Общая база** проще: можно сделать JOIN и транзакцию на две таблицы. Но любая миграция становится общей, и сервисы связаны через схему сильнее, чем через любой API. Это допустимая ступень при переезде с монолита, но не конечная цель.

Цена базы на сервис — запросы и транзакции через границы. Транзакции решает [Saga](../../design/transactions.md): шаги в разных сервисах и компенсации при ошибке, а не одна транзакция на всех. Запросы решают API-композиция и CQRS.

#### API-композиция

Экран задачи показывает саму задачу, комментарии и имена авторов — это три сервиса. **Композитор** (шлюз, BFF или отдельный сервис) вызывает их, по возможности параллельно, и склеивает ответ. Новый сервис комментариев в примере делает то же самое в миниатюре: задача от монолита плюс комментарии.

Это просто, пока выборки маленькие. Запрос «все задачи Ани с непрочитанными комментариями, отсортированные по дате последнего комментария» композицией не собрать: пришлось бы выгрузить все задачи Ани, все её комментарии и соединить их в памяти. Фильтр и сортировка по полям из разных сервисов, большие объёмы и постраничный вывод — сигнал, что нужна отдельная модель для чтения.

#### CQRS

**CQRS** (Command Query Responsibility Segregation, разделение команд и запросов) — разные модели для записи и для чтения. Команды («назначить задачу», «закрыть задачу») проверяют правила и меняют состояние. Запросы («сколько открытых задач у Ани») только читают, и им удобна модель, заточенная под конкретный экран.

- **Простая форма**: одно хранилище, но разные модели в коде. Запись идёт через доменную модель с правилами, а чтение — прямыми SQL-запросами или представлениями (view), минуя доменные объекты. Согласованность полная, инфраструктура та же.
- **Расширенная форма**: отдельное хранилище для чтения. Например, денормализованная таблица, индекс Elasticsearch или документ в Redis. Его обновляет **проекция** — обработчик событий записи, обычно асинхронно. Чтение быстрое и масштабируется отдельно, но согласованность [итоговая](../../design/consistency.md#base-и-итоговая-согласованность): сразу после команды модель чтения может показывать старые данные.

#### Event Sourcing

Обычно база хранит текущее состояние: строку задачи со статусом `done`. **Event Sourcing** хранит вместо этого журнал событий: «создана», «назначена Ане», «выполнена», «переоткрыта». Текущее состояние получается проигрыванием событий по порядку. Это как банковская выписка: остаток на счёте — это сумма всех операций, а не отдельное поле, которое кто-то перезаписал.

Что это даёт: полная история изменений и аудит из коробки, ответ на вопрос «каким было состояние в прошлый вторник» и возможность построить новую модель чтения по старым событиям. Event Sourcing почти всегда идёт вместе с CQRS: искать по журналу событий неудобно, поэтому для запросов строят проекции.

Скрипт [example/event_sourcing.py](examples/event_sourcing.py) хранит события задач в SQLite и строит проекцию «сколько открытых задач у пользователя»:

```bash
python3 example/event_sourcing.py
```

```text
1. Команды пишут события в журнал
   проекция до запуска: {}, обработано 0 из 7 событий
   проекция догнала:    {'Аня': 1, 'Борис': 1}, обработано 7 из 7 событий

2. Новые события — проекция отстаёт, пока её не обработают
   читаем сразу:        {'Аня': 1, 'Борис': 1}, обработано 7 из 10 событий
   после обработки:     {'Аня': 0, 'Борис': 3}, обработано 10 из 10 событий

3. Состояние задачи 1 восстанавливается проигрыванием событий
   v1 TaskCreated {"title": "Сдать отчёт"}
   v2 TaskAssigned {"user_id": 10}
   v3 TaskAssigned {"user_id": 11}
   → {'title': 'Сдать отчёт', 'assignee': 11, 'status': 'open'} (версия 3, проиграно 3)

4. Снимок: длинную историю не нужно проигрывать целиком
   без снимка: версия 1003, проиграно событий: 1003
   со снимком: версия 1004, проиграно событий: 1
   совпадает с полным проигрыванием (1004 событий): True

5. Два запроса изменили задачу одновременно
   задачу 3 уже изменили (ожидали версию 2)

6. Проекцию можно выбросить и построить заново из журнала
   было:      {'Аня': 1, 'Борис': 1}
   с нуля:    {'Аня': 1, 'Борис': 1}, обработано 1012 из 1012 событий
   совпадает: True
```

Что видно в выводе:

- **проекция отстаёт** (шаг 2): задачу уже переназначили Борису, а модель чтения ещё показывает старые цифры. Это и есть итоговая согласованность расширенного CQRS. Проекция хранит позицию последнего обработанного события в той же транзакции, что и свои данные, поэтому после сбоя продолжает с нужного места и не считает событие дважды;
- **состояние — функция от событий** (шаг 3): `apply(state, event) → state` — чистая функция без обращений к базе;
- **снимок** (snapshot, шаг 4): после тысячи событий проигрывать их все на каждую команду дорого. Снимок сохраняет состояние на какой-то версии, и дальше проигрываются только события после него. Снимок — это кэш: его можно удалить, и состояние восстановится из журнала;
- **защита от одновременной записи** (шаг 5): у события есть номер версии внутри задачи, и пара «задача, версия» уникальна. Второй запрос, который видел ту же версию, получит ошибку и должен перечитать состояние — это оптимистичная блокировка;
- **перестройка проекции** (шаг 6): модель чтения выбросили и построили заново из журнала, результат совпал. Так же добавляют новую проекцию или исправляют ошибку в старой.

Event Sourcing не нужен, если история изменений никому не интересна, а данные — обычный CRUD: справочник меток, настройки профиля. Ему мешают и требования удалять данные: событие из журнала по смыслу не удаляют, поэтому персональные данные хранят отдельно или шифруют ключом, который можно уничтожить. Схема событий — это контракт навсегда: старые события останутся в журнале, и код должен уметь их читать. Наконец, это непривычный подход для команды, и отлаживать его труднее, чем таблицу с текущим состоянием.

### Коммуникация: шлюз и BFF

Клиенту неудобно знать адреса всех сервисов, поэтому перед ними ставят **API-шлюз** — единую точку входа. Он маршрутизирует запросы по пути, может собрать ответ из нескольких сервисов (API-композиция) и берёт на себя сквозные задачи: TLS, проверку токена, ограничение частоты, логи и метрики. Подробно, с примером на Traefik, — в заметке [API Gateway](../api_gateway/README.md).

Когда клиентов несколько, один общий шлюз начинает обслуживать всех сразу. Мобильному приложению нужны компактные ответы и меньше запросов, веб-интерфейсу — подробные данные, внешним интеграциям — стабильный публичный API. **BFF** (Backend for Frontend) — отдельный шлюз на каждый тип клиента, который обычно поддерживает команда этого клиента. BFF для мобильного приложения сам соберёт экран задачи из трёх сервисов и вернёт один ответ без лишних полей.

### Обнаружение сервисов

Сервис комментариев должен знать адрес монолита, а копии сервисов появляются и исчезают: при масштабировании, перезапуске, переезде на другой узел. Жёстко прописанный IP-адрес быстро устаревает. **Обнаружение сервисов** (service discovery) решает это через **реестр** — список живых копий каждого сервиса с их адресами. Копия регистрируется при старте и снимается при остановке или когда перестаёт отвечать на проверки здоровья.

- **На стороне клиента**: клиент сам спрашивает реестр (например, Consul или Eureka), получает список адресов и выбирает копию. Нет лишнего сетевого шага, но логику выбора и балансировки нужно повторить в клиенте на каждом языке.
- **На стороне сервера**: клиент идёт по одному стабильному адресу, а балансировщик или прокси сам смотрит в реестр и выбирает копию. Клиент простой, но появляется ещё одно звено, которое должно быть надёжным.

В **Docker Compose** обнаружение встроенное: у сети проекта есть свой DNS, и имя сервиса разрешается в адрес контейнера. Поэтому в примере сервис комментариев ходит на `http://monolith:8000`, а Traefik — на `http://comments:8000`. Если у сервиса несколько копий, DNS вернёт несколько адресов.

В **Kubernetes** это обнаружение на стороне сервера. Объект Service получает постоянный адрес и DNS-имя (`comments` внутри своего пространства имён, полностью — `comments.tasker.svc.cluster.local`, если пространство имён называется `tasker`), а реестром служит сам кластер: в Service попадают только поды, прошедшие проверку готовности. См. [Kubernetes](../../../infrastructure/cicd/kubernetes/README.md).

### Развёртывание

Базовый паттерн — **экземпляр сервиса на контейнер**: каждый сервис упакован в свой образ, а каждая копия — отдельный контейнер. Копии одинаковые и не хранят состояние, поэтому их можно добавлять, убирать и заменять. На этом построены все стратегии обновления ниже.

**Blue-green** — две одинаковые среды. «Синяя» обслуживает пользователей, а новая версия разворачивается в «зелёную» и проверяется там без пользовательского трафика. Затем балансировщик переключает весь трафик на зелёную. Если что-то пошло не так, откат — переключение обратно, синяя среда ещё работает. После успешного выпуска синяя становится запасной для следующей версии.

У этого есть цена:

- **двойные ресурсы**: на время выпуска работают две полные копии системы;
- **общая база**: базу обычно не дублируют, и обе версии работают с одной схемой. Значит, миграции должны быть совместимы с обеими версиями. Сначала добавляют новую колонку, и старый код её не замечает; удаляют старую только следующим выпуском, когда синяя версия уже не вернётся;
- **незавершённые запросы и фоновые задачи** в синей среде нужно дождаться, прежде чем её останавливать.

| | Rolling update | Blue-green | Canary |
|---|---|---|---|
| Как идёт обновление | копии заменяются по одной | весь трафик переключается разом на готовую среду | новая версия получает малую долю трафика, доля растёт |
| Обе версии одновременно | да, во время замены | нет, только одна обслуживает пользователей | да, намеренно |
| Откат | новая замена копий, минуты | переключение обратно, секунды | убрать долю трафика с новой версии |
| Лишние ресурсы | одна-две копии сверху | вторая полная среда | несколько копий новой версии |
| Проверка на части пользователей | нет | нет, но новую среду проверяют до переключения | да, по метрикам |
| Где описано | [Kubernetes](../../../infrastructure/cicd/kubernetes/README.md#обновление-без-остановки) | здесь | [CI/CD](../../../infrastructure/cicd/README.md#сборка-развёртывание-выпуск) |

Требование совместимых миграций касается всех трёх стратегий: при rolling update и canary старая и новая версии тоже работают с одной базой одновременно.

### Отказоустойчивость

Чем больше сервисов в цепочке, тем выше шанс, что один из них медленный или недоступен. Если сервис комментариев ждёт монолит без таймаута, зависший монолит подвесит и комментарии. Поэтому у каждого сетевого вызова есть таймаут, повторы с паузой только для идемпотентных операций, выключатель (circuit breaker), который перестаёт дёргать упавший сервис, и перегородки (bulkhead), чтобы один медленный сосед не занял все соединения. Всё это с примерами — в заметке [Устойчивость](../../design/resilience.md). Отдельно продумывают деградацию: если сервис комментариев недоступен, экран задачи показывает задачу без комментариев, а не ошибку 500.

## Частые ошибки

- **Микросервисы с первого дня.** Границы предметной области ещё не ясны, и их приходится двигать. В монолите это рефакторинг, а между сервисами — перенос данных и смена контрактов. Начинают с модульного монолита и выносят модули, когда граница устоялась и есть причина выносить.
- **Нарезка по техническим слоям.** Сервис базы, сервис бизнес-логики, сервис API — любая фича меняет все три. Режут по бизнес-возможностям.
- **Общая модель на всех.** Один класс `User` или общая библиотека с моделями для всех сервисов связывает их выпуски. У каждого контекста своя модель, общий только идентификатор.
- **Сервис читает чужие таблицы.** Схему соседа больше нельзя менять без согласования, и сервисы превращаются в распределённый монолит. Чужие данные получают через API, события или свою копию.
- **Старая модель без предохранительного слоя.** Поля `txt` и `st` расползаются по коду нового сервиса, и избавиться от них потом так же трудно, как от монолита. Перевод делают в одном месте.
- **Душитель без плана по данным.** Пути переключены, а запись идёт в две базы без синхронизации. Откат маршрута тогда теряет данные. До переключения решают, кто владеет данными и как они попадут в другую сторону.
- **Чтение из модели чтения сразу после команды.** Пользователь закрыл задачу, а счётчик открытых не изменился, потому что проекция ещё не обработала событие. Либо ответ на команду возвращает новое состояние сразу, либо интерфейс честно показывает, что данные обновляются.
- **Изменение смысла старых событий.** Поле события переименовали, и старые события в журнале перестали читаться. События версионируют и добавляют в обработчик перевод старых версий.
- **Миграция, ломающая предыдущую версию.** Колонку переименовали в том же выпуске, где поменяли код, и откат в blue-green сломал синюю среду. Изменения схемы делают в несколько выпусков: добавить, перейти, удалить.

## Когда не использовать

- **Микросервисы** не нужны маленькой команде с одним продуктом и без проблем с нагрузкой: модульный монолит даёт ту же структуру кода без сетевых проблем.
- **Душитель** не нужен маленькому монолиту: его быстрее разделить или переписать.
- **CQRS с отдельным хранилищем** не нужен, если запросы обслуживаются индексами основной базы. Простая форма — разные модели в коде — почти ничего не стоит и часто полезна.
- **Event Sourcing** не нужен для CRUD без интереса к истории. Если нужен только аудит, хватит таблицы истории изменений рядом с обычной таблицей.
- **Blue-green** дорог, если система большая и вторую копию держать накладно, или если миграции базы нельзя сделать совместимыми. Тогда хватит rolling update с пробами готовности.
- **Собственный реестр сервисов** не нужен в Docker Compose и Kubernetes: обнаружение там уже есть.
