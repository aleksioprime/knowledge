# Шардирование и кластер MongoDB

Оценки, комментарии и закладки задач копятся быстрее самих задач: каждый пользователь ставит десятки оценок, а таблица растёт миллионами строк в месяц. Одна машина упирается в диск, память или поток записи. MongoDB решает это двумя механизмами: **репликасет** (replica set) держит несколько копий данных, чтобы база пережила падение сервера, а **шардирование** (sharding) делит данные между несколькими репликасетами, чтобы каждый хранил и обрабатывал только часть.

Общая теория — почему шардирование откладывают и как работает консистентное хэширование — в заметке [Масштабирование и репликация](../../design/scaling.md). Здесь — как это устроено именно в MongoDB.

## Минимальный пример

Учебный кластер лежит в [examples/cluster](examples/cluster/): два шарда, config server и маршрутизатор `mongos` на порту 37017.

```bash
cd docs/backend/databases/mongodb/examples/cluster
docker compose -p kb-mongo up -d                 # init-контейнер сам соберёт кластер
docker compose -p kb-mongo logs init | tail -1   # шарды: rs1, rs2
uv run --with-requirements requirements.txt python load.py   # 200 000 оценок в две коллекции
```

Приложение подключается только к `mongos` и не знает, сколько за ним шардов:

```python
from pymongo import MongoClient

client = MongoClient('mongodb://localhost:37017')
client.admin.command('enableSharding', 'tasker')
client.admin.command('shardCollection', 'tasker.ratings', key={'task_id': 'hashed'})
client.tasker.ratings.insert_one({'task_id': 777, 'user_id': 1, 'score': 5})
```

```javascript
// docker compose -p kb-mongo exec mongos mongosh tasker
db.ratings.getShardDistribution()
```

```text
Shard rs2 at rs2/shard2a:27017
{ data: '7.65MiB', docs: 101545, chunks: 2, ... }
Shard rs1 at rs1/shard1a:27017
{ data: '7.41MiB', docs: 98455, chunks: 2, ... }
Totals
{ 'Shard rs2': [ '50.77 % data', ... ], 'Shard rs1': [ '49.22 % data', ... ] }
```

200 000 оценок разошлись по двум шардам почти поровну.

## Репликасет

Репликасет — группа `mongod`, хранящих одни и те же данные:

- **primary** — единственный узел, который принимает запись. Каждое изменение он пишет в **oplog** — журнал операций;
- **secondary** — читают oplog primary и повторяют операции у себя. Отстают на миллисекунды, под нагрузкой — на секунды.

Узлы постоянно обмениваются heartbeat. Если primary не отвечает 10 секунд (`electionTimeoutMillis`), secondary устраивают **выборы**: побеждает узел со свежими данными, за которого проголосовало **большинство** узлов. Поэтому узлов нечётное число: из трёх можно потерять один, из двух — ни одного (оставшийся один не составит большинство).

В учебном кластере выборы видны с профилем `replica`, который добавляет в `rs1` ещё две ноды:

```bash
docker compose -p kb-mongo --profile replica up -d
docker exec kb-mongo-shard1b-1 mongosh --quiet --eval 'rs.status().members.map(m => m.name + " " + m.stateStr)'
# shard1a PRIMARY | shard1b SECONDARY | shard1c SECONDARY

docker compose -p kb-mongo stop shard1a       # остановлен в 07:24:09
# shard1a (not reachable/healthy) | shard1b PRIMARY | shard1c SECONDARY
# electionDate shard1b: 07:24:10 — новый primary за ~1–3 секунды

docker compose -p kb-mongo start shard1a
# через 20 секунд shard1a снова PRIMARY: у него priority 2, он догнал oplog и забрал роль обратно
```

Остановка контейнера — «вежливое» выключение, узлы сразу узнают о потере. При настоящем обрыве сети выборы начнутся только через `electionTimeoutMillis`.

### Подтверждение записи и чтения

Три настройки определяют, насколько можно доверять записи и чтению:

| Настройка | Что задаёт | Типичные значения |
|---|---|---|
| `writeConcern` | сколько узлов должны подтвердить запись | `w: 1` — только primary; `w: "majority"` (по умолчанию с 5.0) — большинство |
| `readConcern` | какие данные можно увидеть | `local` — всё, что есть на узле; `majority` — только то, что уже не откатится |
| `readPreference` | с какого узла читать | `primary` (по умолчанию), `primaryPreferred`, `secondary`, `secondaryPreferred`, `nearest` |

Почему `majority` важен: запись, которую подтвердил только primary, может пропасть. Если primary упадёт до того, как secondary её скопировали, новый primary о ней не знает, и при возвращении старый узел **откатит** (rollback) такие записи. Запись с `w: "majority"` уже есть у большинства, а новый primary всегда выбирается из большинства — она переживёт выборы.

Что происходит, когда большинства нет — остановим две ноды из трёх:

```javascript
db.ratings.insertOne({task_id: 1, user_id: 2, score: 4}, {writeConcern: {w: 'majority', wtimeout: 3000}})
// WriteConcernFailed: waiting for replication timed out
// запись могла примениться на primary, но не подтверждена — считать её сохранённой нельзя

// ещё через несколько секунд primary замечает, что остался в меньшинстве, и сам становится SECONDARY
// shard1a SECONDARY | shard1b (not reachable) | shard1c (not reachable)
db.ratings.insertOne({task_id: 1, user_id: 4, score: 4}, {maxTimeMS: 5000})
// Write results unavailable from failing to target a host in the shard rs1
```

Шард без primary не принимает запись вообще, но данные других шардов остаются доступными. Чтение с secondary через `mongos` видно по `explain()` — запрос обслужил другой контейнер:

```javascript
db.ratings.find({task_id: 1}).readPref('primary').explain().queryPlanner.winningPlan.shards[0].serverInfo.host    // 49e9df142164
db.ratings.find({task_id: 1}).readPref('secondary').explain().queryPlanner.winningPlan.shards[0].serverInfo.host  // 80bcab49068c
```

Чтение с secondary разгружает primary, но может вернуть устаревшие данные: пользователь поставил оценку и тут же не увидел её. Для «прочитать свою запись» используют `primary` или сессии с причинной согласованностью (causal consistency).

## Компоненты шардированного кластера

```text
            приложение
                │
             mongos  ── читает карту чанков ──  config servers (репликасет)
            ╱      ╲
   шард rs1          шард rs2
 (репликасет)      (репликасет)
```

- **Шард** — обычный репликасет, запущенный с `--shardsvr`. Хранит часть данных каждой шардированной коллекции.
- **Config servers** — отдельный репликасет (`--configsvr`) с метаданными: какие коллекции шардированы, по какому ключу, какие диапазоны на каком шарде. Без него кластер не может менять раскладку и маршрутизацию.
- **mongos** — маршрутизатор без собственных данных. Кэширует карту чанков, отправляет запрос на нужные шарды и склеивает ответы. Их ставят несколько — например, по одному рядом с каждым экземпляром приложения.

У каждой базы есть **primary shard** — шард, где лежат её нешардированные коллекции. В выводе `sh.status()` это `primary: 'rs2'`.

## Ключ шардирования

Ключ шардирования (shard key) — поле или поля, по которым MongoDB решает, на каком шарде лежит документ. Он есть в каждом документе коллекции и выбирается при `shardCollection`. От него зависит всё: равномерно ли распределены данные, сколько шардов участвует в запросе и можно ли масштабировать запись.

### Диапазонный и хэшированный

- **Диапазонный** (ranged, `{created_at: 1}`): соседние значения ключа лежат рядом, в одном чанке. Запросы по диапазону (`created_at` за вчера) идут на один-два шарда.
- **Хэшированный** (hashed, `{task_id: 'hashed'}`): шард выбирается по хэшу значения. Данные и запись расходятся равномерно, но запрос по диапазону ключа идёт на все шарды — соседние `task_id` лежат где угодно.

Можно совместить: `{task_id: 'hashed', _id: 1}` — составной ключ, где первое поле хэшируется (с MongoDB 4.4).

### Что проверить у кандидата

- **Кардинальность** — сколько разных значений. Ключ `status` с пятью значениями даст максимум пять чанков: шестой шард простаивает, а чанк «done» вырастет до неразделимого гиганта (jumbo chunk).
- **Частота** — насколько равномерно встречаются значения. Даже при высокой кардинальности одна популярная задача с миллионом оценок упрётся в один чанк.
- **Монотонность** — растёт ли значение со временем. Это главная ловушка.

### Почему `_id` и время — плохой диапазонный ключ

`ObjectId` и `created_at` всегда растут. Каждая новая запись больше всех предыдущих и попадает в последний чанк — тот, у которого верхняя граница `MaxKey`. Этот чанк живёт на одном шарде, и вся запись кластера идёт в него. Остальные шарды при этом простаивают — **горячий шард** (hot shard).

В примере коллекция `ratings_by_time` шардирована по `{created_at: 1}`. Диапазон времени разделён на «прошлое» (`rs1`) и «будущее» (`rs2`), и для наглядности балансировщик для неё выключен:

```javascript
db.ratings_by_time.getShardDistribution()
```

```text
Shard rs1 at rs1/shard1a:27017
{ data: '0B', docs: 0, chunks: 1, ... }
Shard rs2 at rs2/shard2a:27017
{ data: '15.06MiB', docs: 200000, chunks: 1, ... }
Totals
{ 'Shard rs1': [ '0 % data', ... ], 'Shard rs2': [ '100 % data', ... ] }
```

Те же 200 000 документов, что легли поровну в `ratings`, целиком ушли на `rs2`. Балансировщик потом перенесёт старые диапазоны на другой шард, но последний чанк — и вместе с ним вся новая запись — останется на одном шарде:

```javascript
const last = db.ratings_by_time.find().sort({created_at: -1}).limit(1).next().created_at
db.ratings_by_time.find({created_at: {$gt: last}}).explain().queryPlanner.winningPlan
// stage: 'SINGLE_SHARD', shards: [ 'rs2' ] — даже после балансировки
```

Если по времени всё же нужно искать, его делают не первым полем ключа: `{task_id: 'hashed', created_at: 1}` или `{user_id: 1, created_at: 1}`.

## Чанки и балансировщик

Шардированная коллекция разбита на **чанки** (chunks) — непрерывные диапазоны значений ключа. Карта «диапазон → шард» лежит на config servers:

```javascript
sh.status()
```

```text
'tasker.ratings': {
  shardKey: { task_id: 'hashed' },
  chunks: [
    { min: { task_id: MinKey() }, max: { task_id: Long('-4611686018427387902') }, 'on shard': 'rs2' },
    { min: { task_id: Long('-4611686018427387902') }, max: { task_id: Long('0') }, 'on shard': 'rs2' },
    { min: { task_id: Long('0') }, max: { task_id: Long('4611686018427387902') }, 'on shard': 'rs1' },
    { min: { task_id: Long('4611686018427387902') }, max: { task_id: MaxKey() }, 'on shard': 'rs1' }
  ]
},
'tasker.ratings_by_time': {
  shardKey: { created_at: 1 },
  balancing: false,
  chunks: [
    { min: { created_at: MinKey() }, max: { created_at: ISODate('2026-10-29T07:07:31.000Z') }, 'on shard': 'rs1' },
    { min: { created_at: ISODate('2026-10-29T07:07:31.000Z') }, max: { created_at: MaxKey() }, 'on shard': 'rs2' }
  ]
}
```

Для хэшированного ключа на пустой коллекции MongoDB сразу создаёт по два чанка на шард — данные с первой записи пишутся равномерно. Для диапазонного ключа сначала есть один чанк на primary shard.

**Балансировщик** (balancer) — фоновый процесс на primary config server. Начиная с MongoDB 6.0.3 он смотрит на объём данных, а не на число чанков: если на одном шарде данных больше, чем на другом, на три размера чанка (по умолчанию 128 МБ, в учебном кластере 1 МБ), он переносит диапазоны (`moveRange`). Включим его для `ratings_by_time`:

```javascript
sh.enableBalancing('tasker.ratings_by_time')
sh.balancerCollectionStatus('tasker.ratings_by_time')
// { balancerCompliant: false, firstComplianceViolation: 'chunksImbalance' }
// ...через полторы минуты
// { balancerCompliant: true }
// чанков: rs1 — 8, rs2 — 1; данных: rs1 6.99MiB, rs2 8.06MiB
```

Перенос — это копирование документов на новый шард, переключение владельца в метаданных и удаление старой копии. Удаление откладывается (по умолчанию на 15 минут), и всё это время старые документы — **сироты** (orphans): `mongos` их не показывает, но `getShardDistribution()` в поле `docs` их считает. Сразу после балансировки он показал 92 904 + 200 000 документов при 200 000 настоящих.

Перенос нагружает оба шарда, поэтому в продакшене балансировщику задают окно (`activeWindow`) в часы низкой нагрузки.

## Запросы: адресные и широковещательные

`mongos` смотрит на фильтр запроса:

- в фильтре есть ключ шардирования → знает нужный чанк → **адресный** запрос (targeted) на один шард;
- ключа нет → спрашивает **все** шарды и склеивает ответы (scatter-gather, broadcast).

```javascript
db.ratings.createIndex({user_id: 1})
const plan = q => db.ratings.find(q).explain().queryPlanner.winningPlan
```

| Запрос | `winningPlan.stage` | Шарды | План на шарде |
|---|---|---|---|
| `{task_id: 777}` | `SINGLE_SHARD` | rs2 | `FETCH ← IXSCAN(task_id_hashed)` |
| `{user_id: 4242}` | `SHARD_MERGE` | rs2, rs1 | `SHARDING_FILTER ← FETCH ← IXSCAN(user_id_1)` |
| `{task_id: {$gte: 100, $lte: 110}}` | `SHARD_MERGE` | rs1, rs2 | `SHARDING_FILTER ← COLLSCAN` |

Последняя строка — ловушка хэшированного ключа: диапазон по `task_id` идёт на все шарды и читает коллекцию целиком (`totalDocsExamined: 200000`), потому что хэшированный индекс не умеет искать по диапазону. Нужен отдельный обычный индекс `{task_id: 1}` или диапазонный ключ.

`SHARDING_FILTER` отбрасывает документы-сироты, которые физически лежат на шарде, но уже ему не принадлежат.

Широковещательный запрос не ошибка: отчёт «все оценки пользователя» можно и разослать. Плохо, когда так работает самый частый запрос — тогда каждый новый шард добавляет нагрузку на всех, а не снимает её.

## Что нельзя или дорого менять

- **Ключ шардирования.** С 4.4 можно только *дополнить* ключ полями справа (`refineCollectionShardKey`), с 5.0 — полностью сменить (`reshardCollection`), но это переписывает всю коллекцию и требует свободного места на диске. Отменить шардирование можно только с 8.0 (`unshardCollection`).
- **Значение ключа в документе.** С 4.2 менять можно, но только в транзакции или retryable write и с полным ключом в фильтре — документ переезжает на другой шард.
- **Уникальность.** Уникальный индекс возможен, только если ключ шардирования — его префикс: шард проверяет уникальность лишь у себя. `{task_id: 1, user_id: 1}` при ключе `{task_id: 'hashed'}` — можно, `{user_id: 1}` — `CannotCreateIndex`.
- **Запросы без ключа** в `updateOne`/`deleteOne`/`findOneAndUpdate` раньше требовали `_id` или ключ шардирования; в 7.1+ ограничение ослаблено, но такие операции всё равно рассылаются по всем шардам.

## Зоны

**Зоны** (zones) привязывают диапазоны ключа к конкретным шардам: данные европейских пользователей — на шарды в ЕС, архивные задачи — на дешёвые диски. Шард добавляют в зону (`sh.addShardToZone`), диапазону ключа назначают зону (`sh.updateZoneKeyRange`), и балансировщик держит эти диапазоны только на шардах зоны. Поэтому для зонирования в начало ключа ставят поле, по которому делят: `{region: 1, user_id: 1}`.

## Частые ошибки

- **Монотонный ключ.** `{_id: 1}` или `{created_at: 1}` → вся запись в один шард → хэшировать или ставить время вторым полем.
- **Ключ с малой кардинальностью.** `{status: 1}` → неразделимые jumbo-чанки, балансировщик не может их перенести → добавить поле с высокой кардинальностью.
- **Подключение мимо mongos.** Приложение ходит напрямую на шард → видит часть данных и сирот → подключаться только к `mongos`.
- **Два узла в репликасете.** При падении одного второй не наберёт большинство и станет SECONDARY → три узла (или два + арбитр, с оговорками).
- **`w: 1` для важных данных.** Подтверждённая запись исчезает после выборов → оставить `w: "majority"` по умолчанию.
- **Диапазонные запросы при хэшированном ключе.** `task_id` в диапазоне → broadcast и `COLLSCAN` → обычный индекс рядом с хэшированным.

## Когда не использовать

Шардирование — последний шаг. Сначала индексы, затем вертикальное масштабирование и чтение с secondary, затем архивирование старых данных. Десятки гигабайт и тысячи записей в секунду спокойно держит один репликасет. Шардирование оправдано, когда рабочий набор не помещается в память одной машины, диска не хватает или primary не справляется с потоком записи.
