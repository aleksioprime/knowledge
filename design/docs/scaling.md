# Масштабирование и репликация

«Задачником» пользуется сотня человек, и всё работает на одном сервере. Через год пользователей сто тысяч: API отвечает по две секунды, база упирается в диск, а падение единственного сервера означает, что не работает ничего. Масштабирование — это набор приёмов, которые применяют **по очереди**, начиная с самых простых, по мере того как появляется конкретная проблема.

## Минимальный пример: путь роста

1. **Один сервер.** Приложение и база на одной машине. Для старта — нормально.
2. **База отдельно.** Приложение и PostgreSQL на разных машинах: им больше не мешают общие процессор и память.
3. **Несколько копий приложения** за балансировщиком. Нагрузка делится, а падение одной копии незаметно для пользователей.
4. **Кэш** для частых запросов — см. [кэширование](caching.md).
5. **Реплики базы** для чтения.
6. **Очереди** для тяжёлой работы: письма, отчёты, обработка файлов — в [Celery](../../framework/celery/README.md) или брокер.
7. **Шардирование** базы — когда данные не помещаются в одну машину.

Каждый следующий шаг сложнее в эксплуатации, поэтому переходят к нему, только когда предыдущих не хватает. И только по данным [мониторинга](../../analyze/prometheus/README.md), а не по ощущениям.

## Вертикальное и горизонтальное масштабирование

**Вертикальное** — дать машине больше ресурсов: процессоров, памяти, быстрый диск. Код менять не нужно, но есть потолок, цена растёт быстрее мощности, а машина остаётся одной точкой отказа.

**Горизонтальное** — добавить больше машин. Потолка почти нет, отказ одной машины не страшен, но приложение должно уметь работать в нескольких копиях.

## Приложение без состояния (stateless)

Чтобы запустить несколько копий API, ни одна копия не должна хранить у себя то, что нужно другим:

- сессии и кэш — в Redis, а не в памяти процесса;
- загруженные файлы — в [S3](../../data/s3/README.md), а не на локальном диске;
- фоновые задачи — в очереди, а не в `asyncio.create_task` внутри процесса;
- авторизация — по [JWT](../../framework/fast_api/docs/auth_jwt.md), который проверяет любая копия.

«Задачник» так и устроен, поэтому его можно запустить в нескольких копиях за [балансировщиком](../../web/nginx/load_balancing.md) или в [Kubernetes](../../ci_cd/kubernetes/README.md) с `replicas: 3`.

## Репликация базы

База — обычно первое узкое место, и её так просто не размножишь: все копии должны видеть одни и те же данные. **Репликация** держит копии в актуальном состоянии:

- **основной сервер** (primary) принимает все записи;
- **реплики** (replicas) получают поток изменений и отвечают на чтение.

Большинство приложений читают гораздо чаще, чем пишут, поэтому чтение с реплик снимает с основного сервера большую часть нагрузки. А если основной сервер упал, одну из реплик можно сделать основной.

**Задержка репликации** (replication lag). Реплика отстаёт от основного сервера на миллисекунды, а под нагрузкой — на секунды. Пользователь создал задачу, следующий запрос попал на реплику, а задачи там ещё нет. «Я же только что её создал!»

Решения:

- **читать свои записи с основного сервера** (read-your-writes): какое-то время после записи этот пользователь читает с primary;
- **отправлять на реплики только то, где отставание не важно**: отчёты, аналитику, поиск;
- **синхронная репликация**: запись подтверждается, только когда её получила реплика. Задержки нет, но каждая запись медленнее, а при недоступной реплике запись вообще встаёт.

## Шардирование

Когда данные или поток записи не помещаются в один сервер, данные **делят** между несколькими базами: пользователи 1–1 000 000 на первой, следующие на второй, и так далее. Каждый шард — независимая база со своими репликами.

Главный вопрос — **ключ шардирования**: по какому полю решать, в какой шард попадает запись. Для «Задачника» естественный ключ — `owner_id`: все задачи пользователя лежат в одном шарде, и запросы «мои задачи» идут в одну базу.

Простой способ выбрать шард — остаток от деления: `shard = hash(owner_id) % N`. Проблема видна, когда шардов становится больше:

```python
keys = [f'user:{i}' for i in range(10_000)]

before = {key: h(key) % 4 for key in keys}
after = {key: h(key) % 5 for key in keys}
moved = sum(before[key] != after[key] for key in keys)
# hash % N: при добавлении 5-го сервера переехало 80% ключей
```

Почти все данные пришлось бы переносить. **Консистентное хэширование** раскладывает серверы и ключи на одно кольцо значений хэша. Ключ принадлежит ближайшему по кольцу серверу, поэтому новый сервер забирает ключи только у своих соседей:

```python
import bisect
import hashlib


def h(value: str) -> int:
    return int(hashlib.md5(value.encode()).hexdigest(), 16)


class HashRing:
    def __init__(self, nodes, replicas=100):
        # Каждый сервер — 100 «виртуальных точек» на кольце, чтобы ключи делились ровнее
        self.ring = sorted((h(f'{node}#{i}'), node) for node in nodes for i in range(replicas))
        self.points = [point for point, _ in self.ring]

    def node_for(self, key: str) -> str:
        index = bisect.bisect(self.points, h(key)) % len(self.ring)
        return self.ring[index][1]


ring4 = HashRing(['db1', 'db2', 'db3', 'db4'])
ring5 = HashRing(['db1', 'db2', 'db3', 'db4', 'db5'])
moved = sum(ring4.node_for(key) != ring5.node_for(key) for key in keys)
# консистентное хэширование: переехало 20% ключей — ровно та доля, которую забрал новый сервер
```

Тот же приём используют Redis Cluster, Cassandra, балансировщики и CDN.

Цена шардирования высока: запросы и транзакции между шардами становятся сложными или невозможными, `JOIN` по данным разных пользователей больше не работает, а миграции нужно катить на каждый шард. Поэтому шардирование откладывают как можно дольше.

## Частые ошибки

- **Масштабирование без измерений.** Поставили пять серверов приложения, а тормозил один медленный SQL-запрос без индекса. Сначала найдите узкое место.
- **Состояние в памяти процесса.** Кэш в словаре или сессии в памяти работают на одной копии и ломаются на двух.
- **Чтение с реплики сразу после записи.** Пользователь не видит то, что только что сохранил.
- **Ключ шардирования, по которому неравномерно делятся данные.** Шардирование по стране отправит 80% пользователей в один шард. Выбирайте ключ с большим количеством разных значений.
