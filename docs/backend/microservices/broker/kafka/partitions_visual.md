# Партиции и группы потребителей наглядно

Топик в Kafka — не одна очередь, а несколько журналов-партиций. Производитель выбирает партицию по ключу сообщения, потребители одной группы делят партиции между собой, а разные группы читают один и тот же топик независимо. Из этих трёх правил следует почти всё поведение Kafka: порядок, масштабирование и то, что сообщение после чтения никуда не исчезает.

## Как сообщения расходятся по партициям и потребителям

Отправьте несколько событий, прочитайте их обеими группами, добавьте и уберите потребителей в группе `analytics`.

Что видно на схеме:

- Партиция сообщения — `hash(key) % число партиций`. События с одним ключом (одна задача) всегда попадают в одну партицию и читаются в том порядке, в каком были записаны. Между разными партициями порядка нет.
- У каждого сообщения есть смещение (offset) — номер в своей партиции. Сообщение не удаляется после чтения: группа просто запоминает, до какого смещения дошла.
- Внутри группы каждую партицию читает ровно один потребитель. Поэтому потребителей больше, чем партиций, не имеет смысла: лишние простаивают.
- Группы независимы: `mailer` и `analytics` читают одни и те же сообщения, и смещения у каждой свои.
- При добавлении или уходе потребителя партиции раздаются заново (ребалансировка). Смещения хранятся в Kafka, поэтому новый владелец партиции продолжает с места, где остановился прежний.
- Лаг — сколько сообщений в партиции группа ещё не прочитала. Растущий лаг означает, что потребители не успевают.

## Попробуйте сами

Производитель Kafka считает партицию по ключу детерминированно: один ключ — всегда одна партиция. Ниже та же идея на хеше Python (сам Kafka использует murmur2):

```python run
def partition_for(key: str, partitions: int) -> int:
    return sum(key.encode()) % partitions


events = ['task-7', 'task-3', 'task-7', 'task-11', 'task-3', 'task-7']
for key in events:
    print(f'{key:8} → партиция {partition_for(key, 3)}')
```

Если ключ не задан, производитель раскладывает сообщения по партициям по кругу (round-robin) или пачками — быстрее, но порядок событий одной задачи уже не гарантирован.

## Частые ошибки

- Ключ не задан у событий, где важен порядок → события одной задачи оказываются в разных партициях и обрабатываются вразнобой → используйте идентификатор сущности как ключ.
- Один «горячий» ключ (например, `user-1` с 90 % событий) → одна партиция и один потребитель перегружены, остальные простаивают → пересмотрите ключ или разбейте его.
- Потребителей больше, чем партиций → лишние ничего не делают → число партиций задаёт потолок параллелизма, его закладывают заранее.
- Долгая обработка сообщения без `poll` → брокер считает потребителя мёртвым и запускает ребалансировку → увеличьте `max.poll.interval.ms` или обрабатывайте быстрее.
- Смещение зафиксировано до того, как сообщение обработано → при падении оно потеряно → фиксируйте после обработки и делайте обработку идемпотентной.
