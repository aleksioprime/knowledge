# Потоки в Python

Потоки легче процессов: у них меньше накладных расходов, они работают с любыми типами данных, и не нужно думать, получится ли сериализовать данные для передачи потоку.

Потоки создаются модулем `threading`. Работа с ними похожа на работу с процессами.

::: warning Примеры с потоками запускайте локально
В браузере у Python нет потоков, поэтому под кодом показан вывод, полученный при локальном запуске.
:::

```python
import time
from threading import Thread


def printer(name):
    time.sleep(3)
    print('привет', name)


# Интерфейс похож на работу с процессами
t = Thread(target=printer, args=('Алиса',))
t.start()
print('Пока выполняется поток, съешьте ещё этих мягких французских булок да выпейте чаю ☕️')
# Дожидаемся завершения потока
t.join()
```

```text
Пока выполняется поток, съешьте ещё этих мягких французских булок да выпейте чаю ☕️
привет Алиса
```

## GIL

GIL (Global Interpreter Lock, глобальная блокировка интерпретатора) позволяет работать только одному потоку внутри процесса, что снижает производительность многопоточных программ.

Управление памятью в Python не потокобезопасное, поэтому для него нужна глобальная блокировка. Python подсчитывает ссылки на объекты: у каждого объекта есть счётчик ссылок (refcount), в котором хранится количество ссылок на него. Как только счётчик становится равен нулю, память объекта освобождается.

```python run
import sys

# Переменная 'a' — первая ссылка на объект object()
a = object()
# Переменная 'b' — вторая ссылка
b = a
# Аргумент функции getrefcount — третья ссылка на тот же объект
print(sys.getrefcount(a))  # 3
```

В многопоточном приложении несколько потоков могут одновременно изменять счётчик ссылок. Тогда память может очиститься неправильно: удалится объект, на который ещё есть ссылка.

Счётчик можно было бы защитить блокировками на всех структурах данных, которые делят потоки. Но блокировки на нескольких объектах грозят взаимоблокировками (deadlocks) и снижают производительность из-за постоянного захвата и освобождения.

Если программа в основном занята вводом-выводом — запросами к сервисам и базе данных, чтением файлов, — потоки её ускорят. GIL не мешает: пока поток ждёт ввода-вывода, он не меняет счётчики ссылок, и GIL передаёт управление другому потоку.

## Состояние гонки

Состояние гонки (race condition) — ошибка проектирования многопоточного приложения, при которой результат зависит от того, в каком порядке выполняются части кода. Она возникает при работе потоков с общими объектами, хотя GIL и пускает к байткоду только один поток за раз.

```python
from threading import Thread

# Глобальная переменная, которую меняют несколько потоков
counter = 0


def increment():
    global counter
    for i in range(2000000):
        counter += int(1)


t = Thread(target=increment)
t.start()

t2 = Thread(target=increment)
t2.start()

# Дожидаемся завершения потоков
t.join()
t2.join()
print(counter)
```

```text
2290568
```

Ожидаемый результат — 4000000, но на деле он каждый раз разный. Дело в том, что `counter += 1` — не атомарная операция. Сначала значение `counter` копируется в буфер: допустим, оно равно 100. Оба потока записывают в свой буфер 100, увеличивают его и получают 101. Затем оба сохраняют 101 в `counter`. В итоге `counter` равен 101, а не 102.

Исправление — блокировка `Lock`: пока один поток меняет счётчик, другие ждут.

```python
from threading import Thread, Lock

counter = 0

# Объект блокировки
lock = Lock()


def increment():
    global counter
    for i in range(2000000):
        # Контекстный менеджер захватывает блокировку и отпускает её при выходе
        with lock:
            counter += int(1)


t = Thread(target=increment)
t.start()

t2 = Thread(target=increment)
t2.start()

t.join()
t2.join()
print(counter)
```

```text
4000000
```
