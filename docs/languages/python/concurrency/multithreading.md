# Потоки в Python

Потоки нужны, когда программа много ждёт: запросов к API, ответа базы данных, чтения файлов. Пока один поток ждёт, другой работает, и три запроса по полсекунды занимают полсекунды, а не полторы. Потоки легче процессов: у них меньше накладных расходов, они работают с любыми типами данных, и не нужно думать, получится ли сериализовать данные для передачи потоку.

::: warning Примеры с потоками запускайте локально
В браузере у Python нет потоков, поэтому под кодом показан вывод, полученный при локальном запуске.
:::

## Минимальный пример

Три «загрузки профиля» ждут одновременно. Порядок строк от запуска к запуску меняется: потоки заканчивают, когда успеют.

```python
import time
from threading import Thread


def load_profile(user):
    time.sleep(0.5)  # ожидание ответа сервера
    print(f'профиль {user} загружен')


threads = [Thread(target=load_profile, args=(user,)) for user in ('alice', 'bob', 'carol')]
start = time.perf_counter()
for thread in threads:
    thread.start()
for thread in threads:
    thread.join()
print(f'три загрузки за {time.perf_counter() - start:.1f} с')
# профиль alice загружен
# профиль carol загружен
# профиль bob загружен
# три загрузки за 0.5 с
```

## Как это работает

Потоки создаются модулем `threading`. Работа с ними похожа на работу с процессами.

```python
import time
from threading import Thread


def printer(name):
    time.sleep(3)
    print('привет', name)


# Интерфейс похож на работу с процессами
t = Thread(target=printer, args=('Алиса',))
t.start()
print('Пока выполняется поток, съешьте ещё этих мягких французских булок да выпейте чаю ☕️')
# Дожидаемся завершения потока
t.join()
```

```text
Пока выполняется поток, съешьте ещё этих мягких французских булок да выпейте чаю ☕️
привет Алиса
```

### GIL

GIL (Global Interpreter Lock, глобальная блокировка интерпретатора) позволяет работать только одному потоку внутри процесса, что снижает производительность многопоточных программ.

Управление памятью в Python не потокобезопасное, поэтому для него нужна глобальная блокировка. Python подсчитывает ссылки на объекты: у каждого объекта есть счётчик ссылок (refcount), в котором хранится количество ссылок на него. Как только счётчик становится равен нулю, память объекта освобождается.

```python run
import sys

# Переменная 'a' — первая ссылка на объект object()
a = object()
# Переменная 'b' — вторая ссылка
b = a
# Аргумент функции getrefcount — третья ссылка на тот же объект
print(sys.getrefcount(a))  # 3
```

В многопоточном приложении несколько потоков могут одновременно изменять счётчик ссылок. Тогда память может очиститься неправильно: удалится объект, на который ещё есть ссылка.

Счётчик можно было бы защитить блокировками на всех структурах данных, которые делят потоки. Но блокировки на нескольких объектах грозят взаимоблокировками (deadlocks) и снижают производительность из-за постоянного захвата и освобождения.

Если программа в основном занята вводом-выводом — запросами к сервисам и базе данных, чтением файлов, — потоки её ускорят. GIL не мешает: пока поток ждёт ввода-вывода, он не меняет счётчики ссылок, и GIL передаёт управление другому потоку.

### Состояние гонки

Состояние гонки (race condition) — ошибка проектирования многопоточного приложения, при которой результат зависит от того, в каком порядке выполняются части кода. Она возникает при работе потоков с общими объектами, хотя GIL и пускает к байткоду только один поток за раз.

```python
from threading import Thread

# Глобальная переменная, которую меняют несколько потоков
counter = 0


def increment():
    global counter
    for i in range(2000000):
        counter += int(1)


t = Thread(target=increment)
t.start()

t2 = Thread(target=increment)
t2.start()

# Дожидаемся завершения потоков
t.join()
t2.join()
print(counter)
```

```text
2290568
```

Ожидаемый результат — 4000000, но на деле он каждый раз разный. Дело в том, что `counter += 1` — не атомарная операция. Сначала значение `counter` копируется в буфер: допустим, оно равно 100. Оба потока записывают в свой буфер 100, увеличивают его и получают 101. Затем оба сохраняют 101 в `counter`. В итоге `counter` равен 101, а не 102.

Исправление — блокировка `Lock`: пока один поток меняет счётчик, другие ждут.

```python
from threading import Thread, Lock

counter = 0

# Объект блокировки
lock = Lock()


def increment():
    global counter
    for i in range(2000000):
        # Контекстный менеджер захватывает блокировку и отпускает её при выходе
        with lock:
            counter += int(1)


t = Thread(target=increment)
t.start()

t2 = Thread(target=increment)
t2.start()

t.join()
t2.join()
print(counter)
```

```text
4000000
```

## Частые ошибки

- Общий счётчик или список меняют из нескольких потоков без `Lock` → результат каждый раз разный, часть обновлений теряется → оборачивать изменение в `with lock:` или передавать данные через `queue.Queue`.
- Потоками пытаются ускорить вычисления → время не уменьшается или растёт: GIL пускает к байткоду один поток, а переключения добавляют накладные расходы → для задач на процессор взять [процессы](multiprocessing.md).
- Забыли `join()` → главный поток печатает результат до того, как рабочие потоки закончили, или программа завершается раньше фоновой работы → дожидаться потоков через `join()` или использовать `ThreadPoolExecutor` как контекстный менеджер.
- Исключение внутри потока → программа молча продолжает работу, в консоли только трассировка, результат потерян → ловить исключения внутри `target` и передавать их через очередь, либо использовать `ThreadPoolExecutor`, где `future.result()` пробросит ошибку.
- Два потока захватывают две блокировки в разном порядке → взаимоблокировка (deadlock): программа зависает без ошибок → захватывать блокировки всегда в одном порядке или обходиться одной общей.

## Когда не использовать

Для тяжёлых вычислений потоки не подходят: из-за GIL они выполняются по очереди, и выигрыша нет. Такую работу раздают [процессам](multiprocessing.md), а библиотеки вроде NumPy сами освобождают GIL внутри своих операций.

Если ожиданий очень много — тысячи соединений или запросов, — потоки становятся дорогими: у каждого свой стек и переключение через ОС. Здесь лучше [asyncio](async.md): один поток и цикл событий. А когда нужно выполнить одну-две блокирующие функции из асинхронного кода, достаточно [пула потоков](thread_pool.md).
