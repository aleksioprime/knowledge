# Django: админка

Менеджеру нужно посмотреть задачи пользователей, найти нужную, поправить срок, массово отметить выполненными. Писать для этого отдельный интерфейс — недели работы. В Django админка уже есть: достаточно зарегистрировать модель, и появятся список, поиск, фильтры, формы редактирования и история изменений. Небольшая настройка превращает её в удобный внутренний инструмент.

## Минимальный пример

```python
# tasks/admin.py
from django.contrib import admin

from .models import Task

admin.site.register(Task)
```

```bash
python manage.py createsuperuser
python manage.py runserver
```

Открываем http://localhost:8000/admin/, входим, и задачи уже можно смотреть, создавать и редактировать.

## Как это работает

Админка строит интерфейс по описанию модели: поля формы — по полям модели, подписи — по `verbose_name`, проверки — по валидаторам. Поэтому русские названия полей в модели (`models.CharField('название', ...)`) сразу дают русскую админку. Название приложения в меню и в навигации задаётся в `apps.py`:

```python
# tasks/apps.py
class TasksConfig(AppConfig):
    default_auto_field = 'django.db.models.BigAutoField'
    name = 'tasks'
    verbose_name = 'Задачи'
```

Без этого в навигации будет `Начало › Tasks › Задачи`.

Входить в админку могут пользователи с флагом `is_staff`. Что именно они видят и могут менять, определяют права (`Can view task`, `Can change task`…), которые раздаются пользователям и группам прямо в админке.

## Настройка списка и формы

```python
# tasks/admin.py
@admin.register(Task)
class TaskAdmin(admin.ModelAdmin):
    list_display = ['title', 'owner', 'priority', 'due_date', 'done']  # колонки списка
    list_filter = ['done', 'priority', 'tags']                         # фильтры справа
    list_editable = ['done']                  # галочку можно менять прямо в списке
    search_fields = ['title', 'owner__username']                       # строка поиска
    date_hierarchy = 'due_date'               # навигация по годам, месяцам, дням
    filter_horizontal = ['tags']              # удобный выбор меток в форме
    list_select_related = ['owner']           # без N+1 при показе владельца
    actions = ['mark_done']

    @admin.action(description='Отметить выполненными')
    def mark_done(self, request, queryset):
        updated = queryset.update(done=True)
        self.message_user(request, f'Отмечено задач: {updated}')
```

Что даёт каждая строка:

- **`list_display`** — колонки таблицы. Без него в списке будет только `__str__` модели;
- **`search_fields`** — поиск по полям, в том числе через связи: `owner__username`;
- **`actions`** — массовые действия: отметить нужные задачи галочками, выбрать «Отметить выполненными» и нажать «Выполнить»;
- **`list_select_related`** — колонка `owner` в списке иначе выполнит отдельный запрос на каждую строку (см. [N+1 в ORM](orm.md#проблема-n1-select_related-и-prefetch_related)).

## Частые ошибки

- **Админка как интерфейс для пользователей.** Она сделана для сотрудников: доступ даёт почти полный контроль над данными, а настройка под сложные сценарии быстро становится мучительной. Для клиентов делают отдельный интерфейс.
- **Админка по адресу `/admin/` в открытом доступе.** Это первая цель подбора паролей. Перенесите адрес (`path('secret-panel/', admin.site.urls)`), ограничьте доступ по IP или VPN и включите двухфакторную аутентификацию (например, `django-otp`).
- **Медленный список на большой таблице.** Список считает общее количество строк и выполняет запрос на каждую связь без `list_select_related`. Для таблиц с миллионами строк помогают `show_full_result_count = False` и `list_select_related`.
- **«Выберите задача для изменения».** Русский перевод Django подставляет `verbose_name` в готовую фразу, не склоняя его. Так выглядит заголовок любого списка на русском, это ограничение перевода, а не ошибка в вашем коде.

## Когда не использовать

Админка — инструмент для сотрудников, а не для клиентов. Если интерфейс нужен пользователям продукта, его делают отдельно: фронтенд поверх API на [DRF](drf.md) или FastAPI. Попытка «дотянуть» админку до клиентского сценария (свой дизайн, многошаговые формы, права на уровне отдельных полей) обходится дороже, чем отдельная страница.

Не подходит она и там, где данные живут не в моделях Django: внешний API, чужая база, отчёты с тяжёлой аналитикой. Для просмотра и отчётов удобнее BI-инструменты вроде Metabase, для сложных рабочих процессов (согласования, очереди заявок) — отдельное внутреннее приложение.
