# Балансировка нагрузки

Один экземпляр приложения перестал справляться: запросы ждут в очереди, а при его перезапуске сервис недоступен целиком. Второй экземпляр поднять просто, но клиенты знают только один адрес. Группа `upstream` в NGINX решает это: клиенты по-прежнему ходят на один домен, а NGINX распределяет запросы между экземплярами и перестаёт слать трафик на тот, который отвечает ошибками.

## Минимальный пример

Два экземпляра приложения на разных хостах, NGINX отправляет запрос тому, у кого меньше активных соединений:

```nginx
upstream backend {
    least_conn;
    server 10.0.0.11:8000 max_fails=3 fail_timeout=30s;
    server 10.0.0.12:8000 max_fails=3 fail_timeout=30s;
}

server {
    listen 80;
    server_name api.example.com;

    location / {
        proxy_pass http://backend;
        proxy_set_header Host $host;
    }
}
```

После `nginx -t` и `nginx -s reload` несколько запросов `curl http://api.example.com/` будут уходить то на первый, то на второй сервер — это видно в их логах. Если один из них выключить, после трёх неудачных попыток NGINX на 30 секунд перестанет к нему обращаться.

## Как это работает

Группа `upstream` объединяет несколько экземпляров приложения. Полный вариант с постоянными соединениями к upstream:

```nginx
upstream backend {
    least_conn;

    server 10.0.0.11:8000 max_fails=3 fail_timeout=30s;
    server 10.0.0.12:8000 max_fails=3 fail_timeout=30s;
    keepalive 32;
}

server {
    listen 80;
    server_name api.example.com;

    location / {
        proxy_pass http://backend;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_set_header Host $host;
    }
}
```

`keepalive 32` держит до 32 открытых соединений с каждым рабочим процессом NGINX к серверам группы, чтобы не устанавливать TCP-соединение на каждый запрос. Для этого нужны `proxy_http_version 1.1` и пустой заголовок `Connection`.

### Алгоритмы

- round-robin — используется по умолчанию и распределяет запросы по очереди;
- `least_conn` — выбирает сервер с меньшим числом активных соединений;
- `ip_hash` — закрепляет клиентский IP за сервером, но хуже переносит изменения состава группы;
- `weight` — задаёт относительную долю трафика для сервера.

Приложение желательно делать stateless: сессии и другие общие данные хранить вне конкретного экземпляра. Тогда запросы можно свободно направлять на любой здоровый сервер.

Пассивные проверки `max_fails` и `fail_timeout` реагируют на ошибки реальных запросов. Возможности активных health checks зависят от редакции NGINX или внешнего балансировщика.

## Частые ошибки

- Сессии хранятся в памяти экземпляра → пользователь залогинился на одном сервере, следующий запрос ушёл на другой и получил 401 → хранить сессии в Redis или использовать JWT; `ip_hash` — временная мера, а не решение.
- В `upstream` указано имя контейнера или DNS-имя, которое меняет адрес → NGINX разрешает имя один раз при старте и продолжает слать запросы на старый адрес → перезагружать конфигурацию при смене адресов или использовать `resolver` с переменной в `proxy_pass`.
- `keepalive` в `upstream` есть, а `proxy_http_version 1.1` и `proxy_set_header Connection ""` в `location` нет → соединения всё равно закрываются после каждого запроса → добавлять эти две директивы вместе с `keepalive`.
- Не заданы `max_fails` и `fail_timeout`, а приложение иногда падает → по умолчанию сервер исключается после первой ошибки на 10 секунд, и часть запросов получает 502 из-за одной случайной ошибки → выставить значения под реальную частоту сбоев.
- Все экземпляры обновляются одновременно → во время деплоя ни один сервер не отвечает, балансировка не помогает → перезапускать экземпляры по одному и дождаться, пока новый начнёт отвечать.

## Когда не использовать

Если экземпляр один, `upstream` лишний: достаточно `proxy_pass` на адрес приложения, как в заметке про [reverse proxy](reverse_proxy.md). Балансировка не ускоряет приложение, которое упирается в базу данных: два экземпляра будут ждать ту же базу. Сначала посмотрите, где узкое место, — об этом в заметке [масштабирование](../../design/scaling.md).

Для сервисов в Kubernetes или за облачным балансировщиком распределение запросов обычно делает платформа; NGINX перед ними нужен только как входная точка, а не как второй уровень балансировки.
