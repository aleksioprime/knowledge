# HTTPS и TLS

Между браузером и сервером — Wi-Fi в кафе, провайдер и чужие маршрутизаторы. По обычному HTTP любой из них читает пароли и подменяет страницы. HTTPS закрывает это: трафик шифруется, подмена обнаруживается, а сертификат подтверждает, что отвечает именно `example.com`. Без HTTPS не работают `Secure`-cookie, HTTP/2 и многие API браузера, так что это базовое требование, а не опция.

## Минимальный пример

```bash
# Рукопожатие, версия TLS и сертификат сервера
curl -sv https://example.com -o /dev/null 2>&1 \
  | grep -E 'TLS handshake|SSL connection|subject|issuer|expire|verify'
# * (304) (OUT), TLS handshake, Client hello (1):
# * (304) (IN), TLS handshake, Server hello (2):
# * (304) (IN), TLS handshake, Certificate (11):
# * (304) (IN), TLS handshake, Finished (20):
# * (304) (OUT), TLS handshake, Finished (20):
# * SSL connection using TLSv1.3 / AEAD-CHACHA20-POLY1305-SHA256
# *  subject: CN=example.com
# *  expire date: Dec 25 22:56:35 2026 GMT
# *  issuer: C=US; O=SSL Corporation; CN=Cloudflare TLS Issuing ECC CA 3
# *  SSL certificate verify ok.

# Сертификат не прошёл проверку: curl отказывается отправлять запрос
curl -s https://expired.badssl.com; echo "exit=$?"
# exit=60
```

## Как это работает

**HTTPS** — HTTP внутри защищённого TLS-соединения. TLS обеспечивает:

- конфиденциальность — содержимое шифруется;
- целостность — изменение данных обнаруживается;
- аутентификацию сервера — сертификат связывает домен с публичным ключом.

### Проверка сертификата

Клиент проверяет срок действия сертификата, соответствие доменному имени и цепочку доверия до известного центра сертификации. Отключение проверки сертификата допустимо только для краткой локальной диагностики.

### TLS termination

Часто TLS завершается на NGINX или балансировщике, после чего запрос передаётся приложению. Внутренний участок сети тоже следует шифровать, если он проходит через недоверенную среду или этого требует модель угроз.

### Базовые меры

- перенаправлять HTTP на HTTPS;
- использовать актуальные версии TLS и регулярно обновлять сервер;
- автоматизировать выпуск и продление сертификатов;
- включать HSTS только после проверки, что домен и нужные поддомены стабильно доступны по HTTPS;
- не передавать секреты в URL;
- помечать сессионные cookies как `Secure`, `HttpOnly` и подходящим `SameSite`.

## Частые ошибки

- `verify=False` в HTTPX или `curl -k` остались в рабочем коде → подмена сервера проходит незамеченной → добавить корневой сертификат в доверенные (`SSL_CERT_FILE`, `verify='ca.pem'`) и вернуть проверку.
- Сертификат выпущен на `example.com`, а сайт открывают по `www.example.com` → ошибка `hostname mismatch` в браузере и в клиентах → включить оба имени в SAN или взять wildcard-сертификат.
- Сертификат продлевают вручную → ночью сайт падает с предупреждением браузера, API-клиенты получают ошибку TLS → автоматическое продление через ACME (certbot) и мониторинг срока действия.
- Сервер отдаёт только листовой сертификат без промежуточного → в браузере работает (он докачивает цепочку), а `curl` и Python падают с `unable to get local issuer certificate` → указывать `fullchain.pem`, а не `cert.pem`.
- HSTS с `includeSubDomains` и `preload` включили до проверки поддоменов → внутренний поддомен на HTTP перестал открываться, откатить preload нельзя месяцами → начать с короткого `max-age` и без `includeSubDomains`.
- Страница по HTTPS подгружает скрипт по HTTP → браузер блокирует смешанный контент, замок в адресной строке пропадает → все ссылки на ресурсы через `https://`.

## Когда не использовать

Без TLS можно обойтись только на участке, который не выходит наружу: `localhost` при разработке и связь NGINX с приложением на том же хосте или в приватной сети. Тогда TLS завершается на NGINX ([настройка TLS в NGINX](../nginx/tls.md)), а приложение работает по обычному HTTP и не возится с сертификатами.

Если внутренний трафик идёт через недоверенную сеть или между дата-центрами, обычного HTTP недостаточно даже внутри: нужен TLS между сервисами, обычно взаимный (mTLS) через service mesh или балансировщик.
