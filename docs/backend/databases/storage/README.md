# Как базы данных хранят данные

Почему PostgreSQL считает сумму по миллиарду строк минутами, а ClickHouse — секундами? Почему Cassandra принимает сотни тысяч записей в секунду, а читает медленнее? Ответ не в языке запросов, а в том, как байты разложены на диске. От раскладки зависит, сколько данных придётся прочитать для ответа, сколько раз одна запись будет переписана и насколько хорошо всё это сожмётся.

Три решения определяют характер базы:

1. **строки или колонки** — что лежит рядом на диске;
2. **B-дерево или LSM-дерево** — как обновлять данные: на месте или дописывая новые версии;
3. **как сжимать** — чем однороднее соседние байты, тем сильнее сжатие.

## Минимальный пример

Время событий задачи растёт, а соседние значения отличаются на миллисекунды. Если хранить не сами значения, а разницу с предыдущим (**delta**), огромные числа превращаются в маленькие и хорошо сжимаются. Статус задачи принимает пять значений, и в отсортированной колонке одинаковые значения идут подряд — их можно хранить как «значение × сколько раз» (**RLE**):

```python
def delta_encode(values: list[int]) -> list[int]:
    return [values[0]] + [cur - prev for prev, cur in zip(values, values[1:])]


def rle_encode(values: list[str]) -> list[tuple[str, int]]:
    runs: list[tuple[str, int]] = []
    for value in values:
        if runs and runs[-1][0] == value:
            runs[-1] = (value, runs[-1][1] + 1)
        else:
            runs.append((value, 1))
    return runs


delta_encode([1793000000000, 1793000000120, 1793000000125, 1793000000301])
# [1793000000000, 120, 5, 176]

rle_encode(['done', 'done', 'done', 'new', 'new', 'review'])
# [('done', 3), ('new', 2), ('review', 1)]
```

Замер на миллионе строк — в разделе [Сжатие](#сжатие): delta + ZSTD сжимает колонку времени в 7,8 раза, а одна только ZSTD — в 4,9.

## Как это работает

### Строки и колонки

Таблица событий задач:

| task_id | user_id | status | created_at | duration_ms |
|---|---|---|---|---|
| 1 | 101 | new | 10:00:00.120 | 0 |
| 2 | 102 | done | 10:00:00.125 | 5400 |
| 3 | 101 | review | 10:00:00.301 | 120 |

**Строковое хранение** (row-oriented: PostgreSQL, MySQL, MongoDB) кладёт на диск строку целиком, одну за другой:

```text
[1,101,new,10:00:00.120,0] [2,102,done,10:00:00.125,5400] [3,101,review,10:00:00.301,120] ...
```

**Колоночное** (column-oriented: ClickHouse, Parquet, Vertica, BigQuery) — каждую колонку отдельным файлом:

```text
task_id.bin:     1, 2, 3, ...
status.bin:      new, done, review, ...
created_at.bin:  10:00:00.120, 10:00:00.125, 10:00:00.301, ...
```

Что это даёт аналитике. Запрос `SELECT status, count() FROM events GROUP BY status` в строковой базе читает с диска все пять колонок каждой строки, хотя нужна одна. В колоночной — только `status.bin`, то есть в пять раз меньше данных при пяти колонках и в сто раз меньше при ста. Вдобавок значения одной колонки однотипны и похожи, поэтому сжимаются в разы лучше строк, где число соседствует с текстом. И обрабатывать их можно пачками — векторно, по тысяче значений за инструкцию процессора.

Цена — точечные операции. Прочитать одну строку целиком значит заглянуть в пять файлов. Изменить строку — переписать кусок в каждом из них. Поэтому колоночные базы любят большие пакетные вставки и плохо переносят частые `UPDATE`/`DELETE`.

| | Строки | Колонки |
|---|---|---|
| Нагрузка | OLTP: много мелких чтений и записей по ключу | OLAP: агрегаты по большим диапазонам |
| Прочитать одну строку | один блок | по блоку на колонку |
| Агрегат по одной колонке | читает все колонки | читает одну колонку |
| Сжатие | среднее | сильное |
| `UPDATE` одной строки | дёшево | дорого, часто асинхронно |

### B-дерево и LSM-дерево

#### B-дерево: изменять на месте

[B-дерево](../postgres/README.md#индексы) — сбалансированное дерево страниц фиксированного размера (8 КБ в PostgreSQL). Чтобы изменить значение, база находит страницу и переписывает её **на месте**. Чтение быстрое и предсказуемое: от корня до листа три-четыре страницы. Запись — случайная: каждая вставка трогает какую-то страницу в середине файла, а изменение одной строки заставляет записать целую страницу (плюс запись в [WAL](../postgres/README.md#wal)). Так устроены PostgreSQL, MySQL InnoDB и движок WiredTiger в MongoDB.

#### LSM-дерево: только дописывать

**LSM-дерево** (Log-Structured Merge tree) никогда не меняет записанное. Путь записи:

1. **WAL** — операция дописывается в конец журнала, чтобы пережить падение;
2. **memtable** — запись попадает в отсортированную структуру в памяти. Подтверждение клиенту уже можно отправлять;
3. **SSTable** (Sorted String Table) — когда memtable заполнилась, она целиком сбрасывается на диск отсортированным неизменяемым файлом, а WAL очищается;
4. **компакция** (compaction) — фоновый процесс сливает несколько SSTable в одну: от каждого ключа остаётся последняя версия, удалённые ключи выбрасываются.

Удаление — тоже запись: в memtable кладут «надгробие» (tombstone), и ключ исчезает только при компакции.

Чтение сложнее: ключ может быть в memtable или в любой SSTable, причём новая версия важнее старой. Поэтому поиск идёт от новых данных к старым. Чтобы не открывать каждый файл, у каждой SSTable есть **bloom-фильтр** — битовая маска, которая отвечает «ключа точно нет» или «возможно, есть». Отрицательный ответ всегда верен, ложноположительный случается с заданной вероятностью (обычно около 1%).

Всё это помещается в сотню строк — [examples/tiny_lsm.py](examples/tiny_lsm.py):

```text
файлы: ['sst_000.json', 'sst_001.json', 'sst_002.json', 'sst_003.json']
task:1 = done | task:2 = None | task:3 = review
поиск 100 отсутствующих ключей прочитал файлов: 0 из 400
после компакции: ['sst_compacted.json'] {'task:1': 'done', 'task:3': 'review', 'task:4': 'new', ...}
```

Двенадцать записей с memtable на три ключа дали четыре SSTable. `task:1` обновлена — читается новая версия из более свежего файла, `task:2` удалена надгробием. Bloom-фильтры отсекли все 400 обращений к файлам для отсутствующих ключей. Компакция оставила один файл без надгробий.

Где встречается: Cassandra, ScyllaDB, HBase, RocksDB (а через неё — хранилища состояний Kafka Streams, Flink и многих баз), LevelDB. **ClickHouse MergeTree** — близкий родственник: каждый `INSERT` пишет отсортированный неизменяемый кусок (part), а фоновые слияния (merges) объединяют куски — отсюда и название. Отличие в том, что у MergeTree по умолчанию нет memtable и WAL: кусок пишется на диск сразу, поэтому ClickHouse просит вставлять большими пачками.

#### Усиление записи, чтения и места

Сравнивать структуры удобно тремя коэффициентами:

- **усиление записи** (write amplification) — сколько байт база реально записала на диск на один байт данных. B-дерево переписывает страницу 8 КБ ради строки в 100 байт; LSM пишет данные в WAL, в SSTable и ещё раз на каждом уровне компакции;
- **усиление чтения** (read amplification) — сколько мест нужно проверить ради одного ключа. У B-дерева — путь от корня до листа; у LSM — memtable и несколько SSTable (bloom-фильтры смягчают);
- **усиление места** (space amplification) — сколько лишнего хранится. У LSM до компакции лежат старые версии и надгробия; у B-дерева — полупустые страницы.

Все три одновременно не минимизировать. B-дерево выбирает быстрое чтение, LSM — быструю последовательную запись. Поэтому LSM берут для потоков событий, логов и метрик, а B-дерево — для транзакционных баз с частыми чтениями по ключу.

### Сжатие

Сжатие обменивает процессор на диск и сеть. Для аналитики это почти всегда выгодно: прочитать с диска 1 МБ и распаковать быстрее, чем прочитать 8 МБ. Алгоритмы делятся на две группы.

**Кодирования** (encodings) используют знание о данных — тип и порядок значений:

- **delta** — хранить разницу с предыдущим значением. Для растущих чисел: время, автоинкрементные id, счётчики;
- **double-delta** — разницу разниц. Если события идут с ровным шагом (метрика раз в секунду), разницы одинаковы, а разницы разниц — нули. Приём из базы метрик Gorilla (Facebook), используется в Prometheus и ClickHouse (`DoubleDelta`);
- **RLE** (run-length encoding) — «значение × сколько раз подряд». Работает только на отсортированных данных с повторами;
- **словарь** (dictionary) — заменить строки номерами: `done` → `3`. Колонка из пяти статусов становится колонкой из байтов плюс словарь из пяти строк. В ClickHouse это тип `LowCardinality(String)`.

**Универсальные компрессоры** (codecs) работают с любыми байтами:

- **LZ77** — ищет повторы в уже прочитанном окне и заменяет их ссылкой «скопируй N байт с отступом M назад». Основа почти всех компрессоров;
- **LZ4** — семейство LZ77 без дальнейшего кодирования. Сжимает слабее, зато распаковывает на скорости памяти. Кодек по умолчанию в ClickHouse;
- **кодирование Хаффмана** — частые символы получают короткие битовые коды, редкие — длинные. Само по себе повторов не ищет, поэтому его ставят после LZ77 (так устроен gzip/DEFLATE);
- **ZSTD** (Zstandard, Facebook) — LZ77 + энтропийное кодирование (Хаффман для литералов, FSE для остального). Сжимает не хуже gzip и при этом в разы быстрее. Уровни от 1 до 22: чем выше, тем медленнее сжатие при почти той же скорости распаковки.

Кодирование и компрессор комбинируют: сначала delta превращает большие числа в маленькие похожие, затем ZSTD сжимает получившиеся байты.

#### Замер на колонках журнала задач

Скрипт [examples/column_compression.py](examples/column_compression.py) генерирует миллион событий и сжимает две колонки разными способами. Apple M1, Python 3.12.14, `zstandard==0.25.0`, `lz4==4.4.5`:

```bash
uv run --python 3.12 --with zstandard==0.25.0 --with lz4==4.4.5 python column_compression.py
```

```text

  zstd                         1,601 КБ   x4.9
  delta + lz4                  2,936 КБ   x2.7
  delta + zstd                 1,005 КБ   x7.8
  double-delta + zstd          1,603 КБ   x4.9

  zstd                         1,998 КБ   x3.9
  delta + zstd                   404 КБ   x19.4
  double-delta + zstd          1,004 КБ   x7.8

Статус задачи (строки): сырые данные 6,738 КБ
  lz4                          1,856 КБ   x3.6
  zstd                           790 КБ   x8.5
  словарь (1 байт)               977 КБ   x6.9
  словарь + zstd                 325 КБ   x20.8
  RLE (по времени)             3,641 КБ   x1.9
  RLE (отсортировано)           25 байт   x275,974.8
  серий RLE: по времени 745,755, после сортировки 5

lz4       сжатие    38.1 мс, распаковка  15.1 мс, размер 4,275 КБ
zstd -3   сжатие    61.2 мс, распаковка  20.3 мс, размер 1,601 КБ
zstd -19  сжатие  4809.4 мс, распаковка  18.1 мс, размер 1,605 КБ
```

Что видно:

- **delta перед компрессором** почти удваивает сжатие времени событий, а у метрик с ровным шагом — в пять раз;
- **double-delta не всегда лучше delta.** Шаг событий случаен (0–200 мс), а у метрики есть дрожание ±2 мс, и разность двух случайных величин только шумнее. Наивный double-delta + ZSTD выигрывает лишь при идеально ровном шаге, а в ClickHouse `DoubleDelta` сделан хитрее — побитовым кодированием, как в Gorilla (см. ниже);
- **RLE бесполезен без сортировки.** В порядке времени статусы перемешаны: 745 тысяч серий на миллион строк. После сортировки — пять серий и 25 байт. Поэтому в колоночных базах порядок сортировки (`ORDER BY` в ClickHouse) — главный рычаг сжатия;
- **словарь + ZSTD** для строк с малым числом значений даёт ×20;
- **высокий уровень ZSTD** не помог: −19 сжимал в 80 раз дольше, а файл не стал меньше. Для таких данных хватает уровней 1–3.

#### То же в ClickHouse

В ClickHouse кодеки задаются на колонку. [examples/clickhouse_codecs.sql](examples/clickhouse_codecs.sql) создаёт таблицу, где одна и та же колонка записана с разными кодеками, и вставляет миллион событий с тем же распределением (ClickHouse 26.3.62.3 в отдельном контейнере):

```sql
CREATE TABLE task_events
(
    ts_lz4          DateTime64(3),                                 -- кодек по умолчанию: LZ4
    ts_zstd         DateTime64(3) CODEC(ZSTD(3)),
    ts_delta_zstd   DateTime64(3) CODEC(Delta, ZSTD(3)),
    ts_ddelta_zstd  DateTime64(3) CODEC(DoubleDelta, ZSTD(3)),
    status_string   String,
    status_lowcard  LowCardinality(String),
    status_zstd     LowCardinality(String) CODEC(ZSTD(3))
    -- ...
)
ENGINE = MergeTree
ORDER BY tuple();
```

```text
   ┌─name───────────┬─type───────────────────┬─codec───────────────────────┬─raw────────┬─compressed──┬─ratio─┐
1. │ ts_lz4         │ DateTime64(3)          │                             │ 7.63 MiB   │ 4.18 MiB    │   1.8 │
2. │ ts_zstd        │ DateTime64(3)          │ CODEC(ZSTD(3))              │ 7.63 MiB   │ 1.57 MiB    │   4.9 │
3. │ ts_delta_lz4   │ DateTime64(3)          │ CODEC(Delta(8), LZ4)        │ 7.63 MiB   │ 2.90 MiB    │   2.6 │
4. │ ts_delta_zstd  │ DateTime64(3)          │ CODEC(Delta(8), ZSTD(3))    │ 7.63 MiB   │ 1021.05 KiB │   7.7 │
5. │ ts_ddelta_zstd │ DateTime64(3)          │ CODEC(DoubleDelta, ZSTD(3)) │ 7.63 MiB   │ 1.25 MiB    │   6.1 │
6. │ status_string  │ String                 │                             │ 13.26 MiB  │ 3.72 MiB    │   3.6 │
7. │ status_lowcard │ LowCardinality(String) │                             │ 978.54 KiB │ 569.13 KiB  │   1.7 │
8. │ status_zstd    │ LowCardinality(String) │ CODEC(ZSTD(3))              │ 978.54 KiB │ 335.44 KiB  │   2.9 │
   └────────────────┴────────────────────────┴─────────────────────────────┴────────────┴─────────────┴───────┘
```

Цифры почти совпали с Python: `Delta, ZSTD` сжимает время в 7,7 раза против 1,8 у кодека по умолчанию. Статус в `String` занимает 3,72 МБ, в `LowCardinality(String)` с ZSTD — 0,33 МБ, в 11 раз меньше. Если таблицу отсортировать по статусу (`ORDER BY status_lowcard`), та же колонка сжимается до 4,76 КБ: одинаковые значения идут подряд.

Кодек по умолчанию для сервера задаётся в конфигурации (`<compression>`), а `Delta`/`DoubleDelta`/`Gorilla`/`T64` — специализированные кодеки, которые ставят перед универсальным.

## Частые ошибки

- **Колоночная база под точечные обновления.** Частые `UPDATE` одной строки в ClickHouse → переписываются целые куски, слияния не успевают → вставлять новые версии (`ReplacingMergeTree`) или держать такие данные в OLTP-базе.
- **Вставка по одной строке в MergeTree или LSM.** Каждый `INSERT` — новый кусок или SSTable, компакция захлёбывается (`Too many parts`) → пачки по тысячам строк или асинхронные вставки.
- **Delta для неотсортированной колонки.** Разницы между случайными значениями не меньше самих значений → delta только для монотонных или медленно меняющихся колонок.
- **Максимальный уровень сжатия «на всякий случай».** ZSTD −19 в 80 раз медленнее −3 при том же размере → начинать с уровней 1–3 и мерить.
- **Порядок сортировки выбран только под фильтры.** Сжатие и RLE сильно зависят от `ORDER BY` → ставить первыми колонки с малым числом значений, по которым фильтруют.

## Когда это не важно

Пока данные помещаются в память одной машины, а запросы — точечные по ключу, выбор структуры хранения почти не влияет на результат: берите PostgreSQL и индексы. Об устройстве хранения стоит думать, когда появляются аналитические запросы по миллионам строк (колонки), поток записи, который не выдерживает B-дерево (LSM), или счёт за диск (сжатие).
