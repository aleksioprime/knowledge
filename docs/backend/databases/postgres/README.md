# PostgreSQL

Задачи, пользователи и связи между ними должны переживать сбой сервера, не ломаться при одновременных правках и отвечать на отчёты без переписывания приложения. Для таких данных нужна реляционная база с транзакциями, строгой схемой и индексами — в заметках раздела это PostgreSQL.

**PostgreSQL** — мощная объектно-реляционная СУБД с открытым исходным кодом. Поддерживает ACID-транзакции, расширения (PostGIS, pg_trgm, pgvector), JSON/JSONB, оконные функции, CTE, partitioning и репликацию.

## Минимальный пример

Две таблицы с внешним ключом и запрос с соединением — то, с чего начинается любая схема:

```sql run
CREATE TABLE users (id serial PRIMARY KEY, email text UNIQUE NOT NULL);
CREATE TABLE tasks (
    id serial PRIMARY KEY,
    user_id int NOT NULL REFERENCES users (id),
    title text NOT NULL,
    done boolean NOT NULL DEFAULT false,
    created_at timestamptz NOT NULL DEFAULT now()
);

INSERT INTO users (email) VALUES ('anna@example.com'), ('boris@example.com');
INSERT INTO tasks (user_id, title, done) VALUES
    (1, 'Купить хлеб', true), (1, 'Сдать отчёт', false), (2, 'Починить кран', false);

-- невыполненные задачи с почтой владельца
SELECT u.email, t.title
FROM tasks t JOIN users u ON u.id = t.user_id
WHERE NOT t.done
ORDER BY t.id;
-- anna@example.com  | Сдать отчёт
-- boris@example.com | Починить кран
```

`REFERENCES` не даст завести задачу несуществующего пользователя, `UNIQUE` — двух пользователей с одной почтой, а `DEFAULT now()` проставит время создания без участия приложения. Подробнее о выборе ключей, типов и ограничений — в заметке [Проектирование схемы](schema_design.md).

## Как это работает

**ACID** — набор свойств, которые делают транзакции надёжными:
- атомарность: транзакция выполняется целиком или откатывается целиком;
- согласованность: данные после транзакции остаются корректными;
- изолированность: параллельные транзакции не ломают результат друг друга;
- надёжность: после `COMMIT` данные не должны потеряться при сбое.

### Установка и запуск

Через `docker run`:
```sh
docker run --name postgres \
  --platform linux/arm64 \
  -e POSTGRES_USER=postgres \
  -e POSTGRES_PASSWORD=postgres \
  -e POSTGRES_DB=test_db \
  -p 5432:5432 \
  -v postgres_data:/var/lib/postgresql/data \
  -d postgres:16
```

Через `docker-compose`:
```yaml
services:
  postgres:
    image: postgres:16
    container_name: postgres
    platform: linux/amd64
    restart: unless-stopped
    environment:
      POSTGRES_USER: admin
      POSTGRES_PASSWORD: 1q2w3e
      POSTGRES_DB: database
      TZ: Europe/Moscow
      PGTZ: Europe/Moscow
    volumes:
      - postgres_volume:/var/lib/postgresql/data
    ports:
      - "5432:5432"
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U admin -d database"]
      interval: 5s
      timeout: 5s
      retries: 5

volumes:
  postgres_volume:
```

## Частые ошибки

- Индекс «на всякий случай» на каждую колонку → вставки и обновления замедляются, место растёт, а часть индексов планировщик никогда не выбирает → индексы создают под конкретные запросы и проверяют их `EXPLAIN ANALYZE`.
- Транзакция открыта, пока приложение ждёт пользователя или внешний сервис → блокировки держатся, `VACUUM` не может убрать старые версии строк, таблицы раздуваются → транзакции держат короткими, сетевые вызовы делают вне их.
- Внешний ключ без индекса → удаление родителя и `JOIN` по этой колонке сканируют всю дочернюю таблицу → индекс на каждую колонку с `REFERENCES`.
- `timestamp` без часового пояса → при другом `TZ` на сервере или у клиента время «уезжает» на несколько часов → `timestamptz`.
- `NOT IN (SELECT ...)`, где подзапрос возвращает `NULL` → результат всегда пустой, ошибки нет → `NOT EXISTS` или `WHERE ... IS NOT NULL` в подзапросе.

## Когда не использовать

Для кэша, сессий и счётчиков, которые нужны за доли миллисекунды и которые не жалко потерять, PostgreSQL — лишняя нагрузка на диск и транзакции: это задача [Redis](../redis/basics.md). Аналитика по сотням миллионов событий, где каждый запрос сканирует всю таблицу и считает агрегаты по нескольким колонкам, на строковом хранении проигрывает колоночному на порядок — такие данные выносят в [ClickHouse](../clickhouse/README.md). Файлы хранят в [S3](../s3/README.md), а полнотекстовый поиск с опечатками и релевантностью отдают [Elasticsearch](../elasticsearch/search.md).

Это не значит, что при первых признаках нагрузки нужен другой инструмент: один сервер PostgreSQL с подходящими индексами и партицированием держит терабайты данных и тысячи запросов в секунду. Отдельное хранилище заводят, когда задача действительно другая, а не когда забыли посмотреть `EXPLAIN`.

## Шпаргалка для собеседований

### Индексы

**Индекс** — отдельная структура данных, которая помогает быстрее находить строки без полного прохода по таблице.
Главный trade-off: чтение ускоряется, но `INSERT`, `UPDATE`, `DELETE` становятся дороже, потому что PostgreSQL должен обновлять не только таблицу, но и индексы.

**B-tree** — индекс по умолчанию в PostgreSQL. Это сбалансированное дерево: значения хранятся в отсортированном виде, а путь от корня до листьев остаётся коротким.
Поэтому поиск обычно работает за `O(log n)`, а глубина дерева часто остаётся небольшой даже на миллионах строк.

B-tree хорошо подходит для:
- `=`, `<`, `>`, `<=`, `>=`
- `BETWEEN`
- `ORDER BY`
- `MIN` / `MAX`
- префикса составного индекса

Пример:

```sql
CREATE INDEX idx_users_email ON users (email);
CREATE INDEX idx_orders_user_id_created_at ON orders (user_id, created_at);
```

Важно про составной индекс: индекс `(user_id, created_at)` хорошо работает по `user_id` и по `user_id + created_at`, но обычно не помогает для фильтра только по `created_at`.

Другие типы индексов:
- **Hash** — для точного равенства `=`, не подходит для сортировки и диапазонов.
- **GIN** — для JSONB, массивов, полнотекстового поиска; хранит "элемент -> строки".
- **GiST** — для геоданных, диапазонов и сложных структур; полезен там, где B-tree не описывает порядок значений.
- **Уникальный индекс** — не только ускоряет поиск, но и запрещает дубликаты.
- **Функциональный индекс** — индексирует выражение, например `lower(email)`.

Индекс может не использоваться, если:
- таблица маленькая;
- условие возвращает большую часть таблицы;
- статистика устарела;
- в запросе функция над колонкой, а функционального индекса нет;
- типы в условии приводятся неудачно;
- порядок колонок в составном индексе не подходит запросу.

### EXPLAIN

`EXPLAIN` показывает план запроса, но не выполняет его.
`EXPLAIN ANALYZE` выполняет запрос и показывает фактическое время, количество строк и выбранный план.

Частые операции в плане:
- `Seq Scan` — полный проход по таблице.
- `Index Scan` — чтение через индекс с обращением к таблице.
- `Index Only Scan` — чтение только из индекса, если данных достаточно в индексе и visibility map позволяет.
- `Bitmap Index Scan` + `Bitmap Heap Scan` — PostgreSQL сначала собирает подходящие строки из индекса, потом пачками читает таблицу.

На собеседовании важно не просто сказать "добавить индекс", а проверить план через `EXPLAIN ANALYZE`.

### Транзакции и ACID

**Транзакция** — группа операций, которая должна выполниться целиком или не выполниться совсем.

ACID:
- **Atomicity** — атомарность: все операции транзакции применяются вместе или откатываются вместе.
- **Consistency** — согласованность: после транзакции данные не нарушают constraints, foreign keys, типы и другие правила.
- **Isolation** — изолированность: параллельные транзакции не должны ломать результат друг друга.
- **Durability** — надёжность: после `COMMIT` данные сохраняются даже при сбое.

Если транзакцию долго не завершать, она удерживает ресурсы, может держать блокировки и мешать очистке старых версий строк.

### WAL

**WAL** (Write-Ahead Log) — журнал предзаписи. PostgreSQL сначала записывает информацию об изменении в WAL, а уже потом изменяет файлы таблиц и индексов на диске.

Зачем нужен WAL:
- восстановление после сбоя;
- гарантия `Durability` из ACID;
- репликация;
- point-in-time recovery, то есть восстановление на конкретный момент времени.

Главная идея: если PostgreSQL подтвердил `COMMIT`, но сервер сразу после этого упал, при следующем старте база сможет прочитать WAL и восстановить подтверждённые изменения.

**Checkpoint** — момент, когда PostgreSQL сбрасывает накопленные изменения из памяти на диск и фиксирует точку, с которой восстановление будет быстрее.
Без checkpoint после сбоя пришлось бы читать слишком большой объём WAL.

Короткая формулировка для собеседования: PostgreSQL пишет изменения сначала в WAL, потом в data files. После сбоя он проигрывает WAL с последнего checkpoint и возвращает базу в согласованное состояние.

### Уровни изоляции

Уровни изоляции определяют, какие изменения других транзакций видит текущая транзакция.

- **Read Committed** — уровень по умолчанию в PostgreSQL. Каждый запрос видит только уже закоммиченные данные, но разные запросы внутри одной транзакции могут видеть разные снимки.
- **Repeatable Read** — транзакция работает с одним снимком данных; повторное чтение тех же строк даёт тот же результат.
- **Serializable** — самый строгий уровень; PostgreSQL старается выполнить параллельные транзакции так, будто они шли последовательно. Возможны ошибки сериализации, транзакцию надо повторить.

В PostgreSQL `Read Uncommitted` фактически работает как `Read Committed`: грязного чтения нет.

Типичные аномалии:
- **Грязное чтение** — прочитали незакоммиченные данные другой транзакции.
- **Неповторяющееся чтение** — одна и та же строка изменилась между двумя чтениями.
- **Фантомное чтение** — между чтениями появились или исчезли строки, подходящие под условие.
- **Потерянное обновление** — две транзакции обновили одни данные, и одно изменение потерялось.

### MVCC

**MVCC** (Multi-Version Concurrency Control) — механизм, благодаря которому чтение не блокирует запись, а запись не блокирует чтение.

PostgreSQL не перезаписывает строку "на месте" при обычном `UPDATE`, а создаёт новую версию строки.
Разные транзакции видят разные версии данных в зависимости от своего snapshot.

Важные служебные поля:
- `xmin` — id транзакции, которая создала версию строки.
- `xmax` — id транзакции, которая удалила или заменила эту версию.

Из-за MVCC появляются старые версии строк. Их убирает `VACUUM`.
Если есть долгие транзакции, старые версии нельзя очистить, таблицы и индексы могут раздуваться.

### Блокировки и deadlock

PostgreSQL использует блокировки для согласованности данных.
Обычный `SELECT` не блокирует запись благодаря MVCC, но `UPDATE` блокирует изменяемые строки.

Примеры:
- две транзакции не могут одновременно изменить одну и ту же строку;
- `LOCK TABLE` может заблокировать таблицу целиком;
- индексы и constraints тоже могут приводить к ожиданиям блокировок.

**Deadlock** — ситуация, когда транзакции ждут друг друга по кругу.
PostgreSQL строит граф ожидания, обнаруживает цикл и прерывает одну из транзакций.

Как снижать риск deadlock:
- обновлять ресурсы в одинаковом порядке;
- держать транзакции короткими;
- не ждать пользовательского ввода внутри транзакции;
- индексировать foreign keys и часто используемые условия поиска;
- обрабатывать retry для транзакций, которые могут конфликтовать.
