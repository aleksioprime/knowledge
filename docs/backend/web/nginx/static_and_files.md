# Статика и передача файлов

Отдавать картинки, CSS и собранный фронтенд через Python-приложение расточительно: каждый файл проходит через воркер, который мог бы обрабатывать запросы к API. NGINX читает файлы с диска напрямую, кеширует их в браузере через заголовки и принимает большие загрузки, не занимая приложение. Эта заметка — про три задачи: раздать статику, принять загрузку и отдать закрытый файл после проверки доступа в приложении.

## Минимальный пример

Файлы из `/var/www/example/static` отдаются по пути `/static/`, остальные запросы уходят приложению:

```nginx
server {
    listen 80;
    root /var/www/example;

    location /static/ {
        try_files $uri =404;
        expires 7d;
    }

    location / {
        proxy_pass http://127.0.0.1:8000;
    }
}
```

Проверка: `curl -I http://localhost/static/app.css` возвращает `200` с заголовками `Expires` и `Cache-Control: max-age=604800`, а несуществующий файл — `404` без обращения к приложению.

## Как это работает

### Статические файлы

```nginx
server {
    listen 80;
    server_name example.com;

    root /var/www/example;

    location /static/ {
        try_files $uri =404;
        expires 7d;
        add_header Cache-Control "public";
    }

    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

`try_files` перебирает варианты по порядку: сначала файл по URI, потом каталог, потом запасной вариант. Строка `try_files $uri $uri/ /index.html` — стандартный приём для одностраничных приложений: любой неизвестный путь отдаёт `index.html`, а маршрут разбирает фронтенд.

`root` добавляет URI к указанному каталогу. Если используется `alias`, путь подменяется; завершающие слеши у `location` и `alias` должны быть согласованы:

```nginx
location /uploads/ {
    alias /srv/user-files/;
    try_files $uri =404;
}
```

### Ограничение загрузки

```nginx
server {
    client_max_body_size 20m;
    client_body_timeout 30s;

    location /api/uploads {
        proxy_pass http://127.0.0.1:8000;
        proxy_request_buffering off;
        proxy_read_timeout 5m;
    }
}
```

Отключать `proxy_request_buffering` следует только когда приложение действительно обрабатывает поток. Иначе NGINX может сначала принять тело и защитить upstream от медленного клиента.

### Закрытые файлы

Приложение может проверить доступ, а передачу файла поручить NGINX через внутренний location:

```nginx
location /protected-files/ {
    internal;
    alias /srv/protected/;
}
```

После проверки приложение отвечает заголовком `X-Accel-Redirect: /protected-files/report.pdf`. Нельзя формировать такой путь прямо из непроверенного пользовательского ввода.

Подробнее о форматах загрузки, скачивании и диапазонах: [передача файлов по HTTP](../http/file_transfer.md).

## Частые ошибки

- `alias /srv/files` без завершающего слеша при `location /files/` → NGINX склеивает путь в `/srv/filesreport.pdf`, ответ 404 → ставить слеш в обоих местах или в обоих не ставить.
- `root` внутри `location /static/` указывает на сам каталог статики → NGINX ищет `/var/www/static/static/app.css` → для `root` указывать родительский каталог, для подмены пути брать `alias`.
- Файлы принадлежат пользователю, а процесс NGINX работает от `www-data` → ответ 403 при существующем файле, в `error.log` строка `Permission denied` → дать права на чтение файлам и на выполнение всем каталогам по пути.
- `expires 7d` для `index.html` и файлов без хеша в имени → после деплоя браузеры неделю показывают старую версию → долгий кеш только для файлов с хешем в имени, для `index.html` — `Cache-Control: no-cache`.
- Загрузка файла падает с 413 → `client_max_body_size` по умолчанию 1 МБ → задать значение в `server` или `location` для загрузок.
- `internal` забыт у `location` для закрытых файлов → любой, кто знает путь, скачивает файл без проверки в приложении → всегда добавлять `internal` и отдавать путь только через `X-Accel-Redirect`.

## Когда не использовать

Для десятков файлов на маленьком сайте `StaticFiles` в FastAPI или `whitenoise` в Django достаточно, и отдельный конфиг NGINX только усложняет деплой. Для большого объёма медиа или аудитории в разных регионах файлы лучше отдавать из объектного хранилища (S3) через CDN, а NGINX оставить для API. Пользовательские загрузки тоже удобнее отправлять прямо в хранилище по подписанной ссылке, не пропуская через сервер.
