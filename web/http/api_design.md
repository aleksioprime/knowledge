# Проектирование API: REST, версионирование, gRPC

API живёт дольше, чем кажется. Фронтенд, мобильное приложение и соседние сервисы начинают на него опираться, и каждое неудачное решение — глагол в адресе, ошибка с кодом 200, переименованное поле — потом приходится поддерживать годами. Эта заметка о том, как спроектировать API, чтобы им было удобно пользоваться и его можно было менять, ничего не ломая. Сначала REST как стиль, потом версионирование, потом gRPC — альтернатива для общения сервисов между собой.

Что такое методы, коды ответов и заголовки, разобрано в заметке про [структуру запросов и ответов](request_response.md); здесь — как ими пользоваться при проектировании.

## REST: ресурсы и действия над ними

REST (Representational State Transfer) — не протокол и не библиотека, а стиль. Его главная идея: API — это набор **ресурсов** (задачи, метки, пользователи), у каждого есть адрес, а действие над ресурсом выражается **HTTP-методом**. Адрес — существительное, метод — глагол.

Для «Задачника» это выглядит так:

| Запрос | Что делает | Ответ |
|---|---|---|
| `GET /tasks` | Список задач | `200` и список |
| `POST /tasks` | Создать задачу | `201`, заголовок `Location: /tasks/42` |
| `GET /tasks/42` | Одна задача | `200` или `404` |
| `PUT /tasks/42` | Заменить задачу целиком | `200` |
| `PATCH /tasks/42` | Изменить часть полей (`{"done": true}`) | `200` |
| `DELETE /tasks/42` | Удалить задачу | `204` без тела |
| `GET /tasks/42/labels` | Метки задачи | `200` и список |
| `PUT /tasks/42/labels/work` | Повесить метку на задачу | `204` |
| `DELETE /tasks/42/labels/work` | Снять метку | `204` |

**Вложенные ресурсы** показывают принадлежность: метки *этой* задачи — `/tasks/42/labels`. Глубже одного-двух уровней лучше не уходить: `/users/7/projects/3/tasks/42/labels` трудно читать, а задачу всё равно можно найти по её собственному `id` — `/tasks/42`.

Даже действие, которое не похоже на «создать» или «изменить», обычно можно выразить через ресурс. «Закрыть задачу» — это `PATCH /tasks/42` с `{"done": true}`, а не `POST /closeTask`. Если действие действительно не сводится к полю (например, «перезапустить импорт»), допустим `POST /imports/15/restart`, но это исключение, а не правило.

### Коллекции: пагинация и фильтры

Список нельзя отдавать целиком: сегодня задач десять, через год — сто тысяч. Фильтры, сортировка и пагинация передаются параметрами строки запроса, а в ответ кладут сами элементы и сведения о странице:

```python
from fastapi import FastAPI, Query
from pydantic import BaseModel

app = FastAPI()
tasks = [{'id': i, 'title': f'Задача {i}', 'done': i % 3 == 0} for i in range(1, 51)]


class TaskPage(BaseModel):
    items: list[dict]
    total: int
    limit: int
    offset: int


@app.get('/tasks')
def list_tasks(
    done: bool | None = None,
    limit: int = Query(20, ge=1, le=100),
    offset: int = Query(0, ge=0),
) -> TaskPage:
    found = [t for t in tasks if done is None or t['done'] == done]
    return TaskPage(items=found[offset : offset + limit], total=len(found), limit=limit, offset=offset)
```

```text
GET /tasks?done=true&limit=2&offset=4
200 {"items": [{"id": 15, ...}, {"id": 18, ...}], "total": 16, "limit": 2, "offset": 4}

GET /tasks?limit=1000
422 Input should be less than or equal to 100
```

Верхняя граница `limit` обязательна: без неё один клиент с `?limit=1000000` положит базу. На больших таблицах `offset` работает медленно (базе всё равно приходится пропустить все предыдущие строки), и вместо него используют **курсор**: клиент передаёт `id` последнего полученного элемента, а сервер отдаёт следующие за ним.

### Коды ответов

Код ответа — часть контракта: по нему клиент, балансировщик и мониторинг понимают, что произошло. `201` после создания, `204` после удаления, `404` если объекта нет, `422` если данные не прошли проверку, `409` при конфликте. Таблица с примерами из «Задачника» — в заметке про [ошибки в FastAPI](../../framework/fast_api/docs/errors.md), полный список — в [структуре запросов и ответов](request_response.md#ответ).

### Идемпотентность: что можно повторять

Сеть ненадёжна: клиент отправил запрос, а ответ не дошёл. Можно ли повторить? Зависит от метода.

- `GET`, `PUT`, `DELETE` **идемпотентны**: повтор приводит сервер в то же состояние. Два `PUT /tasks/42` с одинаковым телом дадут одну и ту же задачу; второй `DELETE /tasks/42` ничего не удалит (вернёт `404` или `204` — состояние то же). Такие запросы клиент, прокси и HTTP-библиотеки могут повторять смело.
- `POST` **не идемпотентен**: два `POST /tasks` создадут две одинаковые задачи. Если повтор нужен (оплата, заказ), клиент передаёт заголовок `Idempotency-Key` с уникальным значением, а сервер запоминает, какие ключи уже обработал, и на повтор возвращает прежний ответ.
- `PATCH` может быть любым: `{"done": true}` идемпотентен, а «увеличить счётчик на 1» — нет.

Поэтому важно не путать `PUT` и `PATCH`. `PUT` заменяет ресурс целиком: поле, которое не пришло, становится значением по умолчанию. `PATCH` меняет только присланные поля — так устроен `TaskUpdate` в заметке про [схемы](../../framework/fast_api/docs/schemas.md).

### Частые ошибки дизайна

- **Глаголы в адресе.** `GET /getTasks`, `POST /createTask`, `POST /tasks/42/delete` — действие уже выражено методом. Правильно: `GET /tasks`, `POST /tasks`, `DELETE /tasks/42`.
- **Ответ 200 с ошибкой в теле.** `200 {"error": "not found"}` — клиентская библиотека не выбросит исключение, кэш сохранит ответ, а мониторинг покажет, что ошибок нет. Ошибка должна менять код.
- **`GET`, который что-то меняет.** `GET /tasks/42/complete` выполнится, когда браузер заранее подгрузит ссылку или поисковый робот пройдёт по сайту. `GET` должен только читать.
- **Разный стиль в одном API.** `/tasks`, `/Label`, `/user_profiles`, поля `dueDate` и `created_at` вперемешку. Выберите одно соглашение (множественное число, `snake_case` или `camelCase`) и держитесь его.
- **Список без пагинации.** Работает, пока данных мало, а потом ответ весит мегабайты и выполняется секундами.

### Минусы REST

У REST нет встроенного **строгого контракта**: стиль говорит, как называть адреса, но не говорит, какие поля в ответе, какие обязательны и какого они типа. Клиент узнаёт это из документации или опытным путём. Эту дыру закрывает **OpenAPI** — машиночитаемое описание API, по которому строится документация, генерируются клиенты и проверяется совместимость. FastAPI строит его сам; как сделать его полезным, разобрано в заметке про [документацию API](../../framework/fast_api/docs/openapi.md).

Другие минусы: текстовый JSON тяжелее бинарных форматов, а один экран приложения часто требует нескольких запросов (задача, её метки, автор).

## Обратная совместимость

Опубликованный API нельзя просто поменять: у вас нет контроля над клиентами. Мобильное приложение, установленное полгода назад, продолжит отправлять старые запросы и ждать старые ответы. Поэтому изменения делят на два вида.

**Совместимые** — старые клиенты их не замечают:

- новый эндпоинт;
- новое **необязательное** поле в запросе (со значением по умолчанию);
- новое поле в ответе (клиенты должны игнорировать незнакомые поля);
- новое значение там, где клиент его не разбирает.

**Ломающие** — старые клиенты перестают работать:

- удаление или переименование поля, эндпоинта, параметра;
- смена типа поля (`id` был числом, стал строкой);
- новое **обязательное** поле в запросе;
- более строгая проверка (раньше название до 500 символов, теперь до 200);
- изменение смысла: `done: bool` заменили на `status: "open" | "in_progress" | "done"`;
- новое значение перечисления, если клиент обрабатывает их через `switch` без ветки по умолчанию.

Совместимые изменения выкатываются без церемоний. Для ломающих нужна **новая версия API**: старые клиенты остаются на старой, новые переходят на новую.

## Версионирование: три способа

| Способ | Пример | Плюсы | Минусы |
|---|---|---|---|
| В пути | `GET /api/v2/tasks` | Видно сразу: в логах, в браузере, в `curl`. Балансировщик или API Gateway может отправить `/api/v1/` на старые серверы, а `/api/v2/` — на новые. Кэш различает версии без настроек | Формально у одной задачи становится два адреса |
| Параметр запроса | `GET /tasks?version=2` | Легко добавить к существующему API | Легко забыть; непонятно, какая версия без параметра; маршрутизировать по параметру неудобно |
| Заголовок | `Accept: application/vnd.tasker.v2+json` или `X-API-Version: 2` | Адреса не меняются — «чистый» REST | Версию не видно в логах доступа и в адресной строке; кэш и CDN должны учитывать заголовок (`Vary`); труднее проверять руками |

На практике чаще всего выбирают **версию в пути**: она самая простая для всех, кто с API работает, — от фронтендера до дежурного, который читает логи NGINX. Номер версии — только мажорный (`v1`, `v2`): совместимые изменения версию не меняют.

### Две версии в FastAPI

Каждая версия — отдельный роутер со своим префиксом и своими схемами, а бизнес-логика общая. Пусть в v2 поле `done` заменили на `status`:

```python
from typing import Literal

from fastapi import APIRouter, Depends, FastAPI, HTTPException, Response
from pydantic import BaseModel

tasks = {
    1: {'id': 1, 'title': 'Купить хлеб', 'status': 'done'},
    2: {'id': 2, 'title': 'Сдать отчёт', 'status': 'in_progress'},
}


def find_task(task_id: int) -> dict:
    if task_id not in tasks:
        raise HTTPException(status_code=404, detail='Задача не найдена')
    return tasks[task_id]


class TaskV1(BaseModel):
    id: int
    title: str
    done: bool


class TaskV2(BaseModel):
    id: int
    title: str
    status: Literal['open', 'in_progress', 'done']


def mark_deprecated(response: Response) -> None:
    response.headers['Deprecation'] = '@1793491200'  # 1 ноября 2026
    response.headers['Sunset'] = 'Sat, 01 May 2027 00:00:00 GMT'
    response.headers['Link'] = '</api/v2/tasks>; rel="successor-version"'


v1 = APIRouter(prefix='/api/v1', tags=['v1'], deprecated=True, dependencies=[Depends(mark_deprecated)])
v2 = APIRouter(prefix='/api/v2', tags=['v2'])


@v1.get('/tasks/{task_id}')
def get_task_v1(task_id: int) -> TaskV1:
    task = find_task(task_id)
    return TaskV1(id=task['id'], title=task['title'], done=task['status'] == 'done')


@v2.get('/tasks/{task_id}')
def get_task_v2(task_id: int) -> TaskV2:
    return TaskV2(**find_task(task_id))


app = FastAPI(title='Задачник')
app.include_router(v1)
app.include_router(v2)
```

Проверка через `TestClient`:

```python
from fastapi.testclient import TestClient

client = TestClient(app)

response = client.get('/api/v1/tasks/2')
print(response.json())             # {'id': 2, 'title': 'Сдать отчёт', 'done': False}
print(response.headers['sunset'])  # Sat, 01 May 2027 00:00:00 GMT

response = client.get('/api/v2/tasks/2')
print(response.json())                     # {'id': 2, 'title': 'Сдать отчёт', 'status': 'in_progress'}
print('deprecation' in response.headers)  # False
```

Данные хранятся в новом формате, а v1 — это **адаптер**, который переводит их в старый. Так старая версия не тянет за собой старую логику: когда её отключат, удалится один роутер и одна схема. В `/docs` эндпоинты v1 будут сгруппированы отдельно и зачёркнуты как устаревшие (`deprecated=True` у роутера).

### Как вывести старую версию из эксплуатации

Отключать версию без предупреждения нельзя. Обычный порядок:

1. Объявить, что версия устарела, и назначить дату отключения: в документации, в списке изменений, письмом владельцам интеграций.
2. Добавить в ответы старой версии заголовки. `Deprecation` сообщает, что эндпоинт устарел (значение — дата в формате `@<unix-время>`), `Sunset` — когда он перестанет работать (обычная HTTP-дата), `Link` с `rel="successor-version"` — куда переходить. Клиентские библиотеки и API Gateway умеют предупреждать о таких ответах.
3. Смотреть в логах и метриках, кто ещё ходит в старую версию, и напоминать им лично.
4. После даты `Sunset` отвечать `410 Gone`, а потом удалить код.

## gRPC

Внутри системы сервисы постоянно вызывают друг друга: сервис уведомлений спрашивает у сервиса задач, какие задачи просрочены. Для таких вызовов REST избыточен: JSON нужно сериализовать и разбирать, контракт описан отдельно от кода, а мыслить приходится ресурсами, хотя нужно просто «вызвать функцию на другом сервере». gRPC решает именно эту задачу.

gRPC — фреймворк **удалённого вызова процедур** (RPC, Remote Procedure Call). Вместо ресурсов и методов HTTP — сервис с методами, как у обычного класса: `TaskService.GetTask`, `TaskService.CreateTask`. Клиент вызывает метод так, будто объект лежит рядом, а библиотека сама упаковывает аргументы, отправляет их по сети и распаковывает ответ.

### Контракт в `.proto`

Всё начинается с файла `.proto` на языке Protocol Buffers (protobuf): какие у сервиса методы и из каких полей состоят сообщения. Этот файл и есть строгий контракт — по нему генерируется код и для сервера, и для клиента на любом языке.

```proto
syntax = "proto3";

package tasker.v1;

service TaskService {
  rpc GetTask(GetTaskRequest) returns (Task);
  rpc ListTasks(ListTasksRequest) returns (ListTasksResponse);
  rpc CreateTask(CreateTaskRequest) returns (Task);
}

message Task {
  // Поле 4 когда-то было `priority`: номер и имя заняты навсегда.
  reserved 4;
  reserved "priority";

  int64 id = 1;
  string title = 2;
  bool done = 3;
  repeated string labels = 5;
}

message GetTaskRequest {
  int64 id = 1;
}
```

Полный контракт, сервер и клиент — в папке [examples/grpc](examples/grpc/README.md).

### Номера полей важнее имён

`= 1`, `= 2` — не значения по умолчанию, а **номера полей**. В бинарном сообщении protobuf передаются только номера и значения, имён там нет. Вот задача `id=7, title='Сдать отчёт', done=True` в байтах:

```text
b'\x08\x07\x12\x15\xd0\xa1\xd0\xb4...\x18\x01'
#  ^поле 1 = 7  ^поле 2, 21 байт строки  ^поле 3 = 1
```

Отсюда правила совместимости, которые надо помнить наизусть:

- **переименовать поле можно** — имя не передаётся по сети, старые клиенты ничего не заметят (но сломается код, который обращается к полю по старому имени, и JSON-представление сообщения — в нём используются имена);
- **менять номер или тип поля нельзя** — старый клиент прочитает байты не так или потеряет значение;
- **добавить поле можно** — с новым номером; старый клиент его пропустит, а у нового в старых сообщениях оно будет пустым;
- **удалённый номер нужно зарезервировать** (`reserved 4;`), иначе кто-нибудь займёт его под новое поле, и старые клиенты будут читать в нём чужие данные. `protoc` не даст использовать зарезервированный номер:

```text
bad.proto:13:12: Field "priority_level" uses reserved number 4.
```

Ещё одна особенность proto3: у всех полей есть значение по умолчанию (`0`, `""`, `false`), и «поле не передали» неотличимо от «передали ноль». Если отличие важно, поле помечают `optional`.

За счёт номеров вместо имён сообщения компактные. Та же задача из клиента примера занимает 51 байт в protobuf и 98 байт в JSON (`json.dumps(..., ensure_ascii=False)`).

### Генерация кода, сервер и клиент

Код по контракту генерирует `grpcio-tools`:

```bash
pip install grpcio grpcio-tools
python -m grpc_tools.protoc -I. --python_out=. --pyi_out=. --grpc_python_out=. tasks.proto
```

Появятся `tasks_pb2.py` (классы сообщений), `tasks_pb2.pyi` (подсказки типов для редактора) и `tasks_pb2_grpc.py` (базовый класс сервера и клиентская заглушка). Руками их не правят и обычно не коммитят — генерируют при сборке.

Сервер наследуется от сгенерированного класса и реализует методы. Ошибки — не HTTP-коды, а собственные статусы gRPC (`NOT_FOUND`, `INVALID_ARGUMENT`, `UNAVAILABLE`, `DEADLINE_EXCEEDED`):

```python
class TaskService(tasks_pb2_grpc.TaskServiceServicer):
    def GetTask(self, request, context):
        task = self.tasks.get(request.id)
        if task is None:
            context.abort(grpc.StatusCode.NOT_FOUND, f'Задача {request.id} не найдена')
        return task
```

Клиент работает через заглушку (stub) — объект, у которого есть те же методы, что у сервиса:

```python
with grpc.insecure_channel('localhost:50051') as channel:
    stub = tasks_pb2_grpc.TaskServiceStub(channel)
    task = stub.GetTask(tasks_pb2.GetTaskRequest(id=3), timeout=2)
```

Вывод клиента из примера:

```text
Создана: 3 Позвонить врачу ['здоровье']
Получена: 3 Позвонить врачу открыта
Открытые: ['Сдать отчёт', 'Позвонить врачу']
Размер сообщения: 51 байт
Ошибка: NOT_FOUND - Задача 999 не найдена
Ошибка: INVALID_ARGUMENT - Название не может быть пустым
```

`timeout=2` — **дедлайн**: если сервер не ответит за 2 секунды, клиент получит `DEADLINE_EXCEEDED`. Задавайте его всегда, иначе зависший сервис потянет за собой всех, кто его вызывает. Для асинхронного кода есть `grpc.aio` с тем же API и `await`.

### Транспорт и виды вызовов

gRPC работает поверх [HTTP/2](versions.md#http2): все вызовы идут по одному долгоживущему соединению параллельными потоками. Это и даёт четыре вида вызовов:

| Вид | В `.proto` | Пример |
|---|---|---|
| Унарный (unary) | `rpc GetTask(Req) returns (Task)` | Запрос — ответ, как обычная функция |
| Поток от сервера (server streaming) | `returns (stream Task)` | Сервер отдаёт задачи по одной по мере чтения из базы |
| Поток от клиента (client streaming) | `rpc Import(stream Task) returns (Report)` | Клиент загружает тысячу задач, сервер отвечает итогом |
| Двусторонний поток (bidirectional) | `stream` с обеих сторон | Обе стороны пишут и читают одновременно, как в чате |

### Минусы gRPC

- **Браузер не умеет вызывать gRPC напрямую**: у браузерного JavaScript нет нужного контроля над HTTP/2. Нужен gRPC-Web с прокси (Envoy) или шлюз, переводящий REST/JSON в gRPC (grpc-gateway). Поэтому публичные API обычно остаются на REST.
- **Балансировка.** Клиент открывает одно HTTP/2-соединение и шлёт по нему все вызовы. Балансировщик уровня L4 (распределяет TCP-соединения) отправит это соединение на один экземпляр сервиса — и вся нагрузка от клиента окажется на нём, а остальные будут простаивать. Нужен балансировщик уровня L7, который понимает HTTP/2 и распределяет отдельные запросы (Envoy, NGINX с `grpc_pass`), или балансировка на стороне клиента: клиент сам знает список экземпляров и чередует их.
- **Труднее отлаживать.** Бинарное сообщение не прочитать глазами и не отправить через `curl`. Для ручных вызовов есть `grpcurl` и Postman, но им нужен `.proto` или включённая на сервере рефлексия.
- **Нужна общая инфраструктура контрактов**: `.proto`-файлы должны быть доступны всем командам (общий репозиторий или реестр схем), а генерация кода — встроена в сборку.

## Что выбрать: REST, gRPC или GraphQL

| | REST | gRPC | GraphQL |
|---|---|---|---|
| Модель | Ресурсы и методы HTTP | Сервисы и методы | Один адрес, клиент описывает, какие поля нужны |
| Формат | Обычно JSON | Protobuf (бинарный) | JSON |
| Контракт | Необязателен, обычно OpenAPI | Обязателен, `.proto` | Обязателен, схема GraphQL |
| Браузер | Да | Только через gRPC-Web или шлюз | Да |
| Стриминг | Ограниченно (SSE, WebSocket отдельно) | Встроенный, в обе стороны | Подписки (subscriptions) |
| Кэширование HTTP | Да, `GET` кэшируется | Нет | Сложно: почти всё — `POST` на один адрес |
| Отладка | `curl`, браузер | `grpcurl` | Встроенные песочницы (GraphiQL) |

- **Публичный API, браузер, мобильное приложение, интеграции с партнёрами** → REST. Его понимают все инструменты, его легко кэшировать и отлаживать.
- **Внутренние вызовы между сервисами, много вызовов с малыми сообщениями, стриминг, строгий контракт между командами** → gRPC.
- **Много разных клиентов, которым нужны разные срезы данных** (один экран — задача с автором и метками, другой — только заголовки), и не хочется плодить эндпоинты → GraphQL. Цена — сложнее защищаться от тяжёлых запросов и кэшировать.

Их часто совмещают: снаружи REST через [API Gateway](../../microservices/api_gateway/README.md), внутри — gRPC между сервисами.

## Частые ошибки

- **Ломающее изменение без новой версии.** Переименовали поле в ответе — мобильное приложение, которое пользователи не обновили, падает. Перед изменением задайте себе вопрос: «Что увидит клиент, собранный полгода назад?»
- **Новая версия на каждое изменение.** `v7` через год — значит, совместимые изменения тоже выпускались как ломающие. Добавление поля не требует новой версии.
- **Переиспользование номера поля в protobuf.** Удалили поле `4`, через месяц добавили новое с номером `4` другого типа — старые клиенты читают мусор. Всегда пишите `reserved`.
- **gRPC за L4-балансировщиком.** Экземпляров пять, а нагружен один. Проверяйте распределение нагрузки по метрикам каждого экземпляра.
- **Вызов без дедлайна.** Один медленный сервис забирает потоки у всех, кто его вызывает, и сбой расползается по системе. Подробнее — в заметке про [устойчивость](../../design/docs/resilience.md).
