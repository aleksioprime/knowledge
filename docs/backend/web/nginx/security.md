# Ограничения и безопасность NGINX

Один клиент за минуту отправил десять тысяч запросов на `/api/login`, и приложение тратит все воркеры на проверку паролей для него, а остальные пользователи ждут. Отбрасывать такой трафик в самом приложении поздно: запрос уже занял соединение и воркер. NGINX стоит раньше и умеет ограничить частоту запросов, число соединений и размер тела ещё до того, как запрос дойдёт до приложения. Но NGINX не заменяет проверку доступа и входных данных в самом приложении.

## Минимальный пример

Не больше 10 запросов в секунду с одного адреса на `/api/`, всплеск до 20 запросов разрешён:

```nginx
limit_req_zone $binary_remote_addr zone=api_per_ip:10m rate=10r/s;

server {
    listen 80;

    location /api/ {
        limit_req zone=api_per_ip burst=20 nodelay;
        proxy_pass http://127.0.0.1:8000;
    }
}
```

Проверка: `for i in $(seq 30); do curl -s -o /dev/null -w '%{http_code}\n' http://localhost/api/tasks; done` — первые двадцать с лишним ответов `200`, дальше `503`, пока за секунду не освободится место.

## Как это работает

### Ограничение частоты

Зона объявляется в контексте `http`, а правило применяется в `server` или `location`:

```nginx
limit_req_zone $binary_remote_addr zone=api_per_ip:10m rate=10r/s;
limit_conn_zone $binary_remote_addr zone=connections_per_ip:10m;

server {
    location /api/ {
        limit_req zone=api_per_ip burst=20 nodelay;
        limit_conn connections_per_ip 20;
        proxy_pass http://127.0.0.1:8000;
    }
}
```

`limit_req` работает как дырявое ведро: `rate` — скорость, с которой запросы уходят в приложение, `burst` — размер очереди. Без `nodelay` лишние запросы ждут своей очереди, с `nodelay` первые `burst` запросов проходят сразу, а следующие отклоняются с кодом 503 (код можно поменять через `limit_req_status`). `limit_conn` ограничивает число одновременных соединений с одного адреса. Зона в 10 МБ вмещает примерно 160 тысяч адресов.

Если NGINX находится за доверенным балансировщиком, сначала необходимо корректно настроить real IP. Иначе все запросы будут выглядеть пришедшими с одного адреса либо клиент сможет подделать адрес.

### Границы запроса

```nginx
client_max_body_size 20m;
client_body_timeout 15s;
client_header_timeout 15s;
keepalive_timeout 30s;
send_timeout 30s;
```

Значения подбираются под реальные клиенты и размеры данных. Слишком строгие лимиты нарушат медленные загрузки, слишком мягкие увеличат стоимость атаки.

### Защитные заголовки

```nginx
add_header X-Content-Type-Options "nosniff" always;
add_header Referrer-Policy "strict-origin-when-cross-origin" always;
```

CSP и CORS лучше задавать там, где известна семантика ответа. Избыточные или дублирующиеся заголовки от приложения и NGINX могут дать неожиданный результат. Подробнее: [защитные HTTP-заголовки](../security/security_headers.md).

### Дополнительные меры

- принимать только известные `server_name` и добавить отдельный default server для неизвестных доменов;
- скрывать служебные endpoints и не публиковать внутренние порты приложений;
- ограничивать методы там, где набор действительно фиксирован;
- регулярно обновлять NGINX и TLS-библиотеки;
- анализировать access/error logs, не записывая токены и другие секреты;
- использовать внешний DDoS-фильтр, если атака способна заполнить сетевой канал.

## Частые ошибки

- NGINX стоит за балансировщиком, а `set_real_ip_from` и `real_ip_header` не настроены → все клиенты видны с адресом балансировщика, и лимит на один адрес блокирует всех сразу → настроить real IP только для доверенных адресов балансировщика.
- `limit_req` без `burst` → страница, которая делает десять запросов к API при загрузке, получает 503 на часть из них → задавать `burst` под реальный всплеск от одного клиента.
- `add_header` в `location` при наличии `add_header` в `server` → заголовки из `server` в этом `location` пропадают, потому что директива не наследуется при переопределении → повторять все нужные заголовки в каждом `location` или выносить в `include`.
- `add_header` без `always` → заголовок не добавляется к ответам 4xx и 5xx → добавлять `always`, если заголовок защитный.
- Лимит частоты считается надёжной защитой от перебора паролей → атакующий меняет адреса, лимит на IP не срабатывает → в приложении считать попытки по логину и добавлять задержку или блокировку, подробнее в заметке [ограничение частоты запросов](../../design/rate_limiting.md).
- `client_max_body_size` задан только в `http`, а в `server` для загрузок указан другой → действует ближайшее значение, и загрузка падает с 413 там, где не ожидали → проверять итоговое значение для каждого `location` с загрузками.

## Когда не использовать

Лимиты на уровне NGINX считают запросы по адресу или другой переменной и не знают, кто за ними стоит. Квоты по пользователю или тарифу, лимиты с учётом стоимости операции и блокировка аккаунта после неудачных входов — задача приложения или шлюза с доступом к токену. Если атака заполняет сетевой канал, NGINX уже ничего не отбросит: нужен внешний фильтр перед сервером.

Защитные заголовки, которые зависят от содержимого ответа (CSP с nonce, CORS для конкретных источников), удобнее выставлять в приложении: там известно, какая страница или API отвечает.
